# PR #60 (deterministic fake scheduler): review

## Review of #60 (Opus subagent, 2026-10-05)

Verdict: NO-GO

One High finding blocks the merge, and its fix is small. The rest of the PR is sound. Accounting is correct for inputs the schema allows. The sort is a total order over unique ids, so the result is deterministic. Run is atomic: it works on a local copy and writes back only when every step succeeds. The property tests do real contention: 705 of 800 leases are waiting after the first Step across the 20 seeds. I ran 9 mutations on a copy of the code. 8 were caught, including `>` changed to `>=` in fits, `limit+1`, releasing only the first reservation, checking only the first reservation, and never re-granting a waiting lease. The one that survived reverses the id tie-break, which is only a policy choice.

How I checked: I copied the code into `rv60/` with `.git` left out and added probe tests and sed mutations there. The worktree was not touched.

### High

**H1. Evidence-target leases settle without a restore. `apply` passes `evidenceTarget=false` for every lease.** (`internal/capacity/fakesched/fakesched.go:143-145`)
`New` accepts `evidence_target` groups, because `capacity.CheckGroup` allows them. The test at `fakesched_test.go:279` even builds one. A lease that reserves such a group goes through the plain settle path in Run. The probe showed: `Run(id, &att, lease.Completed)` gives `err=nil state=settled receipt=<nil>`, and the target's slot comes back at once. That breaks note 05 §"Evidence-target leases" [G5] and the release rule `on_restore_verified` (13, D40), and the state machine's guard never sees the case. The PR says "the state machine refuses any other path". Here it cannot refuse, because it was told the lease is not an evidence target.
Fix (choose one):
- (a) Simplest: in `Request`, refuse any reservation on a group of kind `ResourceGroupKindEvidenceTarget`, with an error like "the fake scheduler does not model restores". Add that case to `TestRefusals`.
- (b) Work out `evidenceTarget` from the lease's groups and pass it to `ApplyLease`. Run then drives `RestoreStarted` → `RestoreVerified{Receipt}` → `Settled` and releases the slot only after that.

Do not just pass `true` on its own. Run would then fail at `Settled`, the lease would stay granted forever, and the claim that every lease can end would break.

### Medium

**M1. A negative amount is accepted and breaks the "never more than the limit" invariant.** (`fakesched.go:69`, `:84`, `:126`)
`types.Amount` is `int64`. The schema minimum of 0 is not checked here, and `int64(-3) > limit` is false, so Request accepts the lease. Probe: on a 3-slot group I requested one lease reserving `-3` slots and four leases reserving `3` slots each. One Step granted 3 leases, and `Reserved` reported 3. Two real 3-slot leases were running at once on a 3-slot group.
Fix: in `Request`, refuse `r.Amount < 0`. Optionally refuse `> 9007199254740991` too, to match the schema's `Amount` definition. Add a refusal test.

**M2. `reserved + amount` can overflow `int64`.** (`fakesched.go:84`)
`CheckGroup` does not cap the limit. Probe: with limit = `MaxInt64`, two leases (`MaxInt64` and `10`) were both granted, and `reserved` became `-9223372036854775799`. Inputs that pass the schema (≤ 2^53) cannot reach this, but Go callers can.
Fix: compare without adding: `int64(r.Amount) > *limit - g.reserved`. This cannot overflow, since 0 ≤ reserved ≤ limit. Also cap the limit in `New`, or refuse such a group there.

**M3. A waiting lease keeps a stale hold, and the test comment claims otherwise.** (`fakesched.go:129-137`; `fakesched_test.go:210-216`)
Step only sets a hold when a lease moves from requested to waiting. If the group blocking a waiting lease changes, the hold still names the old group. Probe: after tokens were freed, `both` was blocked only by broker credit, yet it showed `hold=quota_reset on rg_…tokens`. The comment at test line 210 says "it waits on the broker's hold", but the assertion at line 214 checks only `State`. That breaks 05's rule that a hold names its signal instance, and it would send a wake-up for the wrong signal.
Fix: in Step, when a waiting lease's blocking group differs from `l.Hold.SignalInstance`, or its hold code changes, apply `Requested` and then `Waiting` with the new hold. The state machine has no waiting → waiting step. Then assert `w.Hold.Hold == "broker_credit_exhausted"` and `SignalInstance == gBroker` at test line 214.

### Low

- **L1. A Step that fails part-way through leaves its earlier grants in place but reports none.** (`fakesched.go:116-135`) If a hold is missing from the registry, Step errors after it has already granted and reserved earlier leases. It returns `nil` for the granted list, so the caller never learns about those grants. Probe with an empty holds map: `granted=[] err=hold "quota_reset" is not registered`, while lease 1 was `granted` with `reserved=3`. Fix: in `New`, check that `quota_reset` and `broker_credit_exhausted` are both in `holds`, and/or return the grants made so far together with the error.
- **L2. `Reserved` on an unknown group panics** with a nil dereference (`fakesched.go:185`). Return `(int64, bool)`, or 0.
- **L3. Release rules are ignored.** Every reservation comes back when the lease ends, even for `on_window_reset` and `on_attempt_end`. Release rules are [M7], so this is acceptable for M0. Say so in the package doc so later tests do not rely on it.
- **L4. `holds` is kept by reference** (`fakesched.go:36`), so later changes by the caller change what the scheduler sees. `maps.Clone` it.

### Info: liveness and policy

- "Every lease can end" holds only if the driver calls `Run` on every granted lease. The state machine has no way out of requested or waiting other than a grant. Request refuses any lease larger than its group's limit, and limits never change after `New`, so each waiting lease fits once the scheduler is empty. `drive` meets this condition, and the 1000-round guard would catch a lease that never ends.
- Nothing stops a big high-priority lease from being starved. A pass skips a lease that does not fit and gives the capacity to smaller lower-priority ones, so with leases that keep arriving the big one can starve. A finite population always drains, so this is fine for the fake. Record it as a policy note for the M2 scheduler.
- Determinism: leases are taken from the map and then sorted by (priority descending, id ascending), which is a total order over unique ids, so the order is the same every run. The mutation that removed the tie-break was caught. Reversing the id tie-break survived, which is fine because that is policy.
- Taking out Run's explicit checks is safe. `Expired` and `AttemptStarted` are only allowed from `granted`. A waiting, requested or finished lease gets `ErrTransition` before any capacity is touched, and Run commits nothing on error. The guard at `:169` is redundant with the state machine, but harmless.

### Lead notes on round 1 (applied)

- H1: evidence-target reservations are refused in `Request`. Their slot returns only on a verified restore (13), which the fake scheduler does not model. The package doc says so. Tested with a valid one-slot target.
- M1: a negative amount is refused. Tested.
- M2: `fits` compares the amount with `limit - reserved`, so the sum cannot overflow.
- M3: a waiting lease whose blocking group changed goes back to requested, then waits on the new group's hold. The test asserts the lease moves from `quota_reset` to `broker_credit_exhausted` once tokens free up.
- L1: `New` refuses a hold registry without `quota_reset` and `broker_credit_exhausted`. Tested.
- L2: `Reserved` returns 0 for an unknown group. Tested.
- L3: the package doc says reservations return when a lease ends, whatever the release rule (the rules are M7).
- L4: the holds map is cloned.
- Mutation: 18 points. The id tie-break stays as it is: it is a policy choice, and determinism is what is tested.

## Review of #60, round 2 (Opus subagent, 2026-10-05)

Verdict: GO

Head reviewed: `bddacbb`. No High finding. Every round-1 finding is fixed, and the fixes add no defect that a caller can hit. Two Low items are test gaps: a mutant survives for each, but the code itself behaves correctly.

How I checked: I copied the tree without `.git` into `rv60b/` and left the worktree alone. `go vet` is clean. `go test -count=1 -cover` passes for `internal/capacity/...` and `internal/lease/...`; fakesched coverage is 93.4%. I added probe tests and ran 15 sed mutations on the copy.

### Round-1 findings: status

- **H1 (evidence target settles without a restore): fixed.** `Request` refuses any reservation on a `ResourceGroupKindEvidenceTarget` group (`fakesched.go:81-82`). So `apply`'s `evidenceTarget=false` (`:171`) is now true of every lease the scheduler holds. The package doc says this (`:7-9`). The test builds a *valid* one-slot target, which `New` accepts, and checks that `Request` refuses it (`fakesched_test.go:285-290`). Removing the check is caught by a mutant.
- **M1 (negative amount): fixed.** `fakesched.go:83-84`, tested at `fakesched_test.go:249`. A mutant that weakens the check is killed.
- **M2 (overflow): fixed.** `fits` compares `amount > limit - reserved` (`:102`). This cannot overflow. Request refuses a negative amount, so `reserved` only goes up by non-negative amounts that fit, and it stays in `[0, limit]`. `limit - reserved` therefore stays in `[0, limit]`. A negative limit (CheckGroup does not refuse one) is harmless too, because Request then refuses every amount ≥ 0 (`:87`). Mutants for "ignore reserved" and "off by one" are killed. I did not add an upper cap on `Amount` or `Limit`. None is needed, because no addition is left.
- **M3 (stale hold): fixed.** When a waiting lease is blocked by a different group, it goes `waiting → requested → waiting{new hold}` (`:152-162`). These are the only legal steps, because the table has no waiting → waiting step. A waiting lease that now fits goes `waiting → requested → granted` through the `fallthrough` (`:133-146`). The test asserts the move from `quota_reset/tokens` to `broker_credit_exhausted/broker` (`fakesched_test.go:215`). A probe showed the same-code case works too. Lease `b` (tokens 200 and slots 1) first waited on `quota_reset/rg_…tokens`. Once tokens were freed but slots were not, it waited on `quota_reset/rg_…slots` (signal instance updated). It was granted when slots freed. Mutants are killed for "always keep the old hold", "skip requested before re-wait" and "skip requested before granting from waiting".
- **L1: fixed for its cause.** `New` refuses a registry that lacks either hold (`:45-49`), and this is tested. The partial-Step-on-error shape remains: Step returns `nil` after earlier grants. No error path is reachable now, though. The holds are guaranteed, the hold always has a `SignalInstance`, and every transition Step uses is legal from the state it checked. See Info.
- **L2: fixed.** `Reserved` returns 0 for an unknown group (`:211-217`). This is tested, and a mutant returning 1 is killed.
- **L3: fixed.** The package doc states the release-rule simplification (`:7-8`).
- **L4: fixed in code, not tested.** See Low-2.

### Info

- The re-wait uses `lease.requested`, which note 05 labels "(signal fired)", even though no signal fired. The state machine has no other legal route, and the fake keeps no event log, so this is fine for M0. The M2 scheduler should decide whether "blocker changed" is its own signal or its own event.
- When several groups block a lease, the hold names the first blocking reservation in the lease's reservation order. This is deterministic. The real scheduler might prefer the blocker that frees last.
- `concurrency` (and `gpu`, `controller_*`) blockers map to `quota_reset`, whose signal is "time". This is approximate. The vocabulary has no slot-freed hold, and the reasons table ties capacity waits to `quota_reset`, so it is acceptable for the fake. Record it for M2.
- A zero amount and a lease with no reservations are both accepted and granted at once. This is consistent with the schema minimum of 0 and with "fits" semantics.
- Step's error returns still drop earlier grants (`:135`, `:140`, `:157`, `:161`). After the L1 fix they are unreachable, so they serve as defensive code. Returning `granted` with the error would be cheap insurance if Step ever gains a reachable error.
- The release loop in `Run` (`:194-200`) could decrement some groups and then return an error. Its guard is unreachable while the reserve and release invariants hold, so Run is still atomic in practice.
