### 1. The schema in the system message
- **What it carries:** `reviewerSystem(schema)` appends `JSON.stringify(schema)`, the run's `response_schema` or `defaultDecisionSchema` (`adapters/http-chat/src/adapter.ts:51`, `:199-202`). It is the controller's decision schema, and it holds no task, candidate, gate or I18-redacted data. So nothing the reviewer must not see can reach it, and the reviewer's inputs are otherwise unchanged (one turn, no tools, the same user prompt). Independence is not weakened.
- **Ordering:** the schema is now read and compiled before the first `push`, so the system message and the validator use the same object. A schema that fails to read, parse or compile still ends as `executor_incomplete` before any request.
- **Unchanged:** `response_format` is still sent (`:216`). The decision check is unchanged: `parseStrict`, `isWellFormed`, and Ajv against the same `schema` (`:274-278`).
- **Binding:** the system message is the adapter's, not the prompt's. `review.PromptDigest` is unchanged and correctly so. The change is bound by `AdapterDigest`, which covers `adapters/http-chat/src` plus `max_turns`/`max_output_tokens` (`internal/qualify/qualify.go:138`, `:227-233`). So a record made before this head no longer matches. That is the intended effect, and no record is committed under `fixtures/m1/review-qualification`. This also closes #306's M6 for the system message.

### 2. The 32000 budget
- **ONE value:** `qualify.MaxOutputTokens` is used by `route.go:168` and adcd's reviewer prepare (`internal/daemon/run.go:309`). `AdapterDigest` binds it, and `TestAReviewerDescribingHTTPChatsToolsIsPrepared`/`reviewrun_test.go:192` assert that the two are equal.
- **Rails:** no footprint or lease bound reads it. At the live example's reviewer price ($15/Mtok output), one call's output floor is $0.48. Its reservation (32000 × 20) covers it.
- **The floor can pass the reservation (M1).** The gateway's floor takes the request's `max_tokens` (`internal/gateway/count.go:69-80`) and never caps it at the lease's reservation. A reviewer lease is reserved at min(fit, `context_tokens × expected_turns`). So a reviewer whose registry footprint is small (the stub registry's 500 × 2 = 1000 tokens), or a lease whose fit is just one turn (32000 against 32000 output plus the input), owes a floor above what admission priced. The USD rail is overshot by at most one review call, which is bounded and visible on the next placement. This existed at 8000; it is now four times larger. Not blocking.

### 3. `finish_reason`
- **A builder that did finish is not read as incomplete.** The check runs only on the last turn, after `calls.length` was handled (`adapter.ts:268-269` returns or continues on any turn with calls). So:
  - a provider that sends `stop` only at the end passes;
  - a `tool_calls` turn followed by a text turn is judged on the text turn's `stop`;
  - `tool_calls` with no calls is accepted.
  
  [INFERENCE] A provider that names a clean end differently (`eos_token`, `end_turn`) would make every build `executor_incomplete`. That fails closed and is visible as `could_not_run`, so it is a registry/qualification matter, not a defect.
- **A truncated reply cannot pass as found.** A builder's `length`, `content_filter`, null or missing finish ends as `could_not_run/executor_incomplete` before `workspace.patch()`. The reviewer path does not read `finish_reason`, but a truncated decision fails `parseStrict`/Ajv and becomes `degenerate_output` (new TS row: "a reasoning reply that spends the whole budget thinking ... is degenerate_output").
- **Host or candidate?** It is the host's.
  - adcd reads the submitted `could_not_run` as not completed, so the build is `could_not_run` (with `partial_patch` when the workspace has a diff).
  - A build `could_not_run` is never `Repairable`, which covers reviews and accepts only.
  - The next launch supersedes it under the attempts rail.
  
  So no repair round is opened. A cut is still a paid **retry**: up to the round's attempts, then the attempts rail holds.
- **The builder's budget (M2).** `builderOutputTokens = 8000` (`internal/daemon/run.go:112`) is the builder's whole edit loop's output (`max_tokens = max_output_tokens − outTokens`, `adapter.ts:214`). It is untouched, while this PR's own finding is that a reasoning model spends 8000 thinking. Before this PR, a `length`-cut last turn reported its partial workspace as found/empty. Now it is held as incomplete, which is correct. But with a reasoning builder it will be the usual outcome: three paid attempts, then an attempts-rail hold that `task.raise_rail` cannot cure, since the budget is a code constant.

### 4. The charge link
- **A counted call keeps its link.** The gateway commits its floor durably before the send, and a floor it cannot record refuses the send. So any request that reached the provider has a measurement by the time `Review` reads `ledger.Measurements` (`internal/qualify/route.go:193-205`).
- **An uncounted call gains none.** The new row shows it: an adapter whose node fails to load gives `adapter_protocol_error` and no charge link.
- **L1:** the code checks for *any* measurement. `ledger.Measurements` also returns the host's `adapter_report` usage (`internal/adapterhost/submit.go:216`, `:317`), so the check is wider than its comment ("only when the gateway counted"). With http-chat this makes no difference, because usage is only reported after a gateway reply. Still, an adapter that reported usage without a request would gain a link. Filter on `gateway_floor`/`gateway_count`, or reword the comment.
