Verdict: NO-GO

**High H1 — Restarting without a registry after the gate completes leaves the task stuck without a hold.** `internal/reconcile/reconcile.go:616`; `internal/daemon/reviews.go:105`.

**Input:** Complete the gate, stop before `RecordReview`, then restart without `--registry`. This configuration is accepted. The loop repeatedly requests `RecordReview`, but `roster` returns `(nil, false, nil)` and `Record` returns no events. The executor treats this as `errNothing`, silently. No review exists for `HoldReview` to hold, and the completed build cannot acquire `placement: registry`. The task remains admitted, blocking subsequent admission, with no hold.

**Fix:** Represent the missing-reviewer wait on a holdable frontier even when no roster can be constructed. Clear and rederive that frontier when a registry returns. Add a row that removes the registry **after gate completion**, rather than before build placement.

**High H2 — Losing qualification between a completed `no_go` and its repair leaves another task stuck without a hold.** `internal/reconcile/reconcile.go:503`.

**Input:** With review qualified, complete and settle a `no_go` review; restart before the next pass records its repair, using a release whose qualification records are missing or stale.

`Inactive` explicitly excludes completed reviews. Meanwhile, line 511 collects repair verdicts only when review is active. The existing review prevents another `RecordReview`; `CandidateGo` rejects its `no_go`; all preceding nodes are completed. Consequently, nothing advances and nothing holds.

**Fix:** Permit controller-only repair recording under launch, then hold the successor review `review_inactive`, or create a durable, task-visible wait for the pending repair. Do not attempt to hold the completed review itself. Add the restart boundary to the derived-activation rows.

**Medium M1 — USD reservations do not bound an attempt’s subsequent requests.** `internal/daemon/run.go:322`; `internal/modelcall/modelcall.go:477`.

**Input:** A priced builder has `context_tokens=128000`, `expected_turns=2`, and rails leaving exactly 128,000 tokens’ worth of spend. Placement reserves 128,000 (`internal/dispatch/reserve.go:69`), but preparation still permits two turns and 128,000 output tokens. Two requests charging 66,000 tokens each exceed the reservation and USD rail.

The gateway records each request before sending, but `sends` checks only that the effect remains pending; it never compares accumulated usage or the next request against the reservation. The consequence is bounded by the attempt and conservatively recorded, so this is Medium. Nevertheless, the comment that “the gateway enforces” the reservation is incorrect.

**Fix:** Enforce a remaining allowance before each egress request, accounting for concurrent requests and input/output exposure. Derive adapter limits from that allowance. Add a multi-turn row with a reservation reduced by the USD rail.

**Medium M2 — A2/A7 accept an unsettled effect as proof of settlement.** `internal/daemon/activation_test.go:354`.

**Input:** The row’s existing `requestingBuilder` returns no `usage_final`. Its gateway counts alone do not settle the ledger, and production `newEgress` supplies no provider usage query. `Reconciler.Ended` can therefore leave the effect `uncertain`. The assertion passes because it rejects only `pending`.

**Fix:** Have the successful fixture report final usage covering the gateway count, then assert `EffectCompleted`, settled standing and the retained charge. Keep a separate missing-final row asserting uncertainty and preserved liability.
