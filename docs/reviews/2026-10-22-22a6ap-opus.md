### 1. Can a review take a gate result run on another tree, image, contract or baseline? No.
`receipt.Applies` compares the gate receipt with the requirement `gateNeed` derives (`internal/daemon/gateneed.go`):
- **The tree:** the subject's tree is accept's selected tree, the gate's producer's. A receipt over any other tree is refused (row).
- **The instrument:** `gate.Contract` over the project's gate *now*, in the measured image. A changed gate command changes the digest, which gives `instrument_changed` (row).
- **The environment:** `sha256:<image id>` from the measurement. The measured pinned reference must be the project's one pinned image (row: an image no longer pinned, another image id).
- **The demand:** derived from the recorded baseline digest (`demandOf`, shared with the receipt's `demand`). Another digest is refused (row).

### 2. Is the baseline digest the controller's fact? Yes.
- `gate.RecordMeasured` is emitted by adcd's gate run in the same command as `graph.Commit` (`internal/daemon/gate.go`). It is built from the `Baseline` that run's own `gate.Measure` returned.
- The fold admits a measurement only if:
  - it is under its gate node;
  - it is of a `gate_result` that node recorded;
  - it is the first for that result.
- No API action produces the event. The receipt's own demand key is never read to make the requirement.

### Medium

**M1 (OBLIGATION). A requirement that cannot be derived aborts the task's whole evaluation, with no hold.**
- `gateNeed` returns a plain error, not a `*receipt.Refusal`, when the gate's result has no measurement, or when the project no longer pins the measured image.
- `Resolve` returns it as is, `evaluation.visit` returns it (`internal/graph/evaluate.go:211-213`), and the whole `reconcile.evaluate` command is refused.
- **Probe:** `needs` returned the "no recorded measurement" error for the review's gate input. After 6 passes:
  - the review is `waiting` with no holds;
  - the review's **requirement node also stays `runnable`**, never claimed, although it does not depend on the gate's measurement;
  - the log has one line: `reconcile.evaluate refused: …`.

  The task is stuck, nothing on the board says why, and the only way out is to revoke its approval.
- Both triggers are stated as unreachable in M1: no gate result predates 6a′, and no action changes a profile. That is why this is not blocking.
- **Fix:** return a `*receipt.Refusal` (for example `receipt_incomplete` for a missing measurement, `instrument_changed` for an image no longer pinned). The review then gets the hold for that reason (missing → `await`), and the rest of the task still evaluates. Add a row: an unmeasured gate result holds the review, and the requirement still completes.

### Low (OBLIGATION)

**L1. The tree is taken from accept's *selected* result, not from what the gate's claim took** (`gateneed.go:67`). Today they are the same. If accept's selected result were ever replaced, for example by a renewal, the requirement would point at the new tree. A gate receipt over the old tree would then be refused, which fails closed, but the refusal names no cause.
- **Fix:** derive the tree from the gate's claim input (`graph.ClaimInputs(gate)`), which is exactly what the gate ran on.

**L2. Only the first gate of a task gets a review.** `reviews.Record` returns at once if the task holds any review or requirement node (`internal/daemon/reviews.go:86`). This predates 6a′, but it limits L1's walk-back: a later round's gate, after a no-go and a repair, never gets a review. That makes "several rounds" moot until 22a-6c.
- **Fix:** key "recorded already" by gate (a review whose `gate` input is this gate), or state it as 6c's.

**L3. The fold accepts a measurement in a later command** ("in this command or before", `internal/gate/measured.go:80`). A gate result committed without a measurement could have one attached later with any digest. Only controller code emits the kind, so this is defense in depth.
- **Fix:** require the result to be recorded in the same command, or state the rule.

**L4. The measurement does not record the baseline's base tree.** The requirement trusts the recorded digest, and never checks that the baseline was measured on the build attempt's base. `gate.Run` checks this at run time (`b.Base == in.Base`), so it holds today.
- **Fix:** record `baseline.base` in `gate.measured`, and have `gateNeed` compare it with the build attempt's base.
