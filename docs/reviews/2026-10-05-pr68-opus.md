# PR #68 (TypeScript adapter SDK): review

## Review of #68 (Opus subagent, 2026-10-05)

Verdict: GO

Scope: the last commit on `wt-sdk` (`30e833e`, `git diff HEAD~1`), read against 09, AUTHORING.md, `schemas/adapter/*.json`, `internal/contract/contract.go` and `gen/ts`. All probes and mutations ran in a copy (`scratchpad/rv68`, no VCS directory, fresh `pnpm install --frozen-lockfile`). The worktree was not touched.

Baseline: `node --test "test/*.test.mjs" "test/*.test.ts"` passes 9/9, `tsc -p tsconfig.json` is clean, and Node v22.23.2 strips types without a warning. A throwaway workspace package that imports `@adc/contract` loads `index.ts` through the pnpm symlink and runs.

### Probes done

- **parseStrict compared with the Go reader.** I ran 106,926 distinct inputs through both: hand-picked seeds plus random mutations over braces, quotes, escapes, `\u` surrogates, digits, signs, `.`/`e`, whitespace, NBSP, BOM, control characters and multi-byte characters, with depths up to 200. The Go side was a test-only copy of `validate()`'s byte path: `utf8.Valid`, then `checkEscapes`, `readValue` and the trailing-token check. The TS side was a fatal `TextDecoder` (as `lines` uses), then `parseStrict`.
  - There were 553 disagreements. Every one was TS refusing something Go accepts, and every one was either an integer outside ±(2^53−1) (478) or nesting deeper than 128 (75).
  - Neither direction showed any other disagreement: not on surrogates, escapes, whitespace, duplicate keys (including keys that only match once escapes are decoded, such as `"a"` and `"a"`), literals, BOM or trailing data.
  - Every contract integer is capped at 9007199254740991 in the schemas, and no adapter schema nests anywhere near 128. So the two places where TS is stricter cannot refuse a valid core message, apart from the JSON-RPC `id` (Low 4).
- **Framing.** These all behave correctly:
  - a frame fed one byte at a time, including `é`, `😀` and CRLF (the `\r` stays in the line, and parseStrict skips it as whitespace, as Go does);
  - a line of exactly `max` bytes is accepted, and `max+1` split across chunks is refused;
  - overlong UTF-8, UTF-8-encoded surrogates and invalid bytes are refused;
  - a BOM is kept and then refused by the parser, as Go refuses it;
  - pending data stays at most `max` bytes.
- **Speed.** A 16 MiB string parses in about 1.9 s, 5M array elements in 0.6 s and 800k keys in 2 s. That is acceptable for core → adapter messages, which are small (handles).

### High

None.

### Medium

**M1. Off-contract strings still reach the wire: a lone UTF-16 surrogate in any adapter string** (`adapter.ts:66-69`, `framing.ts:50-53`)
- **Mechanism.** `check()` uses the ajv validators, which do not test whether a string is well-formed. `JSON.stringify` then writes a lone surrogate as `\ud83d`, and the Go reader refuses that (`checkEscapes`).
- **Reproduced:**
  - a run result with `detail: "trunc \ud83d"` passes `check("adapter/run-result")` and is sent as `"detail":"trunc \\ud83d"`;
  - `contract.Validate("adapter/run-result", …)` on those bytes returns `unpaired surrogate escape \ud83d`.
- **Failure scenario.** Either of these is a realistic trigger:
  - an adapter truncates a harness message to the 4096 limit with `.slice(0, 4096)` and cuts through an emoji;
  - an adapter copies a string out of harness JSON that it parsed with the lenient `JSON.parse`, which accepts `"\ud83d"`.

  Either way the core refuses the whole run result or event, and the attempt's work is lost as a protocol fault. The PR's claim that "an adapter cannot emit an off-contract message" does not hold for this class.
- **Fix.** Refuse strings that are not well-formed, either in `check` (walk the document and test `String.prototype.isWellFormed()`, which Node 22 has) or in `frame`. Add a test for each direction.

**M2. serve never closes the adapter's generator or stops in-flight runs on an abnormal path** (`adapter.ts:97-109`, `adapter.ts:111`, `adapter.ts:147-148`)
- **Event validation.** When an event fails `check` (line 104) or `send` throws, the loop throws without calling `it.return()`. The adapter's `finally` blocks therefore never run.
  - Reproduced: a generator `try { yield badEvent } finally { cleaned = true }` leaves `cleaned === false`.
  - Failure scenario: the fake or a real adapter runs `try { spawn harness; … yield … } finally { child.kill() }`. One off-contract event leaves the harness child process running until the adapter process dies, and it keeps using the model and the workspace after the core has been told the call failed.
  - Fix: `try { … } finally { clearInterval(beat); await it.return?.(undefined) }`, guarded so that a throwing `return` cannot mask the error. A `for await` over the generator would do the same, but it cannot capture the return value.
- **Framing errors.** When `lines` throws (truncated input, an oversize line, invalid UTF-8), `serve` rejects immediately while the runs in `running` keep going.
  - Reproduced: after `serve` rejected with "the input ended inside a message", a slow run kept writing heartbeats and then its result to `write` (11 lines after the rejection).
  - Under `run(adapter)` the unhandled rejection kills the process, which is acceptable as fatal. But anyone driving `serve` in process (the conformance kit, tests) gets timers and output after `serve` has settled.
  - Fix: on a framing error, either wait for the runs before rejecting or tell them to stop (see L1), and document which one it is.

**M3. There is no path for `tool.response`, so a controller-mediated tool round-trip cannot be written on this SDK** (`adapter.ts:126-169`; 09 "Notifications" `tool.request`; `schemas/adapter/event.json` ToolRequestEvent)
- **Gap.** 09 and event.json say that the core "answers with a `tool.response` request to the adapter". `serve` answers any `tool.response` with MethodNotFound, and `Adapter.run` has no way to receive one.
- **Context.** #67 adds no `tool.response` schema, so the SDK is consistent with today's schemas, and this does not block.
- **Failure scenario.** The conformance case "controller-mediated tool round-trip", and AUTHORING §5 ("run test requests as controller-mediated `tool.request`s"), cannot be met by the fake or by any adapter until both the schema and the SDK gain the method.
- **Action.** Record this as an explicit follow-up for #67 and #68 before the fake adapter starts.

### Low

**L1. Cancel cannot reach the run** (`adapter.ts:41-45`)
- `run(p)` gets no `AbortSignal`, and the default `cancel` does nothing.
- An adapter has to build its own shared state between `cancel` and `run` to honour a cancel. Combined with shutdown waiting for runs while it no longer reads input (lines 160-161), a hung harness makes `shutdown` hang, and a cancel sent after it is never read.
- This is allowed by A4, but the conformance case "cancel during a tool call" will make every adapter reinvent the plumbing. Pass a signal that `cancel`, shutdown and EOF abort.

**L2. Tests do not cover several claims: 11 of 18 targeted mutations survive**
- **Killed:** depth 199; a low surrogate allowed before `x`; lenient UTF-8; surrogate-pair order swapped; the InvalidRequest id echo. The depth mutation also dies at 1000, but survives anywhere in 129–199, so the boundary itself is untested: a 129-deep input should be refused.
- **Survived, each a claim with no test behind it:**
  - "the envelope wins over anything the adapter set": `{...envelope, ...step.value}` survives (line 103);
  - "a failed prepare prepares nothing" when an earlier prepare succeeded: keeping the old preparation survives (line 140). This is the fencing invariant that matters;
  - the `attempt` comparison in `fenced`: removing it survives, because every test uses one attempt;
  - an adapter exception mapped to InternalError: changing the code survives, because no test makes the adapter throw;
  - validation of prepare, cancel and shutdown outcomes: removing each of the three checks survives;
  - the 10 s heartbeat cap: removing it survives;
  - a high surrogate followed by a non-low `\u` escape (`"\ud800A"`): removing the check survives;
  - a non-object message (`5`, `[]`, `null`) answered as an InvalidRequest: removing that branch survives;
  - NBSP treated as whitespace: survives;
  - the framing bound `>` mutated to `>=`: survives, because the exact-`max` case is untested.

  Add a test per claim. The PR's "30 points, all killed" did not cover these.

**L3. Heartbeat timing edges** (`adapter.ts:73`)
- `Math.min(x, 10000)` allows exactly 10 s. Timer drift, or a blocked event loop (a 16 MiB parse takes about 2 s), then breaks "every ≤10 s". Cap at, for example, 9000.
- 0, a negative value or `NaN` floods heartbeats every 1 ms. Clamp to a sane range.

**L4. The JSON-RPC `id` must be a safe integer**
- The core reader accepts any integer spelling, but `parseStrict` refuses ids beyond ±(2^53−1) as a ParseError with `id: null`, and the session cannot match the reply.
- Record this as an obligation on `internal/adapterhost`, which does not exist yet: request ids stay small integers or strings.

**L5. One process per attempt is not enforced** (`adapter.ts:134-143`, `144-150`)
- A second successful `prepare` with another attempt replaces `prepared`, and a failed re-prepare during a run sets it to `null`, so the cancel for the running call is refused.
- Two concurrent `run`s, even with the same id, are both accepted.
- 09 says "one adapter process per attempt". Refusing a second prepare or run, or documenting the behaviour, would make faults visible.

**L6. Possible unhandled rejection** (`adapter.ts:81`, `148`)
- If `send` throws inside `respond`'s catch, the run task rejects, and `void task.finally(...)` yields an unhandled rejection. This happens with a user `write` that throws, or when the adapter throws an object that `String()` cannot convert, such as one with a null prototype.
- Handle it with `task.catch(...)` or a try/catch around the error send.

**L7. Adapter exception messages go to the core verbatim** (`adapter.ts:81`)
- `adapter error: ${message}` can carry a gateway URL or token from a fetch error, and nothing redacts it the way stderr is redacted.
- Consider a bounded, redacted message.

**L8. Small issues**
- `parseStrict` accepts 129 levels of empty arrays but not 128 arrays around a scalar; the depth counts the value, not the container (`strict-json.ts:85`).
- A number of 25 or more digits is reported as "not an integer spelling" instead of "outside ±(2^53−1)" (`strict-json.ts:72-76`).
- An over-long or non-UTF-8 line ends the session with no JSON-RPC error reply. The conformance case "oversize message" should expect the process to exit.
- AUTHORING.md:40 says the SDK handles "blob exchange"; it does not.
- The exported `run(adapter)` shares its name with `Adapter.run`.
- `exports` points at `.ts`. This works through workspace symlinks, but an installed (non-symlinked) copy under `node_modules` would hit Node's refusal to strip types there. That is acceptable while the package is private.
- `package.json` has no `engines` field (it needs Node ≥22.18 for type stripping by default).

### What the fake adapter and the conformance kit will trip on

- They need `tool.response` (M3) and a cancellation signal (L1).
- They need a way to emit raw, off-contract lines for the kit's red-proof and the unsafe-output modes, because `serve` validates everything. They will need to use `frame` and `write` directly.
- An oversize or truncated input kills `serve` without a reply (M2, L8).
- A generator whose output fails validation leaks the harness (M2).
- Truncated `detail` strings can trip the Go reader through M1.

### Lead notes (applied before merge)

- **M1 (lone surrogates):** every document the adapter sends is checked for well-formed UTF-16 (keys included) after the schema check, so a string cut in the middle of a pair is an internal error and never goes out. Tested with a cut emoji in `detail`.
- **M2 (cleanup):**
  - `run` receives an `AbortSignal`. It is aborted on cancel, on shutdown, on a broken input and when the run fails.
  - When the run ends early, serve calls the generator's `return()`, so the adapter's `finally` (stopping its harness) runs.
  - A framing error stops the active run before `serve` rejects.
  - Tested: an invalid event closes the generator, cancel aborts the signal, and an oversize input aborts and cleans up the run.
- **M3 (`tool.response`):** this needs its own schema first (the core → adapter answer to `tool.request`). It is recorded as a follow-up contract PR before the fake adapter, together with the kit's raw-line writer for red-proofs.
- **Lows applied:**
  - **One process per attempt:** one run at a time (a second run is refused), and prepare only between runs.
  - **A failed re-prepare** clears the fence.
  - **`heartbeatPeriod`:** 5 s when unset, zero or NaN, and capped at 9 s so a beat lands within 09's 10 s.
  - **Depth:** at most 128 levels, exactly; 128 parses and 129 is refused.
  - **Error reply:** a failure to send one is logged to stderr instead of becoming an unhandled rejection.
  - **AUTHORING.md** no longer claims blob exchange, and documents the signal.
- **Tests:** the surviving mutations now have tests, covering:
  - the envelope overriding adapter fields;
  - the attempt in the fence;
  - a failed re-prepare;
  - the exception error code;
  - the prepare, cancel and shutdown outcome checks;
  - the heartbeat bounds.
- **Noted, not changed:**
  - **Integers and depth** outside the Go reader's limits: no valid core message has them (L4). `internal/adapterhost` must keep JSON-RPC ids small.
  - **Adapter exception text** goes to the core as the adapter wrote it. The core logs with type-based redaction.
- **Mutation:** 33 points, all killed.

### Lead notes: M3 (`tool.response`) resolved after #67

#67 now carries `adapter/tool-response-params` (Astra round 2 GO with changes). This PR is rebuilt on it and adds the
SDK side:
- `run` receives a third argument, `tools: RunTools`. After yielding a `tool.request`, the adapter awaits
  `tools.response(handle)`, which rejects when the run is aborted.
- `serve` handles the `tool.response` request. It validates against the schema, checks the fence and the active call,
  and requires an open request of this run with the same turn and tool, answered at most once. The reply is `{}`.
- A mediated `tool.result` must report exactly a handle the core delivered for that turn and tool (all four handle
  fields compared). An adapter that reuses a request handle is refused.
- Tests drive `serve` interactively: the round-trip for a failed tool, nine refusals, four forged-result cases, and
  release by cancel.
- Mutation: 14 points, all killed. The three first survivors (turn and tool ignored in the report, handles compared
  by name, request-handle reuse) now have tests.
- `AUTHORING.md` documents the round-trip.

## Review of the tool.response support (Opus, 2026-10-05)

Verdict: GO with changes. No Critical or High findings. The reviewer checked the response-before-request ordering
(not a real hazard: a request is recorded before it is sent), abort listeners, per-run state and error codes, and found
them sound.

- **M1:** the request handle was matched by name only, and the delivered handle's attempt was never checked.
- **M2:** one delivery could be reported by any number of mediated results.
- **M3:** three paths were untested: an answer before the wait, a wait after an abort, and a double wait.
- **L1:** `sameHandle`'s attempt and size comparisons were untested.
- **L2:** the tool check in `reported()` was untested.
- **L3:** the record-before-send ordering was not pinned.
- **L4:** a wait the run abandons never settled.
- **L5:** `AUTHORING.md` understated the refusals.

### Lead notes (applied)

- **M1:**
  - A response must name the whole recorded request handle.
  - Its `delivered` and `request` handles must belong to the response's attempt; otherwise InvalidParams.
  - A `tool.request` whose handle names another attempt fails the run.
- **M2:** each delivery is used up by the one mediated `tool.result` that reports it. A second report fails the run.
  Tested with a run that reports its delivery twice.
- **M3:** tests cover an answer the run waits 50 ms for, a wait begun after cancel (rejects), and a concurrent second
  wait (rejects).
- **L1, L2:** the forged-result table adds another size, another attempt, another tool and a request of another
  attempt.
- **L3:** a comment marks the ordering as load-bearing, since `send` is synchronous.
- **L4:** when the run ends, every wait still pending is rejected ("the run ended"). Tested with a run that abandons
  its wait.
- **L5:** `AUTHORING.md` lists every refusal: the core's errors, the run failures and the four rejections.
- **Mutation:** 24 points, all killed, the reviewer's surviving mutants included.
