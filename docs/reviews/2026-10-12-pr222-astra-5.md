**1. High — stopping the local pusher does not establish remote non-delivery.** [00-slice-plan.md:288][lifetime], [00-slice-plan.md:561][p27].

GitHub can receive the complete B→C request, then pause before updating the ref. ADC and its pusher die; restarted ADC observes B and declares `failed_confirmed`, releasing the fence. GitHub can subsequently apply C because its expected-old-SHA check still succeeds. That permits an old operation to land after invalidation, cancellation or replacement.

`PR_SET_PDEATHSIG` and a process group cannot cancel remote processing. Git’s receive implementation executes ref updates before reporting their results; losing the client is not a negative acknowledgement. This counterexample follows from that ordering. [Git receive-pack implementation](https://github.com/git/git/blob/master/builtin/receive-pack.c).

**Required:** retain `uncertain` and the fence after a possibly sent request unless there is definitive settlement evidence. An unchanged ref and absent candidate are insufficient. Add a fixture delaying server application until after restart and observation.

**2. Medium — scratch fixtures still permit nondiscriminating outcomes, and rewind settlement contradicts P27.** [00-slice-plan.md:263][fixtures].

- `crash-after-push-github` proves landing, but ADC may record completion before the driver kills it. Add a barrier before durable outcome recording and assert the outcome is still unrecorded.
- In `crash-unknown-github`, the candidate may land before the driver advances the branch. An unrelated commit built on that tip retains the candidate in first-parent history, so P27 correctly returns completed rather than the required uncertain outcome. Pin the injected history and synchronization.
- The rewind fixture requires `Landed=false` with the ref at ancestor A, while P27 allows false **only** when the ref equals generation base B. Distinguish a definitively rejected, never-sent update from history-based reconciliation.

The **definitely-not-sent** case is sound as specified at [00-slice-plan.md:279][notsent]: P27 explicitly refuses **before egress** and records `before_send`. Qualification must demonstrate that local refusal; removing a credential file or observing a generic authentication error alone is not its proof.

**3. Medium — early installed acceptance still depends on later activation.** [00-slice-plan.md:100][activation], [00-slice-plan.md:528][early], [01-invariant-inventory.md:219][i15].

P1/P3 advertise successful installed creation smokes. However, intake activates through P3, requires I1 admission/fold—including P5/P6’s answer checks—and requires I15, whose remaining admission guard belongs to P22a. Those smokes cannot succeed at their advertised delivery points under the authoritative table. Pull the necessary guards forward, scope the required rows more precisely, or explicitly defer the integration smokes. Do not bypass the guards.

The **H1 CAS mechanism itself is correct**: the explicit lease checks the advertised SHA against B; the push carries B as its old object ID; receive-pack checks that old value transactionally. This closes both the pre-advertisement rewind and the subsequent update race for GitHub’s Git push path. It does not prove cancellation of an in-flight request. [Git push documentation](https://git-scm.com/docs/git-push), [Git HTTP protocol](https://git-scm.com/docs/gitprotocol-http), [receive-pack transaction](https://github.com/git/git/blob/master/builtin/receive-pack.c).
