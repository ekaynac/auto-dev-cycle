### Astra's four Mediums

1. **Final chunk under an expired deadline: closed.** `flushing.Write` clears each write's deadline after it (`serve.go:161`). The deferred `arm` (`gateway.go:228`) runs after `g.count`, because defers run in reverse order: release, then arm, then cancel. A response with an empty body is closed too: its header is written only when the handler ends, under that fresh deadline. My probe had a 900 ms first byte, `writeIdle` 300 ms and an empty 500: it came back whole.
2. **Capture, intent and floor racing `Unbind`: closed.** `admit` checks the request is still in flight under `g.mu` and adds to the token's wait group there. `Unbind` removes the token's in-flight entries under the same lock before it waits, so nothing can be added during the wait. Every successful `admit` calls `done()` on each return path. The checks that read the binding (`observe`, `intend`'s cache) still look at `g.bound`.
3. **A deadline before every write: closed as asked, but the fix adds a regression (M1).**
4. **A refusal that never drains the body: closed.** `Connection: close` makes Go skip the drain, and the read deadline set to now stops the body being read when the request ends. The nearest variant passes: the real `chat()` client sent an unbound token with 100 KiB, 1 MiB and 4 MiB bodies over the socket, three runs each, and got 401 `unbound` every time, never EPIPE.

### Question 2: undercount, deadlock, regression

- **Undercount (#226 entry 69):** none found.
  - Every send still follows its durable floor. An `admit` or floor refusal sends nothing.
  - The usage count commits after `release` and is not waited for by `Unbind`. That over-records at worst, and is documented.
  - A panic in `flushing.Write` mid-copy (a connection closed locally, as at `Server.Close`) skips the count, so the floor stands.
- **Deadlock:** none inside the gateway. `Unbind` cancels the token's requests and releases `g.mu` before it waits. The side effects it waits for take only `g.mu`, which is free at that point. There is a contract hazard for 22a-5 (L2) and a hang after a panic (L1).
- **Regression against main:** yes, M1.

### Medium

**M1. A refusal written after a forward slower than `writeIdle` is lost: the adapter gets EOF instead of the refusal.** `internal/gateway/gateway.go:227` and `internal/gateway/gateway.go:569-576`
- **Cause:** `arm(rc)` sets one 30 s deadline at the top of `ServeHTTP`. `refuse` writes and flushes under it with no fresh `arm`. A refusal decided more than 30 s after the request arrived is therefore written to a connection whose deadline has passed.
- **When it happens:**
  - `upstream_unreachable` (`:512`): the dial timeout alone is 30 s, and the 10 min `RequestDeadline` also ends here;
  - `encoding` (`:516`) or `redirect` (`:510`) after an upstream slow to answer;
  - `intent_unrecorded`, `count_unrecorded`, `capture_failed` or `lease_unreadable` after a store call slower than 30 s.
- **Input (probe):** `writeIdle` 300 ms, and an upstream that waits 900 ms then answers `Content-Encoding: br`. The client got `Post …: EOF`, with no status and no refusal header.
- **Why it is a regression:** main has no write deadline, and at 67e8f3d `refuse` wrote without one, so both deliver this refusal.
- **Effect:** the adapter's `chat` rejects, and `adapter.ts:217` ends the run as `executor_incomplete`. The intended outcomes were `provider_unavailable`/`http_5xx` for `upstream_unreachable` and `failed/routing_violation` for `redirect`. Accounting is not affected: the floor stands.
- **Nearest variant:** the same deadline armed at the start also covers Go's `100 Continue` write. That write happens when `forward` first reads the body, after the lease and attempt reads; if those took over 30 s, the response is broken.
- **Fix:**
  - Call `arm(rc)` at the top of `refuse`, before `WriteHeader`.
  - At the top of `ServeHTTP`, keep the check that a deadline can be set, then clear it with `rc.SetWriteDeadline(time.Time{})`.
  - Add a row like the probe: an upstream slower than the lowered `writeIdle` answering with `Content-Encoding`, and the client receives 502 `encoding` whole.
  - Add the mutation "no `arm` in `refuse`".

### Low

**L1. A panic inside an admitted side effect makes `Unbind` hang for good.** `internal/gateway/gateway.go:458-486` and `internal/gateway/serve.go:110-124`
- **Cause:** `done()` is called inline, so a panic in `Capture.Keep`, `Intents.Intend` or the floor's `Counts.Count` skips it. net/http recovers the panic and the deferred `leave` runs. But if another request of the same token is still in flight, `g.ops[key]` keeps its count, and `Unbind`'s `ops.Wait()` (`gateway.go:186`) never returns.
- **Input (probe):** one request held upstream, then a second request whose `Capture.Keep` panics. `Unbind` had not returned after 2 s.
- **Effect:** for 22a-5, the attempt end would block forever.
- **Fix:** run each side effect in a closure with `defer done()`, and add a row with a panicking `Keep` plus a second request in flight.

**L2. `Unbind`'s blocking is not in its contract.** `internal/gateway/gateway.go:164-166`
- **Cause:** `Unbind` now waits for the admitted capture, intent and floor. The floor's commit runs under `context.WithoutCancel` (`:485`) and has no bound.
- **Hazard:** if 22a-5 calls `Unbind` while holding a lock that the Recorder or Capture takes (a store transaction, or the attempt-end path's own mutex), or from inside one of those implementations, it deadlocks.
- **Fix:** state in `Unbind`'s doc that:
  - it blocks until the admitted side effects end, and the floor's commit is not cancelled;
  - it is never to be called from `Capture`, `Intents` or `Counts` implementations, or while holding a lock they take.
