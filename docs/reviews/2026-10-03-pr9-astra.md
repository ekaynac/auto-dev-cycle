# PR #9 review (Astra, 2026-10-03)

Verdict: NO-GO

The validator choices are plausible, and schema-first generation preserves “one source per contract.” Two High findings block accepting the contract as written: the Go generator’s supported shapes cannot represent even the spike’s approval schema, and the receipt schema changes the documented wire shape.

I read all requested files. An independent local Python Draft 2020-12 validator matched **16/16** expectations. I did not reproduce the pinned Go/TS runs or candidate-generator results.

**High**

1. **The supported-shape contract excludes shapes already required by M0.**  
   **Files:** `docs/research/2026-10-03-codegen-spike/README.md:47–58`; `docs/design/m0/01-repo-layout-and-toolchain.md:68–70`.

   **Problem:** The list supports closed objects, but `schemas/records/approval.json:47` contains an open, action-dependent `scope`. M0 additionally needs typed maps (`04-authority.md:40`, `07-project-profile.md:42`), array-or-literal unions (`04-authority.md:35–37`), booleans and numbers. Their representations are absent from the supposedly exhaustive list.

   **Failure scenario:** A conforming generator must reject the included approval schema. Mapping `scope` to an empty struct instead makes strict decoding reject schema-valid, nonempty scopes; silently using an untyped fallback violates the stated rule.

   **Fix:** Specify the supported schema grammar and representations, including primitives, typed maps, action-dependent payloads and the required array-or-literal unions. Preserve action schemas as the source: use generated dispatch or explicitly retained JSON validated against the selected action schema. Add representative nonempty fixtures. An in-repo generator remains a reasonable choice, but this support boundary is incomplete.

2. **The receipt spike relocates the demand binding.**  
   **File:** `docs/research/2026-10-03-codegen-spike/schemas/records/receipt.json:23`.

   **Problem:** Note `06-receipts.md:33–40` places `demand` inside `subject`. The spike places it at the receipt root and closes every subject variant against additional properties.

   **Failure scenario:** A receipt carrying the documented `subject.demand` is rejected. The fixture at `cases.json:12` instead blesses the changed location. I confirmed the rejection locally. This is a contract change beyond choosing generation tools.

   **Fix:** Match the documented location and test a concrete, non-null demand. Also explicitly inventory the receipt subset: it omits `object_revision`, `environment`, the required `conclusions_digest` described at note 06:84, and accommodation for instrument-specific predicate payloads. Subsetting is reasonable for a spike; silently presenting the subset as the full receipt contract is not.

**Medium**

3. **The decisive generator comparison is reported but not auditable from the PR.**  
   **File:** `docs/research/2026-10-03-codegen-spike/README.md:33–35`.

   **Problem:** There are no candidate invocation commands, generated excerpts or assertions demonstrating the rejected Go generators’ failures. `atombender/go-jsonschema` has no pinned version. The TS harness writes types but never compiles or checks their claimed properties. Two rejected candidates also do not establish “No maintained Go generator” at line 47.

   **Failure scenario:** Reviewers cannot distinguish generator limitations from invocation/configuration problems, or detect weakened TS output while the harness still reports 16/16.

   **Fix:** Record exact versions/options and minimal generated evidence for each rejection. Add small TS compilation assertions for narrowing, required envelope fields and literal discriminators. Restrict the conclusion to the candidates tested. Document or lock transitive dependencies if claiming reproducibility with pinned versions. The complete in-repo generator can remain in step 2b.

4. **The cases provide useful validation coverage, but substantially less than the prose suggests.**  
   **File:** `docs/research/2026-10-03-codegen-spike/cases.json:2–17`.

   **Problem:** Extra-property rejection, discriminator rejection, required envelope fields, outcome enums and digest patterns have meaningful checks. However, there are no positive tree/proposal subjects, turn-start/upstream events, non-null demand objects or populated predicates. There are no negative `minimum`/`uniqueItems` checks.

   **Failure scenario:** Locally, all **16/16 still pass** after removing `minimum` and `uniqueItems`, or replacing receipt `demand` with null-only support. Those regressions are invisible.

   The “approval expected both” case is legitimate, but both branches reject it through `additionalProperties: false`; it does not exercise rejection because *two* branches match. Replacing every `oneOf` with `anyOf` also preserves 16/16. That equivalence is expected for these disjoint alternatives, so it should be described accurately.

   **Fix:** Cover every selected variant, nullable values on both branches, invalid nullable values, neither expected-state key, numeric boundaries and duplicate array entries. Scope “16/16” to validation of these instances, not generated-type fidelity or comprehensive keyword coverage.

5. **“Validate then strict decode” is sound ordering, but an incomplete decoding contract.**  
   **File:** `docs/research/2026-10-03-codegen-spike/README.md:52–61`.

   **Problem:** Schema acceptance does not guarantee lossless representability in the chosen Go types. Integer schemas permit mathematically integral JSON numbers such as `3.0`; ordinary Go integer decoding rejects that spelling. Unbounded integers also exceed Go ranges or JavaScript’s exact-number range. Optional nullable fields mapped to one pointer collapse absent and explicit null. Outer `DisallowUnknownFields` does not automatically govern custom unmarshallers.

   **Failure scenario:** Schema-valid input fails typed decoding, numeric identities change across languages, or round-tripping changes field presence. A custom union decoder can also have different strictness from its parent.

   **Fix:** Define numeric representation/ranges and lexical normalization, absence/null semantics, whole-document consumption and custom-decoder behavior. Require validation and decoding to operate on the same input, with representative round-trip checks in step 2b. Separately require validation before emitting constructed values: sealed interfaces, enum aliases and keyed pointer structs still allow invalid values to compile.

6. **CommonJS standalone output has an unproven installed-package boundary.**  
   **File:** `docs/research/2026-10-03-codegen-spike/ts/spike.mjs:23–25`.

   **Problem:** Loading the generated `.cjs` beside installed Ajv proves that development arrangement. Given the reported helper `require()`, it does not prove that the published `@adc/contract` works when Ajv is absent or only a development dependency.

   **Failure scenario:** Generation and local validation pass, but a production consumer fails to resolve an Ajv runtime helper.

   **Fix:** Explicitly retain the required runtime dependency or bundle the helper, define package exports/declarations, and smoke-test the installed package from the intended consumer. CommonJS is a reasonable Node choice. `strict: true` is useful schema lint, but does not establish type fidelity, semantic contract completeness or deployment independence.

**Low**

7. **Shared scalar descriptions promise stronger validation than their patterns provide.**  
   **File:** `docs/research/2026-10-03-codegen-spike/schemas/common/defs.json:11–32`.

   **Problem:** `Time` admits impossible calendar dates; `TypeID` does not enforce UUIDv7 or entity-specific prefixes and rejects the two-letter `rg_` prefix used by note 05. `ReasonCode` checks spelling, not registration. Fixtures use `cal_` for receipts, approvals, actors and attempts.

   **Failure scenario:** These schemas become production seeds while callers assume their descriptions are enforced guarantees.

   **Fix:** Label these as deliberate spike simplifications, use realistic fixture prefixes, and record the required production checks. Neither Ajv strict compilation nor agreement between validators detects a contract that both schemas underspecify.
