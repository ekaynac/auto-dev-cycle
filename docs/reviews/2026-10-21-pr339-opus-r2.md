**M1′. A service panic with empty text, recovered by decision A, still gets a duplicate block from the latch.**
- **Where:**
  - `internal/accept/integrity_proc.go:435-436`: when `s.panicked == ""`, the latch falls back to exact equality with `"unverifiable: the guard failed ()"`;
  - `internal/accept/integrity_proc.go:447`: `serve` sets `panicked` to `fmt.Sprint(p)`, which is `""` for `panic("")` or `panic(errors.New(""))`.
- **Input (probed):** round 1's input (`guardBase` plus `go.work` or `go 1.13`, and `vendor/modules.txt`; `pkg/calc.go` gains `fmt.Println` and `os.Getpid`), with a Reader that runs `panic("")` on the `vendor/modules.txt` blob.
- **Result:**
  - Main gives 4 blocks; the last is `unverifiable: decision A's outside-initialization check failed ()`.
  - The child gives 5 blocks: the same 4, plus `unverifiable: the guard failed ()` from the latch.
  - The report and the detail differ. Both refuse the change.
- **Why it matters:** an empty panic is a case the package already treats as in scope. `TestIntegrityTypesFailClosed` has an L2 row (Opus #287) for "a panic whatever its text".
- **Fix:**
  - Keep a `bool` for "a panic was latched", separate from its text.
  - Always use the suffix rule: `strings.HasPrefix(b.What, "unverifiable: ") && strings.HasSuffix(b.What, "("+s.panicked+")")`. Drop the equality branch.
  - Every `s.failed` comes from `serve`'s recover, request refusals included, because they are panics too. So the equality branch only ever ran for empty panics.
  - Add `""` as a second panic text in the enumeration row, or at least on the `vendor/modules.txt` blob.
