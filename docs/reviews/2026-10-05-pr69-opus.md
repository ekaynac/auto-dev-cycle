# PR #69 (generated schema reference): review

## Review of #69 (Opus subagent, 2026-10-05)

Verdict: NO-GO

Scope: commit 303d1e7 on 030c00a. I read `internal/schemadoc/schemadoc.go`, `tools/schemadoc/main.go`, the Makefile wiring, the test, all 26 schemas and the "M0 exit check" in `docs/design/m0/00-overview.md`. I ran probes in a copy without .git (`scratchpad/rv69`).

What holds:
- **Determinism.** Two fresh runs are byte-identical to each other and to the committed pages. The output keeps the YAML node order, and `schemas.Paths()` is sorted.
- **gen-check.** `make gen-check` passes on a clean tree. It fails, with "generated code is stale", in each of these cases: a hand-edited page (docs-only change), a stray extra page, a deleted page, and a schema change. `make ci` runs it, and CI runs `make ci`.
- **Links.** There are 281 links. All of them resolve. All `$ref`s have the form `file#/$defs/Name` or point at a whole file. Every definition name is `[A-Za-z0-9_]+`, and no heading collides with another on the same page, so the lowercased anchors match GitHub slugs today.

The problems are in faithfulness. The exit check is "Schemas documented". As generated, the reference states types that are wider than the schema, and it hides required fields and constraints without saying anything is left out.

### High

**H1. A `$ref` with sibling keywords drops those siblings. Every entity ID is rendered with the wrong, wider type.**
- Location: `internal/schemadoc/schemadoc.go:119`. `typeOf` returns the ref link as soon as it sees a `$ref`.
- Schema: `common/defs.json:44` onward says `"ProjectID": {"$ref": "#/$defs/TypeID", "pattern": "^prj_"}`. The same holds for TaskID, UnitID, AttemptID, LeaseID, ActorID and others, 26 cases in all. Under draft 2020-12, sibling keywords of `$ref` apply.
- Page: `docs/reference/schemas/common-defs.md:53-55` says only `Type: [TypeID](#typeid)`.
- Effect: every field typed ProjectID, AttemptID and so on, across all pages, tells the reader that any TypeID is accepted (for example `att_…` where `prj_…` is required). That misleads the reader about a constraint on the most-used types in the contract.
- Fix: render the siblings after the link, for example `[TypeID](#typeid) (pattern `^prj_`)`.

**H2. Nested inline objects become a bare "object" (43 cells on 16 pages). Their fields, required marks, closedness, maps and conditional rules all disappear, with no note.**
- Location: `schemadoc.go:143-147`. `section` only renders a node's own `properties` (`:80`) and never recurses into a property.
- Example 1: `config-project-profile.md:16-34`. 13 of the 20 required top-level fields of the profile, which is the schema users write by hand, are just `object`. `repo` alone hides the required `url` and `base_ref` and the `^refs/heads/` pattern. `integration` hides its `plugin`/`topology` rule.
- Example 2: `records-receipt.md:79` (`Demand`) says `Type: null or object`, which hides the required `key` and `run`.
- Example 3: `vocab-registry.md:30` (`outcomes`) says `array of object`. The item shape and the `minItems`/`maxItems` are hidden.
- Example 4: maps that use `additionalProperties` as a schema, or `propertyNames` (for example `grant.confirmation_overrides`, `toolchain.images` with `minProperties`), are also just `object`.
- Effect: the page never says "see the schema". A bare `object` sits next to an explicit "object (open payload)", so the reader can fairly assume that any object is accepted. That misleads about requirements.
- Fix: recurse. Render nested objects as their own sub-sections or anchored tables, and link to them from the type cell.

### Medium

**M1. A root-level `oneOf` is not rendered.**
- Pages: `adapter-event.md:9`, `api-command-response.md:9`, `vocab-registry.md:9`.
- These pages go from the description straight to "## Definitions", with no line saying the document is one of the listed definitions. Helper definitions (`AdapterTurn`, `Code`, `Semver`) look like peers of the actual document shapes.
- Location: `schemadoc.go:56`. `section` returns when there are no properties, and the root never gets a `Type:` line.

**M2. Array and object limits are dropped.**
- Location: `schemadoc.go:141-142` and `:152`.
- Dropped keywords: `minItems` (14 uses), `maxItems`, `uniqueItems` (35), `minProperties`, `exclusive*`.
- Example: `records-challenge.md:17` (`allowed_confirmers`) says `array of [ActorID]` and does not show that it must be non-empty.
- The PR says the synthetic test covers "an array with bounds". The bound in the test is on the item (`minimum 1`), not on the array.

**M3. Some conditional rules go uncounted, and the count is the only hint the reader gets.**
- Location: `schemadoc.go:103-111`.
- Rules on nested objects are never counted: `approval.confirmation` has 2 rules, `project-profile.integration` has `if`/`then`/`else`.
- The `description` of each `allOf` entry in receipt.json is discarded.
- `else` branches are folded into "`if`/`then`".
- The reader therefore sees no rule at all where the schema has several.

**M4. Tests do not prove the stated claims.** I re-ran mutations, each one compiling.
- Mutations that survive `go test ./internal/schemadoc`:
  - dropping `maxLength`, `format` or `maximum` from the limits list;
  - turning off the top-level `if` counting;
  - leaving `\n` unescaped in cells;
  - always emitting the `Type:` line (even for definitions with properties);
  - deleting the definition properties table entirely (`section(&page, f, def, "####")`);
  - changing the label of a whole-file ref;
  - mapping an empty `type` to "object" instead of "any";
  - changing nil items to "string";
  - removing the banner;
  - removing the trailing-newline normalisation;
  - not escaping the title in the index.
- Closed objects: replacing `extra != nil && extra.Value == "false"` with `extra != nil` or with `extra != nil || true` also survives. The PR lists closed objects among the 13 killed mutations, so that claim is wrong. (Replacing the condition with plain `true` only fails to compile.)
- "Renders exactly" is overstated. `TestRender` checks substrings with `strings.Contains`, not a golden page.
- The committed pages plus gen-check act as a golden, but only until someone regenerates them together with a bug.

### Low

**L1. The link test can miss broken anchors.**
- It computes anchors with the generator's own rule (`schemadoc_test.go:79`, `strings.ToLower`), not GitHub's slug algorithm, and it ignores duplicate-heading suffixes.
- It is correct for today's names, but a definition named `Properties`, or a name with punctuation, would pass the test and break on GitHub.

**L2. Raw `<...>` text in descriptions is not escaped.**
- On GitHub, `<transition>/v1` (`records-lease-event.md:7`) and `legacy:<golden>` (`vocab-registry.md:58`) are swallowed as HTML tags. `cell` (`schemadoc.go:200`) only escapes `|` and newlines.

**L3. Objects that are not closed are not marked as open.**
- The difference between "closed" and "not stated" relies on the reader noticing that the "No other fields are allowed." line is missing.

**L4. `refLink` would build a wrong anchor for a deeper pointer.**
- `path.Base(frag)` on `#/$defs/X/properties/y` gives `y`. No such ref exists today, but nothing fails loudly if one appears.

### To reach GO
- Fix H1 and H2: render siblings of `$ref`, and recurse into or anchor nested objects, item objects and map values.
- Better still, fix M1 to M3 as well.
- Turn `TestRender` into an exact golden that includes a nested object, a ref with siblings, a root `oneOf`, `minItems`/`uniqueItems` and an open object without the "No other fields" line.

### Lead notes on round 1 (applied)

- **H1 (constraints beside a `$ref`):** every type shows the constraints its own node carries, beside a `$ref` too. `ProjectID` now reads "[TypeID](#typeid) (pattern `^prj_`)", and so do all the entity ids.
- **H2 (nested objects):**
  - Every inline object with fields gets its own section, "Fields of `<path>`". This covers a property, array items (`path[]`) and `oneOf` branches, at any depth, and a definition that is itself `null` or an object (receipt's `Demand`).
  - The table cell links to that section, and the section has its own required marks, limits, openness and rules.
  - `config-project-profile` now has 23 field sections.
- **Mediums:**
  - A root `oneOf` reads "A document is one of: …".
  - Array and object limits are shown: `minItems`, `maxItems`, `uniqueItems`, `minProperties`, `maxProperties`, and a `not` constraint.
  - Conditional rules are listed for each object, each with its description, or "(undescribed; see the schema)".
  - **Tests:** `TestRender` is now an exact golden page covering every case above. `TestLinksResolve` checks each link against exactly one heading, computing anchors by GitHub's algorithm, written independently of the generator's `Slug`.
- **Lows:**
  - `<` and `>` in prose are escaped.
  - Open objects say "Other fields are allowed."
  - A `$ref` deeper than `$defs/Name` links to the page, not a wrong anchor.
- **Mutation:** 26 points, all killed.

### New / remaining findings

#### High

**H2-r. Maps (`additionalProperties` as a schema, with `propertyNames`) still render as a bare "object", and their key and value constraints are lost.**
- Location: `schemadoc.go`, the `typeOf` `case "object"` branch. `inlineObjects` and `object()` also skip these maps because they have no `properties`, so no section and no openness line is written either.
- Affected cells (4, all required fields):
  - `config-project-profile.md` `toolchain.images`: `object (minProperties 1)`. The schema says keys are a `Slug` and values a `PinnedImage` (digest-pinned image). This is the hand-written profile.
  - `records-grant.md` `confirmation_overrides`: `object`. Keys are an `ActionKind`; values are `independent_review` or `human`.
  - `records-instrument-contract.md` `artifact_classes`: `object`. Keys are a receipt `Name`; values are `diagnostic` or `restricted`.
  - `records-manifest-intent.md` `policy.renderer_versions`: `object`. Keys are a `Name`; values are strings with minLength 1.

The page still gives a bare `object` with no note. Nothing marks it as constrained, so a reader can fairly take it as "any object".
- Fix (small): in `typeOf`, when `additionalProperties` is a mapping, render "map of <typeOf(propertyNames)> to <typeOf(additionalProperties)>" plus limits. Recurse `inlineObjects` into `additionalProperties` for object values. Add a map to the golden page.

#### Medium

**N-M1. A rule that sits on the object node itself is shown with the object's own description, presented as the rule.**

- The other cases repeat the definition's description as its rule: adapter-event `ToolResultEvent` and `CoverageEvent`, approval `ObjectRef` and `ExpectedState`, lease `PlacementCheck`. For CoverageEvent, the real rule (`observable: complete` means `unobservable` must be empty) is not what the text says.

- Fix: for the node-level `if`, render "(undescribed; see the schema)". Mention `else` when it is present.

#### Low

**N-L1. An object with no properties renders an empty table.** `config-project-profile.md` "Fields of forge.settings" is a table header with no rows. "No fields are defined." would read better.

**N-L2. Some generator branches are still not pinned by `go test`.** Two mutations survive:
- dropping `minProperties` from the limits list;

`gen-check` would catch the first one against the committed pages, but only until someone regenerates with the bug. The lead's claim of "26 points, all killed" therefore does not hold for these two points. Add `minProperties` and a deep `$ref` to the golden page.

#### High

#### Medium

**N3-M1. An array or object `const` renders as an empty code span, so the CoverageEvent rule is still unreadable.**
- Location: `typeOf`, `case get(n, "const") != nil`, which uses `get(n, "const").Value`. That value is `""` for a sequence or mapping node.
- Effect: `adapter-event.md` CoverageEvent reads "when `observable` `complete`, then `unobservable` ``". The schema says `{"const": []}`, meaning the list must be empty. This is the rule round 2 named under N-M1. It no longer states something false, but it states nothing. A reader could also take the empty span for an empty string.
- The golden page has no array `const`, so no test catches this.
- Fix: render a non-scalar `const` as its JSON, giving `` `[]` ``.

**N3-M2. Negated constraints read "any (with a `not` constraint)", so most rule clauses do not say what they require.**
- Extent: 29 clauses in the 36 rule lines. Every `not` in the schemas is `{"const": X}`: 24 with `null`, plus `""`, `[]`, `"empty"` (twice) and `"on_restore_verified"`.
- Examples:
  - `records-attempt`: "when `status` `stopping`, then `stop_reason` any (with a `not` constraint)". The schema means stop_reason must be non-null.
  - `records-receipt` Predicate: "when `outcome` any (with a `not` constraint), ...". The schema means "when outcome is not `empty`".
- The text is not false, since it flags that a constraint exists. It is the same marker round 2 accepted for field limits, so it does not block. But the lead's claim that "each rule now states what it constrains" holds for only part of the clauses.
- Fix: render `not: {const: X}` as "not `X`", and keep the generic marker for any other `not`.
