# PR #83 (source exclusions, B4): Astra reviews

## Review of #83 (Astra, 2026-10-05)

Verdict: NO-GO

1. **High — An exclusion can land between placement and launch.**  
   **docs/design/m0/05-leases-attempts-fencing.md:51–53**  
   Reading exclusions inside placement correctly orders concurrent placement and exclusion transactions. However, the state machine separately permits `lease.granted` and `attempt.started` (lines 76–78). The sequence **grant X → exclude X → start X** remains possible: the placement passed, but the attempt was not already running when X was excluded. This violates the stated immediate exclusion boundary under ordinary operation.

   Note 13’s result-time revalidation is too late to prevent disclosure, and its pre-effect rule does not explicitly require re-running placement checks for every model launch.

   **Fix:** Define the launch authorization boundary. Revalidate exclusions atomically with the transition authorizing an attempt to start; invalidate or re-place granted-but-unstarted leases when their executor becomes excluded. Specify how pending dispatches and restart recovery honor that boundary. Extend the fixture with both transaction orderings, including exclusion after lease grant but before attempt start.

2. **Medium — `no_authorised_route` lacks a concrete resume and escalation contract.**  
   **docs/design/m0/05-leases-attempts-fencing.md:54–58**  
   “A change to the policy-relevant state, or a source becoming available” describes event categories, not the concrete signal instance required by **02-vocabulary.md:80**. It leaves unspecified which revisions and source events matter, who owns the hold, and when it pages. An excluded source becoming healthy does not restore authorization; unrelated changes should not continually recreate the hold and reset escalation.

   **Fix:** Define the relevant policy/registry revision and availability subscriptions, persist their observed versions when entering the hold, and re-run full placement on a matching change. Preserve hold identity and paging history while still blocked. Specify owner, paging defaults, and precedence relative to quota, credit, and reviewer-availability holds. Deferring registry implementation is reasonable; deferring these semantics leaves the contract incomplete.

3. **Low — “Whoever asks” conflicts with existing confirmation defaults.**  
   **docs/design/m0/04-authority.md:81–82**  
   Classifying removal as `policy.widen_destinations` is appropriate. But that class has `every_actor_kind: false` in **schemas/vocab/actions.yaml:30**, while 04:96 explicitly calls knowledge export the only action requiring presence confirmation for operators. Classification alone therefore does not establish the newly promised all-actor confirmation.

   **Fix:** Either retain D32’s supervisor-only confirmation semantics and correct the wording, or explicitly define the additional all-actor requirement for lifting exclusions and reconcile the registry and existing exception statement.

The remaining design is sound at the contract level:

- Retries, restart recovery, provider-reset recovery, and fallback explicitly use placement. Evidence and review nodes also lease through 05 under 12/13; there is no documented alternate launch route.
- Excluding all but one source can steer work, and excluding every source can stop it. Those are substantial delegated powers, but the existing supervisor contract already permits quarantine and fallback ordering within its grant. Installation-wide exclusions must be authorized as installation-wide actions; a project-only grant must not suffice. Narrowing alone does not bypass destination, paid-fallback, or independence checks.
- Leaving **already-running** attempts untouched is acceptable for an admission policy with a separate stop action. It does not justify grandfathering unstarted leases.
- Family exclusions remain conjunctive with independence. A surviving executor cannot review its own contributing family; roster replacement must follow 13’s supersession rules. Excluding every independent option must hold, never weaken independence.

Only finding 1 blocks. This was a contract review; no files were modified.
### Lead notes on round 1 (applied)

- High (launch boundary): the start of an attempt is the launch authorization. The transaction recording `attempt.started` re-reads the exclusion set and refuses an excluded executor, and nothing is dispatched before it commits. A granted but unstarted lease whose executor becomes excluded returns to placement, and restart recovery starts nothing without passing the same boundary. The fixture covers an exclusion before the grant and between the grant and the start.
- Medium (hold contract): the hold persists the exclusion-set, source-registry and profile revisions it was decided on, and a change to any re-runs full placement. A source becoming healthy does not lift it while excluded. The same hold and its paging history continue while blocked. The operator owns it, and it pages after 30 minutes. It applies only when no route is admissible under policy; capacity and reviewer holds take precedence when a route exists but is blocked.
- Low (D32): lifting keeps `policy.widen_destinations`'s D32 semantics: a supervisor's lift waits for a human, and an operator's own lift is that decision. Adding an exclusion needs an installation-scoped grant; a project-only grant never suffices.

## Second review of #83 (Astra, 2026-10-05)

Verdict: GO with changes

- **Round-1 High — Resolved as a blocking finding.** In `05:51–57`, exclusion checking and launch authorization now share the `attempt.started` transaction; dispatch follows commit. This matches `05:136`, where `attempt.started` creates a `running` attempt, and restart closes running attempts as lost (`05:152`). It does not waive 13’s separate pre-effect authority/applicability revalidation (`13:117–120`). The fixture (`11:135–139`) covers exclusions before grant and between grant and start. The return-to-placement transition remains incomplete, below.
- **Round-1 Medium — Substantially resolved; one resume dependency remains missing.** `05:62–70` now specifies concrete observed revisions, preservation of hold identity/paging history, operator ownership, a 30-minute paging threshold, and capacity/reviewer precedence. The explicit threshold overrides 02’s default; existing operator-owned holds retain their owner (`escalate_to: null`). The remaining signal gap is below.
- **Round-1 Low — Resolved.** `04:82–84` correctly preserves D32: supervisor lifts require human confirmation; an operator’s own action suffices. This agrees with `schemas/vocab/actions.yaml:30`.

New findings, by severity:

1. **Medium — “Returns to placement” has no legal state transition or reservation disposition.**  
   **`docs/design/m0/05-leases-attempts-fencing.md:54`**, against the complete table at **`:81–94`**.

   When an exclusion rejects start, the lease remains `granted`. The table permits only starting or deadline expiry from that state; neither returns it to `requested` or `waiting`. Reservations already exist, and their release is tied to settlement/release (`:114–116`). Consequently, the prose and fixture require a recovery path the state machine cannot express. This is a liveness/accounting gap; the explicit start guard still prevents the forbidden launch.

   **Fix:** Define the event and destination state. For example, invalidate the unstarted grant into `releasing`, release its unused reservations, then request a replacement lease. Alternatively, define an atomic return to `requested` with explicit reservation unwinding. Update the table and extend `11:135–139` to assert the transition, reservation disposition, and absence of an attempt on the excluded executor.

2. **Medium — The hold does not observe installation usage-policy changes.**  
   **`docs/design/m0/05-leases-attempts-fencing.md:62–64`**.

   The signal watches exclusions, the source registry, and the project profile. But placement also depends on the installation’s active usage profile and overrides (`docs/plan/01-first-release-plan.md:177–190`; `07-project-profile.md:80`). An authorized installation-policy change can make a route admissible without changing any of the three watched revisions. The hold then lacks a specified wake-up despite the operator having removed its cause.

   **Fix:** Persist and subscribe to the installation usage-policy revision too, or define an effective routing-policy revision covering all inherited dependencies. Add a fixture where only that installation revision changes, placement resumes, and unsuccessful reevaluations preserve paging history.

No Critical/High findings remain under D43. This was a contract review; no files were modified.
