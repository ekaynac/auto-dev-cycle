# PR #46 (strict union encoding): review

## Review of #46 (Opus subagent, 2026-10-04)

Verdict: GO

All checks were run by hand on copies under `scratchpad/rv46/` (`new` = 8e8916c, `old` = the same tree with the PR's seven modified files reverted to origin/main). Toolchain: go1.27.1. `make ci` passes on 8e8916c (exit 0: lint, gen-check, build, vocab-check, sandboxed tests, sandbox self-test, dist).

What I checked and confirmed:
- **Which method runs.** With `json.DefaultOptionsV1()`, `AllowInvalidUTF8(false)` and `EscapeForHTML(false)`, json/v2 calls `MarshalJSONTo` instead of `MarshalJSON`. I tested this on a type that has both methods. On go1.27, v1 `json.Marshal` also calls `MarshalJSONTo`: a nil variant fails with "error calling MarshalJSONTo" through plain `json.Marshal` too.
- **Encoder options reach the variant through `MarshalEncode`.**
  - `AllowInvalidUTF8(false)`: invalid UTF-8 in `TreeSubject.ContractRevision` and in `GrantReadsProjects.List` is now refused while marshalling ("invalid UTF-8"). Before, the bytes were repaired to U+FFFD and either accepted (subject) or caught only by the adc-typeid format check (project lists).
  - `EscapeForHTML(false)`: reaches the variant (see Low-1).
  - v1 nil-slice-as-null: also preserved. `GrantReadsProjects{}` still encodes as `null`, and the schema still refuses it.
- **Output is unchanged for valid records.** Old and new `contract.Encode` produce identical bytes for all five receipt subject variants, a grant with listed projects and `reads.projects: "same"`, a grant with `"*"` projects and a listed `reads.projects`, and the three vocab registry files (outcomes, reasons, holds). Old and new `json.Marshal` output is also identical. The one difference is Low-1.
- **Nil variants.**
  - Nil `Variant`: an error in both `contract.Encode` and `json.Marshal`, same as before.
  - Typed-nil `Variant` (`(*TreeSubject)(nil)`): encodes `"subject":null`, which the schema `oneOf` refuses in `contract.Encode`, same as before.
- **Other custom marshalers.**
  - `ReasonCode.MarshalText`: refuses unregistered codes before UTF-8 even comes up. On its own, the encoder also refuses invalid UTF-8 in any `MarshalText` output.
  - Keyed unions: plain structs with no custom marshaler, so they are strict by construction.
  - `json.RawMessage` fields (`Receipt.Payload`, `Approval.Scope`, `Proposal.Scope`): invalid UTF-8 and lone-surrogate escapes are refused while marshalling. Duplicate keys pass the marshal step but are refused by `validate`/`readValue`.
  - In `gen/go/types` (`Subject`, `VocabRegistry`, `GrantReadsProjects`, `ProjectScope`), no marshaler still lets repaired UTF-8 through `contract.Encode`.
- **Do the tests catch the bug?** Yes. Against the old generated code, `TestUnionsEncodeStrictly` fails at line 31 ("invalid UTF-8 inside a discriminated union: <nil>"), and the restored `TestDeriveValidatesProducerFields` case fails ("invalid UTF-8 in the subject: <nil>").
- **Generator.**
  - `MarshalJSONTo` is now a reserved literal field name (unions.go:233).
  - The `Variant` struct in discriminated unions cannot collide with the new method.
  - `marshalTo` is unexported, and generated type names are always exported, so the two cannot collide.
  - gen-check passes.

### Low

1. **Output bytes change for `<`, `>` and `&` inside a union variant**
   - Where: gen/go/types/records_receipt.gen.go:160, unions.go:173.
   - Before the fix, the inner v1 `json.Marshal` HTML-escaped these characters, and the outer encoder copied its output unchanged. So `contract.Encode` wrote `"a\u003cb\u003e\u0026c"` inside `subject` but `<>&` everywhere else.
   - Now the variant follows `EscapeForHTML(false)`, the same as the rest of the document. This fixes an inconsistency, and digests are taken over JCS, not over `Encode` output, so nothing breaks.
   - It is still a change in `Encode` bytes that the PR does not mention.
   - Fix: add one line to the PR description or the commit body.

2. **The literal-or-list half of the test depends on a substring in the error message**
   - Where: schemas/union_encode_test.go:45-46.
   - Every list in these unions holds format-constrained IDs (`ProjectID`). Without the fix, the repaired `prj_\uFFFD` is still refused, by the adc-typeid format. The test catches the regression only because it checks for "UTF-8" in the error text.
   - That check works today, but a reworded marshal error would break it silently.
   - Fix: also assert the marshal stage, e.g. `strings.Contains(err.Error(), "marshal:")`. Or encode the union directly and check the encoder error: `jsonv2.Marshal(grant.Projects, json.DefaultOptionsV1(), jsontext.AllowInvalidUTF8(false))`. Coverage for `VocabRegistry` would be optional, since it uses the same template.

3. **The package comment overstates what `Encode` catches**
   - Where: internal/contract/contract.go:14-16.
   - The comment says `Encode` refuses invalid UTF-8 "including the output of MarshalText and MarshalJSON methods". That holds only for raw bytes. A `MarshalJSON` that builds its output with v1 `json.Marshal` hands over output that is already repaired. That is the bug this PR fixes.
   - The same pattern still exists in `vocab.Result.MarshalJSON` (internal/vocab/vocab.go:213-222). It is not passed to `contract.Encode` today, so it has no effect now.
   - Fix: add a sentence saying a custom marshaler on a contract type must implement `MarshalJSONTo` (or write only raw bytes) for the encoder's options to apply.

4. **`MarshalJSON` is now effectively dead code and behaves differently from `MarshalJSONTo`**
   - Where: unions.go:164-169, 243-248.
   - On go1.27 both v1 and v2 marshalling call `MarshalJSONTo`, so `MarshalJSON` runs only when someone calls it directly. Called that way, it still repairs UTF-8 and HTML-escapes.
   - Keeping it for `json.Marshaler` assertions is reasonable.
   - Fix (optional): implement it as `jsonv2.Marshal(u, json.DefaultOptionsV1())` so the two cannot drift, or add a comment saying it is the lenient v1 path.

5. **A typed-nil variant is caught only by the schema** (existing behavior, not introduced here)
   - Where: unions.go:173-177.
   - `Subject{Variant: (*TreeSubject)(nil)}` marshals to `null` without an error. `contract.Encode` refuses it at the `oneOf`, but plain `json.Marshal` emits `"subject":null`.
   - Fix (optional): in the template, refuse a typed nil next to the nil check, e.g. with a generated per-variant type switch that checks `v == nil`. That gives a clearer error than the schema dump.

### Lead notes (applied before merge)

- Low 1: the PR body now notes that `<`, `>` and `&` inside a union variant are no longer HTML-escaped by `Encode`,
  matching the rest of the document. Digests are taken over JCS, so none change.
- Low 2: the literal-or-list case also asserts the refusal comes from marshalling (`marshal:`), not from adc-typeid.
- Low 3: the `internal/contract` package comment says a custom marshaler on a contract type must implement
  `MarshalJSONTo` (or write only raw bytes). `vocab.Result.MarshalJSON` never reaches `Encode` today.
- Lows 4 and 5 (lenient `MarshalJSON` kept for direct callers; a typed-nil variant refused by the schema, not the
  marshaler) are left as they are: both are existing behaviour, and `Encode` refuses both cases.
