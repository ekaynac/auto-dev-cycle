### 4. New findings

**L1. One task's own read can still pass the 1 MiB bound, and `task wait` pays for `bench` on every poll. OBLIGATION (state it, or fix).** `internal/api/tasks.go` (`taskRead`, bench `true` for every one-task read); `internal/cli/tasks.go` (`readTask`)
- **Cause:** `task show`, `task wait` and `bench record` all read the facts, so an operator token computes and ships the whole ledger of the task on each poll.
- **Arithmetic:** about 1.2 KB per call makes the bound about 850 calls in one task. That is about 2,600 measurements; the row's large task holds 900 in a third of a MiB.
- **Effect:** past that, the task's own `show` and `wait` fail ("response exceeds 1048576 bytes") where main's did not.
- **How likely:** a task's calls are bounded by its rounds and turns rails, so this is unlikely at (a).
- **Fix:** state the per-task bound. Or let `task wait` read without `bench`, for example with a field mask or a separate facts route.

**L2. Damage before the scope check. OBLIGATION (minor).** `internal/api/tasks.go` (`ReadTask`)
- **Cause:** `graph.TaskNodes` runs before `taskRead`'s board check. A task in a project the caller does not read, whose node index is damaged, answers with an error rather than the empty list.
- **Effect:** this reveals damage, not content.
- **Fix:** check the task's board scope first, then read its nodes.
