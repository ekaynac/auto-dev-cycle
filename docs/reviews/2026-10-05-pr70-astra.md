# PR #70 (adc dev verify-log): Astra reviews

## Review of #70 (Astra, 2026-10-05)
Verdict: NO-GO

### High

- **Verification initializes and repairs the database before checking it.** `internal/cli/verifylog.go:98` calls the normal `Open`, which executes DDL and initializes genesis (`internal/eventstore/store.go:206`, `:244`). The existence check at `verifylog.go:60` is insufficient: I reproduced a zero-byte `adc.db` becoming a populated store and returning `empty/completed_clean`, exit 0. Verification also recreated a deleted append-only trigger. Even with a trusted head, these writes happen before verification fails.

  **Fix:** provide an existing-store, read-only verification path that performs no initialization, schema repair, or migrations. Retain exclusive locking. Add tests for zero-byte databases, unrelated SQLite databases, and missing schema/meta objects, asserting both refusal and preservation of the inspected data.

### Medium

- **Malformed trusted heads receive the wrong result; an explicitly empty head silently disables anchoring.** `internal/cli/verifylog.go:51` validates only the sequence and a nonempty hash. I reproduced `--trusted 0:x` returning `failed/log_integrity_broken`, exit 1, while `--trusted ""` returned success without an anchor. These are malformed arguments, which the acceptance criteria assign exit 64.

  **Fix:** distinguish an omitted flag from an explicitly empty value and validate the complete `sha256:<64 hex>` digest before accessing the store. Test empty, short, nonhex, and wrong-algorithm values.

- **Filesystem access failures are misclassified as usage errors.** `internal/cli/verifylog.go:60` converts every `os.Stat` error into “no event store” and exit 64. An existing database under an inaccessible directory reproduced this behavior. Note 08 assigns inability to perform the check exit 2.

  **Fix:** reserve the missing-store usage response for `os.ErrNotExist`; preserve other errors as `could_not_run` diagnostics, exit 2. Add an access-denied test.

- **Operational failures violate the JSON output contract.** `internal/cli/verifylog.go:99` prints only stderr on open failure; the other operational-error branches behave similarly. With a non-SQLite `adc.db`, `--json` returned exit 2 with empty stdout. Note 08 requires one JSON document for nonstreaming commands.

  **Fix:** emit a checked `could_not_run` result with an appropriate registered reason and nonempty detail for operational failures, keeping diagnostics on stderr. Test parsing the complete stdout document for open, lock-access, and verification-read failures.

- **The verifier rewrites the controller’s lock record.** `internal/cli/verifylog.go:89` uses `AcquireLock`, which creates the lock file and, after acquiring it, truncates and replaces its contents (`internal/eventstore/lock.go:55`, `:80`). This conflicts with note 03’s explicit rule that probes never create or truncate the lock.

  **Fix:** add a verification/probe acquisition mode that locks the existing file without changing its contents. Test byte preservation and refusal while another holder owns the lock. The current implementation does correctly refuse a held lock before opening the database.

The reason registration at `schemas/vocab/reasons.yaml:27` is sound: `log_integrity_broken`, domain `ops`, source `03`, and outcome `failed` accurately describe an observed integrity violation. The normal clean/broken/held-lock mappings to exits 0/1/2 are correct.

For an existing readable store, the command correctly delegates full-chain checking and trusted-head comparison to `Store.Verify`. The tests demonstrate payload-edit detection, anchored truncation detection, and the expected limitation that an unanchored consistent prefix passes. Existing event-store tests also cover a consistently rewritten tail.

Validation: sandboxed tests for `internal/cli`, `internal/eventstore`, and `internal/vocab` passed; disposable probes confirmed the failures above. The passing tests and reported mutation coverage do not establish the store-preservation claim. Full `make ci` was not rerun. No source files were changed.
### Lead notes on round 1 (applied)

- High (initialization and repair): verification no longer opens a `Store`. `eventstore.VerifyExisting` reads an
  existing database through a read-only connection in one read transaction, with no DDL and no genesis. Before SQLite
  opens the file, `checkHeader` requires an SQLite 3 header in WAL mode. A probe showed why this is necessary: with an
  emptied `adc.db`, a read-only connection deleted the 173 KB write-ahead log beside it as stale on close.
  `checkObjects` compares every table, index and trigger (type, name, table, statement) with those the format's DDL
  creates, so a dropped, rewritten or extra trigger fails verification as well. `TestVerifyLogNeverRepairs`
  fingerprints the state directory around each case (a dropped, rewritten or extra trigger, no meta table, an empty
  file, not a database, an unrelated rollback-journal database beside the fixture's log). The fingerprint excludes only
  SQLite's reader mechanics: the `-shm` index, and an empty `-wal` a reader creates.
- Medium (malformed heads): an explicitly empty `--trusted` is malformed, not "no anchor". The head must match
  `^(0|[1-9][0-9]{0,17}):sha256:[0-9a-f]{64}$`; twelve malformed forms are tested to exit 64.
- Medium (access failures): only `os.ErrNotExist` is "no event store" (exit 64). Any other failure is
  `could_not_run/store_unreadable` with exit 2; an unreadable database and an inaccessible state directory are tested.
- Medium (JSON contract): every operational failure prints one result document, `could_not_run/store_unreadable` with
  the error as detail, and the diagnostic on stderr. `store_unreadable` is a new registered reason (ops, 03).
- Medium (lock record): `eventstore.ProbeLock` takes the same `flock` on the existing lock file, opened read-only. It
  never creates the directory or the file, and never truncates or rewrites the record; `TestProbeLockChangesNothing`
  checks byte preservation and mutual exclusion with `AcquireLock`. A store with no lock file is `store_unreadable`,
  and the probe does not create one.
- Mutation: 15 points, all killed.

## Second review of #70 (Astra, 2026-10-05)

Verdict: NO-GO

- **First-round High — initialization/repair: partially resolved.** Zero-byte, unrelated SQLite, and non-SQLite databases are refused unchanged; a deleted trigger is not recreated. However, verification can still delete a populated WAL, as reproduced below.
- **Malformed/empty trusted heads: fixed.** Explicitly empty, short, nonhex, and otherwise malformed values return exit 64.
- **Access failures classified as usage errors: fixed.** An inaccessible directory returns `could_not_run/store_unreadable`, exit 2.
- **Operational failures breaking JSON: fixed.** Reproduced access and SQLite-read failures emit one JSON result with nonempty detail.
- **Lock-record rewriting: fixed.** The record remains byte-identical. The read-only descriptor’s exclusive flock provides mutual exclusion with `AcquireLock` on the tested Linux filesystem.

**High — Header validation does not prevent destructive SQLite side effects.** `internal/eventstore/verify.go:78` and `:81`.

I created a complete store using 512-byte SQLite pages, with one committed event in its 2,176-byte WAL. Verification against its trusted head initially returned exit 0. I then sparsely extended the database to **2,199,023,255,552 bytes**, preserving its existing bytes and header. Verification returned exit 1 but **deleted the WAL containing the event**. The syscall trace confirms:

```text
unlinkat(AT_FDCWD, ".../adc.db-wal", 0) = 0
```

SQLite’s page-count calculation wraps to zero at this size and treats the WAL as belonging to an empty database. This requires neither concurrent modification nor substantial disk allocation.

The header/open race is also real: pausing at line 81, confirming the probe flock remained held, and truncating `adc.db` from another process caused verification to delete its WAL. The advisory lock excludes cooperating `adcd` instances; it cannot stabilize files against direct writes.

**Fix:** prevent SQLite from modifying the inspected files at the filesystem/VFS boundary, or verify a private snapshot containing both the database and committed WAL. Header checks alone are insufficient. Add preservation regressions for the sparse-file case and the controlled race. This remains blocking because the verifier destroys recoverable event data.

**Medium — Schema comparison excludes required automatic indexes and accepts an incomplete store.** `internal/eventstore/verify.go:161`.

Using `PRAGMA writable_schema=ON`, I removed the `sqlite_autoindex_events_1` entry while preserving the table declarations, triggers, and genesis. Verification returned `empty/completed_clean`, exit 0. SQLite’s `PRAGMA integrity_check` reported a malformed database. The blanket `sqlite_%` exclusion hides a required unique index from comparison.

**Fix:** compare required automatic indexes as well as explicit objects, and perform structural integrity validation before declaring the store clean. Add this malformed-schema regression. This finding is nonblocking under the requested severity threshold.

`store_unreadable` is correctly registered in `schemas/vocab/reasons.yaml:28`: outcome `could_not_run`, domain `ops`, source `03`; the Go and TypeScript registrations agree.

Validation: targeted CLI, eventstore, and vocabulary tests passed; vocabulary checking reported zero findings. Independent disposable probes established the failures above. No repository files were modified.
### Lead notes on round 2 (applied)

- **High (SQLite deletes a populated write-ahead log):** SQLite no longer opens the store's files.
  - `VerifyExisting` copies the database and its write-ahead log into a new private temporary directory. It opens each
    original read-only, without following links, and SQLite opens only the copy. Whatever SQLite does to a log it
    takes as stale, or to a file another process changes meanwhile, happens to the copy.
  - The header check runs on the copy, so there is no window between check and open.
  - The copy is bounded (16 GiB, `maxSnapshotBytes`). A larger store is not checked: it is
    `could_not_run/store_unreadable` and nothing is copied. Your 2 TiB sparse file is refused this way, and its log is
    kept byte for byte (`TestVerifyLogRefusesAnOversizedStore`). A file that grows past the bound while being copied is
    refused.
  - The state-directory fingerprint is now exact, SQLite's `-shm` included: a reader of the original would leave its
    marks there. A fully read-only state directory and store still verify, unchanged (`TestVerifyLogReadOnlyState`).
  - The copies are removed, checked with a private `TMPDIR` that must be empty afterwards.
- **Medium (automatic indexes, structural integrity):**
  - The object comparison now includes SQLite's automatic indexes; only `sqlite_stat*` is left out.
  - `PRAGMA integrity_check` must answer `ok`.
  - SQLite's own verdicts on the file (`SQLITE_CORRUPT`, `SQLITE_NOTADB`), raised from whichever query first meets
    them, are `failed/log_integrity_broken`, not "could not run".
  - New cases: a dropped automatic index (your reproduction), an index whose root page points at another index, and an
    index entry changed in the file, which only the integrity check sees.
- **Mutation:** seven points. Six are killed: opening the original, no integrity check, no header check, no corruption
  mapping, the log not copied, and the copy not removed. Skipping automatic indexes in the comparison survives,
  because the integrity check also catches a dropped automatic index; the two layers overlap on that case.

## Third review of #70 (Astra, 2026-10-05)

Verdict: NO-GO

- **Round-2 High — destructive SQLite side effects: fixed.** Both reproductions rerun: the 2 TiB sparse database returns `could_not_run/store_unreadable`, exit 2, preserving its populated WAL. Truncating the original database from another process while verification is paused no longer deletes its WAL; the probe lock remained held.
- **Round-2 Medium — automatic indexes and structural integrity: fixed.** Missing automatic indexes and malformed index roots return `failed/log_integrity_broken`, exit 1, without changing the originals. Structural-integrity regression tests pass.

**High — The database and WAL copies can describe different moments and falsely pass verification.** `internal/eventstore/verify.go:148`, `:168`, `:181`.

The probe lock excludes cooperating controllers, but the sequential copies neither stabilize nor revalidate their sources. I reproduced this with an event whose payload already disagreed with its hash:

1. Verification initially returned `failed/log_integrity_broken`.
2. I paused the verifier after copying the database, immediately before opening its WAL. A separate process checkpointed and truncated the WAL, then committed a projection update. The probe lock remained held.
3. Resuming verification returned **`empty/completed_clean`, exit 0, head sequence 0**. Verification of the source immediately afterwards still reported the broken event.

The copy combined the older, empty database with the replacement WAL and silently omitted the corrupted event. Integrity checking cannot detect this structurally valid mixture.

**Fix:** establish and validate a stable source pair before accepting the snapshot. Open and validate source descriptors, retain identities and change metadata, and recheck both files and WAL presence after copying. Reject replacement, truncation, growth, or modification as `could_not_run`; alternatively use a genuinely atomic snapshot mechanism. Add the controlled checkpoint regression.

**Medium — `TMPDIR` can place all temporary writes inside the inspected state directory.** `internal/eventstore/verify.go:162`.

With `TMPDIR` equal to `--state`, syscall tracing showed verification creating a directory there, writing copied database/WAL files, creating SQLite’s shared-memory file, and removing them afterwards. The command returned success. A final content fingerprint misses these operations and the changed directory metadata.

**Fix:** choose a validated temporary location outside the state directory, accounting for relative paths and symlink aliases, before creating anything.

**Medium — Cleanup failures silently retain the copied store.** `internal/eventstore/verify.go:94`, `:170`.

Both `RemoveAll` errors are discarded. Making the temporary directory non-writable before cleanup reproduced a successful verification that left the database and sidecars behind. Their private permissions limit exposure, but successful return does not establish removal.

**Fix:** check cleanup errors on both success and failure paths; report incomplete cleanup and the residual location instead of silently returning success.

Other checks passed: ordinary source access was read-only; static symlinks/hardlinks and a symlink substituted after preflight were refused unchanged. A checkpointed database without a WAL verified successfully; an orphan WAL was preserved while the command returned missing-store usage error. The aggregate copy guard correctly refused growth with exit 2, tested using a reduced debugger-set bound; ordinary copy failures removed their temporary files.

Validation: targeted CLI, event-store, and vocabulary tests passed, plus independent syscall traces and debugger-controlled reproductions. No repository files were modified.

- **Mutation:** seven points, all killed: no recheck, the times ignored, presence ignored, an inside TMPDIR allowed,

**Medium — A symlink followed by `..` bypasses containment validation.** `internal/eventstore/verify.go:236`, `:180`.

With `alias -> state/sub` and `TMPDIR=alias/..`, `filepath.Abs` cleans away the symlink component before resolution, so validation considers the location outside state. `MkdirTemp` uses the original path, which the filesystem resolves inside state. **Fix:** resolve symlinks and `..` in filesystem order, and use the same validated directory for creation. Add this static alias regression.

**Medium — Temporary-directory aliases are re-resolved during creation and cleanup.** `internal/eventstore/verify.go:180`, `:273`.

Two controlled reproductions succeeded:

- Retargeting a TMPDIR symlink from an external directory to state after validation caused database/WAL copies and SQLite’s shared-memory file to be created inside state, then removed. Verification returned `completed_clean`, exit 0.
- Retargeting the alias just before cleanup made `RemoveAll` inspect a nonexistent path and return nil. Verification returned `completed_clean`, exit 0, leaving the original copy and sidecars behind without reporting them.

Neither reproduction changes or restores source-file metadata.

**Fix:** retain stable identities/handles for the validated temporary parent and created snapshot, and use them throughout creation, access, and cleanup. Detect lost identity or incomplete removal and report the residual location. Add both alias-retargeting regressions.

No Critical/High blockers remain under the operator’s scope and severity threshold. Targeted CLI, eventstore, and vocabulary tests passed; independent debugger and syscall probes confirmed the results above. Repository files were unchanged.
### Lead notes on round 4 (applied)

- **Medium (a link followed by `..`):** `tempRoot` resolves `TMPDIR` once, links and `..` in filesystem order. A
  relative `TMPDIR` is joined to the working directory without cleaning it first. A `TMPDIR` that does not exist is
  refused before anything is created. The copy is then made under that canonical root, never under the alias. Tests:
  the state directory, a directory inside it, a link to it, `subalias/..` (your reproduction), and two missing paths,
  each refused with the state directory unchanged.
- **Medium (retargeted aliases):**
  - The copy's directory has no alias in its path, and it is removed by that canonical path.
  - Its identity (device and inode) is recorded when it is made. Before removal it must still be that directory,

  - Tests: the `TMPDIR` link retargeted to the state directory after the check and before the cleanup (both verify
    with the state directory unchanged and nothing left behind), and a copy moved away before its removal (reported).
- **Mutation:** four points, all killed: cleaning before resolving, making the copy under the alias, no identity
