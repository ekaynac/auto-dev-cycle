## External review of #231 (Mythos, 2026-10-13)

Verdict: GO with changes

No Critical or High finding. One Medium is cheap to close before merge; the rest go to the backlog issue.

### Medium

**M1. Attachment paths that cannot coexist on one filesystem pass intake.** `schemas/api/scope/task-create.json:27` and `internal/authority/task.go:104`. Uniqueness is by exact string, so `a` and `a/b` are both admitted, yet one is a file and the other needs `a` as a directory. The schema also allows a 256-byte single segment, one over NAME_MAX on ext4. Either task is created, approved and parked in Ready, where it can never run and, until P22a's removal action, never leave. Fix: in `taskInputOf`, refuse a name that equals any ancestor directory of another name (track each name and its parent prefixes in the `seen` map), and lower `AcceptancePath.maxLength` to 255. Add both to the ErrInvalidScope table in `TestTaskCreateRefusals`.

### Low

**L1. The fold does not bind the approval event's project to the task.** `internal/authority/task.go:300`. The payload's `project` is checked, the event header's `ev.Project` is not, while `addTask` checks both for the task. An event-level mismatch only affects read scoping and is out of the threat model, but the asymmetry is a one-liner: add `ev.Project == nil || *ev.Project != string(t.Project)` to the binding condition.

**L2. A storage fault during the Ready count is reported as `ready_backlog_full`.** `internal/authority/task.go:146`. `errors.Join(err, refusal(...))` carries the Refusal even when `tx.Keys` failed, so the daemon's `errors.As` mapping names a full backlog with a count of zero. Same pattern as P1's project check. Fix: return the storage error alone when `err != nil`, and the refusal only on the count.

**L3. Size and review record.** 418 against 400 is explained and inside §2's 300–600 band; accepted. Workflow §3 says reviews are saved in the PR under `docs/reviews/`; recent PRs (#227 onward) have not, and this one should land as `docs/reviews/2026-10-13-pr231-mythos.md`.

**L4. The spec the builder sees carries the acceptance file names.** `schemas/records/task.json:12`. `spec.attachments` lists every hidden test's path and digest. The digests are harmless; the paths may hint at what is tested. This is a P14/P22a rendering decision, not P3's, but the backlog entry for I18 consumption should say explicitly whether `attachments` is withheld from the builder's and reviewer's view of the spec.

### Judged questions

1. **Approval binding.** Sound. The fold at `task.go:284` binds object id, type, version 0, object digest, scope digest, project, action, actor kind, expected version 0, no grant, policy none, and requires the actor to be the task's creator, live, an operator, in the task's creating command, once. The writer stamps every event's actor with the command actor (`writer.go:563`), so a different actor cannot appear in the same command. `ProjectEach` folds per event, so `task.created` is projected before its approval in the same command. The `approval_id/` index is shared with proposal approvals; `approvalOf` (`grant_handlers.go:217`) loads the value as a proposal id, finds no `approval/` record and errors, so a task approval can never be cited by a grant. Fabricated events outside a supported command are out of the threat model; through the supported command only the logic's exact builder output is emitted.

2. **Spec digest.** Computed over the raw command input (`task.go:159`). The stored `spec` is the decoded struct re-marshalled, and the fold re-derives the digest from that stored spec and refuses a mismatch (`task.go:244`), so the record consumers read is digest-equal to what was approved. The approval's `scope` is the raw input and is checked the same way. Attachment bytes are bound by the digests inside the spec.

3. **Restricted classification.** `records/task.json` admits only `class: restricted` with exactly both audiences; `classed` (`task.go:270`) re-checks name, digest, class and both audiences per entry against the spec. Loosening it needs a contract PR to both schema and fold. The consumption side is P22a's.

4. **Uploads.** `Publish` runs inside the logic, after authority, under the command actor (`task.go:150`); `Drop` runs only on an applied, non-replayed commit (`task.go:176`). Ownership is enforced by `uploadPath(actor, digest)` in the blobstore, and the test covers another actor's, an expired and a missing upload. A refusal after a partial publish leaves an already-published content blob, which the P2 contract accepts, and the upload is kept for retry.

5. **Five-Ready bound.** Race-free: the writer is one SQLite connection with `_txlock=immediate` (`store.go:223`), so the `Keys` count and the insert share one serialised transaction, and the fold re-checks on replay. `ready_backlog_full` as `failed` is justified: the request is refused on state and nothing is recorded; `capacity_reserved_full` is a hold. Note that a supervisor with a `task.create` grant can fill all five slots of a project; with no removal action that blocks the operator's intake there. Covered by the P22a prerequisite (backlog #226 entry 23).

6. **Revocation.** Yes. `TaskProjector` folds `identity.actor_revoked/v1`, walks `approver/<actor>/`, marks each approval `revoked` with `revoked_at` and drops the index entry (`task.go:318`). `TestTaskApprovalRevoked` shows the other operator's approval untouched and the store rebuilding equal.

7. **Replay stability.** The goldens freeze both payloads with actor and time filled in; the fold checks binding fields only, and the "another reason" case proves a later change to `TaskApprovalOf`'s free text replays. Payload schema validation runs at append only (`store.go:526`), not at rebuild or verify, so tightening the scope schema later does not strand stored events. A later change to `withheld_from`'s audience set replays because `classed` uses `slices.Contains`.

8. **Deferral.** `TestTaskCreateStaysDeferred` drives the real `adcd` and `adc` with `--scope-file` and `--attach`, gets `action_deferred`, and asserts no handler and a registered kind. `matrix.go` still lists `task.create` as deferred with the P3/P22a ref.

9. **Fault evidence.** Discriminating. The four F cases each fail only on the digest bindings (mutation 1), and the controller-side mutation (the builder given a zeroed digest) fails the three creation tests through the fold. The reused-id and later-command cases cover the two other ways an approval could be attached to the wrong task.

10. **M1 deferral.** Acceptable. `intake` is inert, the gap is recorded as a P22a prerequisite with its trigger, and this PR activates nothing. Workflow §2's "no PR may activate a known blocking defect" is honoured as long as P22a lands the removal action before flipping the capability.
