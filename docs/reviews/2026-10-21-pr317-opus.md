## Opus review of #317 (2026-10-21)

Verdict: NO-GO

I reviewed head `ccf08da` and ran mutation probes in a throwaway copy of the worktree, one test per run. Host load was 7 to 18 on 20 cores. The worktree is unchanged and the copy has been deleted.

### H1. `TestIntegrityDoS` does not catch the quadratic scan it guards against
- **Where:** `internal/accept/integrity_rest_test.go:218-246`. The bound is at `:244`.
- **What it guards against:** `1ae3268`, "perf(accept): find vendor/ and the test files once per run" (P14e-2b).
- **Mutation:** I restored the three per-call scans that commit removed:
  - the `vendor/` changed check and the `vendor/` directory check, once per module, in `internal/accept/integrity_types.go:287-308`;
  - `anyTest`, once per compared directory, in `internal/accept/integrity.go:419-421`.
- **Result:** the row still passes.

  | Run | 250 modules | 2,500 modules | Ratio | Bound |
  |---|---|---|---|---|
  | Unmutated | 1.51 s | 10.56 s | 7.0 | 25 |
  | Mutated | 3.98 s | 45.29 s | 11.4 | 25 |

  The old fixed 30 s bound would have caught this mutation on an idle host.
- **Why:** the PR's "quadratic: 100" ignores the 7,500 `other/` paths that both runs share. The scan cost goes from 250 × ~8,000 paths to 2,500 × ~12,500 paths, about 15.6 times, not 100. The 250-module run also carries its own share of the scan (3.98 s against 1.51 s). No ratio between 7 and 11.4 is a safe bound.
- **Fix:** keep the module count fixed and vary only the other paths, for example 1,000 changed modules over a base with no other paths and over one with 20,000. Before choosing a bound, show in the PR that the scan mutation fails the row. My probe of that design:

  | Code | Ratio, 20,000 other paths against none |
  |---|---|
  | Unmutated | 1.64 |
  | Unmutated, with the scan in L1 removed | 1.22 |
  | Mutated | 3.39 |

  So the bound only separates cleanly once L1's scan is gone. A deterministic count of path scans would be stronger than any timing bound. Also correct the "quadratic: 100" comment at `:221` and the PR body.

### H2. `within`'s baseline repeats the row's expensive work for the Python fixtures, so a slowdown there cannot fail the row
- **Where:** `internal/accept/integrity_test.go:112-119`. Affected rows:
  - `internal/accept/integrity_pyguard_test.go:1025`, 1794, 1847, 1864, 1899, 1912 and 1938.
- **Why:** the baseline changes `zzunit/u.go` in the same pathological base. `r.python` always runs `pb.load` and `candClosure`, which seeds from every candidate `.py` file (`internal/accept/integrity_pyreach.go:396-409`). So the baseline does the same base-wide work as the row. The rows also leave `maxWork` lowered (`:1862`, `:1897`, `:1910`, `:1936`) while the baseline runs. Unmutated ratios are 0.9 to 1.2.
- **Mutation:** I added 15 ms of uncounted work for each seeded file at `integrity_pyreach.go:403`.
- **Result:** `TestPyGuardImportTimeR3` still passes.

  | Row | Row time | Baseline time | Ratio | Bound |
  |---|---|---|---|---|
  | r5 M1, a deep directory walk | 30.93 s | 30.89 s | 1.0 | 20 |
  | r4 M2, the seeding | 13.45 s | 13.35 s | 1.0 | 20 |

  The old 20 s bound would have failed the deep-walk row.
- **Fix:** time the baseline on a separate plain fixture, built once per test, for example `newFixtureWith(t, …astra(nil)…)`. Never time it on the row's own fixture. Restore `maxWork` before the baseline runs.

### M1. The struct-chain row's baseline is not an ordinary run

### M2. "A go over time" contains fixed delays that do not scale with the baseline
- **Where:** `internal/accept/integrity_types_test.go:612`.
- **Why:** the row waits on fixed 200 ms lister timeouts. Measured: 869.8 ms, which is 17.1 runs of a 50.8 ms baseline against a bound of 60, so only 3.5 times of headroom. The other loader rows were 1.2 to 1.6. A fast host or a warm baseline makes this row fail wrongly.
- **Fix:** subtract the fixed delay, as the PR already does for `outSlotWait` and `maxListTime`. For example, give this row the bound `took ≤ n·unit + k·200ms`, with k at least the number of go calls the guard makes.

### M3. Each baseline is one sample, timed after the row
- **Where:** `internal/accept/integrity_test.go:114-118`.
- **Why:** the bound is n times one sample, so one stall in the baseline lifts the bound n-fold. For example, a 2 s stall in a 50 ms baseline raises a 40-run bound by about 80 s, and the row passes wrongly. The baseline also runs after the row, with the row's caches already warm, which biases it fast.
- **Calibration:** in `TestOutTypedBounded` (`internal/accept/integrity_out3_test.go:222`), making the slot wait 20 times longer gives 49.1 runs against a bound of 40. That is caught, but only just. A 10-times-longer wait would be about 21 runs and would pass (estimated, not run). The old 1 min bound caught neither, so this row is still stricter than before.
- **Fix:** take the median of 3 baseline runs, timed before the row.

### L1. A scan of every path for each new module is still in the guard (outside this PR's scope)
- **Where:** `internal/accept/integrity.go:213-214`. For each added `go.mod` it runs `slices.ContainsFunc(slices.Collect(maps.Keys(r.files)), …)`.
- **Evidence:** with 1,000 modules and 20,000 other paths, removing this scan cut the run from 6.54 s to 4.87 s. `TestIntegrityDoS` does not catch it.
