### High — Declared command inputs are not an enforced dependency boundary

**Location:** [docs/design/m0/07-project-profile.md:78](/tmp/claude-1000/-home-mega/d7e41cde-3883-4e5c-8d98-04b890c5f4c4/scratchpad/wt-b2/docs/design/m0/07-project-profile.md:78), lines 105–109.

### High — Profile adoption can disable or replace the check without the configuration answer

**Location:** [docs/design/m0/07-project-profile.md:126](/tmp/claude-1000/-home-mega/d7e41cde-3883-4e5c-8d98-04b890c5f4c4/scratchpad/wt-b2/docs/design/m0/07-project-profile.md:126), lines 105–121; `04-authority.md:55–101`.

Calling this “a profile change” does not establish operator authorization. `04` does not explicitly include `required_config` in effective-change classification; an otherwise unclassified `profile.adopt` under a supervisor grant defaults to confirmation `none`. Switching to `source: none` while retaining existing protected-path entries can therefore disable the comparison without removing a protected path.

There is also no explicit ordering rule for a merge accompanied by profile adoption. For example, a candidate introduces configuration and changes an adopted `none` mechanism to a declaration listing it. Checking only the old mechanism skips the question; adopting the new mechanism after merge is too late. Recomputing on profile change does not specify how this transition must gate that merge.

A protected-document edit alone cannot implicitly adopt a profile under `07:13–14`; that protection is sound. The gap is the separately authorized adoption path, including when no independent-review confirmation is required.

**Fix:** Explicitly classify disabling, replacing or weakening `required_config` as protection weakening. Require any accompanying mechanism transition to be evaluated before merge under the current authority, with an operator answer bound to the transition and resulting key obligations. Protected-document/profile approvals must not substitute for that answer. Make configuration-integrity assessment mandatory on these paths regardless of their ordinary confirmation policy.

### High — Protecting the named path does not establish the static-file boundary

**Location:** `docs/design/m0/07-project-profile.md:101–109,113`

The contract does not require a regular Git blob or define consistent path resolution for reading and protection. Consider an already-adopted `required.json` symlink to an unprotected `data/keys.json`. A builder changes only the target from `["OLD"]` to `[]`. A reader following the symlink accepts the new list, while Git’s changed-path list contains no protected-path edit. There are no added keys or newly introduced configuration reads, so neither readiness nor the completeness-review obligation necessarily catches the missing integrity approval.

Case-insensitive filesystem lookup creates the same mismatch when the adopted/protected spelling differs from the tracked filename. The existing protection matcher uses literal, case-sensitive path segments (`internal/profile/glob.go:89–93`). Neither 04’s protected-document operation nor commit-time revalidation repairs a discrepancy between the protected object and the object read.

This requires ordinary repository access, not elevated privileges. It is a contract gap; the gate implementation is deferred.

**Fix:** Define the declaration as an exact, repository-relative path to a regular blob in each pinned Git tree. Read those immutable bytes directly; reject symlink entries/components and unsupported entry types. Use the identical path identity for protection and comparison, without filesystem case folding; reject ambiguous materialization if working-tree reads are supported. Add target-only symlink edits and case-alias/collision fixtures asserting refusal or an unavoidable operator question.

### Medium — First introduction cannot recover from the missing-base hold

**Location:** `docs/design/m0/07-project-profile.md:106–108,128–129`

When the declaration first appears in the candidate, applying the adopted mechanism to both trees finds it missing in the pinned base. The check must return `could_not_run`. Recomputing the same candidate in another generation does not supply that baseline, and an integrity/readiness answer cannot resolve an unreadable-input hold. Thus the advertised declaration-addition path lacks a completion rule.

**Fix:** Specify a bootstrap procedure: either require an explicit empty declaration to land before enabling the mechanism, or define a narrowly authorized absent-base initialization that treats every candidate key as added and requires integrity plus readiness approval. Preserve fail-closed behavior for unexpected absence. Add a fixture demonstrating completion through the chosen procedure.

### Medium — Wrong-shaped JSON lacks an explicit negative fixture

**Location:** `docs/design/m0/11-testing.md:173–184`; `docs/design/m0/07-project-profile.md:76,128`

The declared format already excludes `null`, objects, scalar strings and arrays containing non-strings, so these are not valid empty declarations. However, “unreadable” alone does not exercise this distinction: syntactically valid JSON can decode successfully without satisfying the required shape.

**Fix:** Explicitly require shape validation and add cases for `null`, `{}`, `"KEY"` and `["KEY", null]`. Each must produce `could_not_run` and keep merge blocked; only a valid string array may reach comparison.

**Only the High path-resolution finding blocks.** Under development-workflow §2, this third NO-GO triggers the split rule. No files were modified.
