### Low

**L1. The start and `adc dev rebuild-projections` disagree about an unknown `_built` row.**
- **Where:** `internal/eventstore/build.go:125` makes the row a difference. `internal/eventstore/rebuild.go:92` (`compareLive`) leaves all `_built` rows out.
- **Input:** a started store, then `INSERT INTO proj_kv VALUES ('_built','zzz','{"version":1}')`. The start refuses with "the persisted projections differ from a replay", but `RebuildProjections` returns 0 differences. An operator following the refusal sees nothing.
- **Fix (one of):**
  - have `RebuildProjections` also report `_built` keys that are not valid projection names, or no longer fold-backed;
  - or give the start refusal its own detail, e.g. "the record of built projections names a projection this build does not fold".

**L2. The scanner only sees `*Projection`-named string constants under `internal/`.**
- **Where:** `internal/daemon/startup_test.go:407`.
- **Input:** a future projection declared as `const zzIndex = "zz_index"`, or as a `var`, is not seen. My probe confirmed it passes unnoticed.
- **Why Low:** it fails closed at runtime. The unregistered projection is compared, never built, and main's refusal comes back.
- **Fix:** add a line to the `addedSinceRecord` comment: "declare every projection name as a `const …Projection` string".

### Note (not a finding)

The scanner forces registration of any declared constant, even one whose projector is not wired yet. A store would then record it as built while it is still empty. When a later PR wires it over existing events, the store is refused. That is main's behaviour, so it fails closed, but the build-at-start benefit is lost for such a projection. It is worth a sentence next to `addedSinceRecord`.
