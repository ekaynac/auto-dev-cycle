### 2. Is (c) sound?
`listVerdict` evaluates every listing of the run at its end, so the order of listings does not matter. I probed it with shaped listings:
- the candidate refused after the base succeeded on the same platform: a refusal;
- the base succeeded only on another platform: the host's;
- no base listing: the host's;
- the base refused too: the host's;
- the candidate refused, then the base succeeded: a refusal (order-free);
- a refusal plus a host failure on another platform: **the host wins**, because `converse` checks `listHost` first.

Platforms are compared exactly. Listings are per guard run, since `service` is made anew each run, so there is no mixing across runs. The base flag comes from `typer.need` (`ty.t == ty.r.trees[0]`), not from the child's say. It is carried in the frame, and `TestProcWire` passes.

**Can a candidate make the base's listing fail? Yes, by one route.** Every listing in a run shares one copy budget (`maxRunCopy`, the run's ledger), and `r.pkg` lists per directory, base then candidate. So the candidate's listing for directory 1 (heavy new imports) can use up the budget, and directory 2's **base** listing is then refused ("over the guard run's export data bound"). Probe: the shaped listings give `host=ErrGuardRun`, no refusal. The effect is `could_not_run`, five accept retries (no builder cost), then `runner: failed`: bounded, visible, fail closed, never an acceptance. That is acceptable under entry 170, but it is not stated (L1).
