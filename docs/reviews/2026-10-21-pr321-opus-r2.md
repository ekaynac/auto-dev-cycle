### Medium

**M1. #321 conflicts with current main, and `KeysAtMost` re-implements a helper main already has.** (`internal/eventstore/writer.go:297`)
- **What main has:** since #333, main has `(*Tx).keys(projection, prefix, limit)` and `prefixEnd` (main `internal/eventstore/writer.go:323-363`). They do the same range query with `LIMIT`, and also count `projectionRows`.
- **What the PR adds:** `KeysAtMost` re-derives the range end, a second copy of that logic. Its `projectionRows` count would also be missing after a rebase.
- **Why it matters:** none of the race tests and mutation results above have run against current main.
- **Input:** `gh pr view 321 --json mergeable` returns `CONFLICTING`. The PR and main both change `writer.go` and `01-invariant-inventory.md` since base `c6fe593`, and both add a projection constant beside `TaskProjection` in `events.go`.
- **Fix:** rebase on main and make `KeysAtMost` a one-line wrapper, `return t.keys(projection, prefix, n)`, keeping the `n < 0` refusal. Then re-run the race tests, the mutations and `make ci`. The PR body also says "`KeysAtMost` is kept because it adds the `LIMIT`"; main's `keys` already takes a limit, so correct that line.

**M2. The declassification grant checks the layout of the bytes, not their content, and the receipt is granted with no read at all.** (`internal/gate/receipt.go:256-276`; `internal/intent/intent.go:186-187`)
- **The report:** `CheckReport` checks the keys, the order, the schema and the id lengths. It leaves `tree`, `reason`, `detail` and `outcome` unchecked, up to the 1 MiB read bound.
- **The receipt:** the verifier returns `true` for any `Sanitised` receipt-typed ref without reading it. Its only check is `readReceipt`, run in `recordResult`, which is schema validity only. A predicate's `detail` there is free text.
- **Input (probe through the production write path, `g.complete`, `graph.Commit`, then `recordResult`):** a gate result `[receipt, report]` whose refs both derive from the acceptance (lineage `alias-1`):
  - The report is report-shaped, 480 KB, with `tree`, `reason` and `detail` set to `hidden_test.py:12: assert refund(-5) == 'CANARY-7f3a'…`. `CheckReport` returns `<nil>`.
  - The receipt's predicate detail is the same canary.
  - `intent.Reviewer` takes both and returns `<nil>`.
- **Who can produce this:** only a controller that publishes such bytes. That is the same threat class as Astra's H1: a wrong attachment from a wiring bug.
- **Fix:**
  - **In `CheckReport`:**
    - require `outcome` to be a `vocab.Outcome`, `reason` a known reason code, and `tree` a hex git id;
    - bound `detail` (e.g. ≤ 1024 bytes, `v.Why`'s phrases);
    - require `elapsed_ms ≥ 0`, `tests ≥ 0` and `truncated ≥ 0`.
  - **In the verifier, for a `Sanitised` receipt:**
    - read the receipt and decode it strictly as `records/receipt`;
    - require kind `gate`, `rcpt.ID == rec.ID` and a matching digest;
    - require each predicate detail to be within the same bound.
  - **Add a row and a mutation for each** (report free text; receipt unread).
  - **The residual line:** the body's "a `Sanitised` receipt is honoured on its result's shape" should become this check, or say clearly that it is not one.
