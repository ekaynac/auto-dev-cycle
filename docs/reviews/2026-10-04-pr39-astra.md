# PR #39 (event store writer): Astra reviews

## Review of #39 (Astra, 2026-10-04)

Verdict: NO-GO

**High**

1. **The hook interface cannot implement the promised transaction boundary.**  
   `internal/eventstore/writer.go:46` — `Tx` exposes only `SubjectVersion`; its database transaction is private. An authorizer in `internal/authority` cannot read current projections, and reservation/projector hooks cannot write through the writer transaction. Separate connections cannot provide the required atomic writes or visibility of uncommitted changes.

   **Fix:** expose transaction-bound query/write operations or suitable typed repositories, keeping commit/rollback owned by `Submit`. Add an external-package integration test demonstrating projection reads, reservation/projection writes, and their rollback after a later failure. This is the blocking finding.

**Medium**

2. **Expected state is excluded from the input digest.**  
   `internal/eventstore/writer.go:92` — `Expected` independently controls execution, but only `Input` is hashed. Reproduced: changing `Expected` from version 0 to 1 while retaining the actor, key and JSON returns the previous success instead of `idempotency_key_reused`. Nothing enforces consistency between the structured expectations and any expectations encoded in `Input`.

   **Fix:** include expectations in the canonical request digest, or derive them from the digested input and reject inconsistencies. Test changed subjects and versions under an existing key.

3. **A projector can corrupt the command’s persisted event range by reordering its input.**  
   `internal/eventstore/writer.go:162,169` — `Project` receives the same mutable slice subsequently used to derive `first_seq` and `last_seq`. A hook swapping two events produced a committed command reporting `2..1`, although its actual events were `1..2`; replay preserved that incorrect range.

   **Fix:** capture the authoritative range before invoking `Project`. Add a regression with a projector that reorders its event slice.

4. **Missing authorization configuration overrides idempotency lookup.**  
   `internal/eventstore/writer.go:96` — The nil-authorizer check precedes the transaction and replay lookup. Reproduced: accept a command, reopen without an authorizer, and retry; the stored result is refused. This breaks note 03’s idempotency-first ordering, although new commands correctly fail closed.

   **Fix:** move the nil-authorizer refusal inside the transaction, after replay/key-reuse handling and before authorization. Test reopening without an authorizer: accepted requests replay, changed inputs report key reuse, and new requests remain refused.

**Verification**

`make ci` and the sandboxed event-store race suite passed; local CI skipped unavailable ShellCheck. Additional isolated probes under `-race` confirmed:

- Same-key races: one application; matching inputs replay and differing inputs receive key-reuse errors.
- Expected-state conflicts: exactly one application.
- Transactional hook writes and events roll back on downstream failures, command-row conflicts, cancellation and panic; the key remains reusable.
- Command UPDATE, DELETE, replacement through either unique key, UPSERT and rowid replacement attempts are refused.

The checkout remains unchanged.
### Lead notes on round 1

- H1: `Tx` exposes `QueryRow` and `Query` (any read) and `Exec` (writes) on the writer transaction itself; commit
  and rollback stay with Submit. Exec accepts exactly one statement that creates, inserts into, updates or deletes
  from a `proj_*` table, so hooks cannot reach the log, the commands or meta (events are appended only through the
  checked path). An external-package test shows an authorizer reading a projection, reservation and projection
  writes, and their rollback after a later failure.
- M2: the idempotency digest covers the request: the input and the expectations together.
- M3: the event range is captured before Project runs, and Project gets a copy of the events.
- M4: the missing-authorizer refusal sits inside the transaction after the idempotency lookup: a stored result
  replays and a changed input is key reuse even without an authorizer; new commands stay refused.
- Regressions for each; the new checks are mutation-tested (the input-validity check was redundant with request
  marshalling and was removed).
