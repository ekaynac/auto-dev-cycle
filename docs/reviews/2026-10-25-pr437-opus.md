### 1. Can `gate.In.Acceptance` and the overlay disagree? No
- **One production caller.** `gate.Run` is called only from `gateNode` (`internal/daemon/gate.go:186`). No fixture, `adc dev` command or other package calls `gate.Run` or builds a `gate.In`.
- **One source for both.** `overlay` and `hidden` come from the same `overlayOf` call, over the same map, in that run: `tests, err = gate.AcceptanceTests(pl, overlay)` (`:365`), assigned together at `:185`. Nothing is cached across runs.
- **Restarts, repairs and holds recompute both.** A restart rediscovers the claimed gate. A repair round's gate is a new node under the same task, and a gate re-placed after a hold is a new run. Each calls `gating`, which re-reads the persisted acceptance, and then `overlayOf`. Neither value can be stale.
- **Same platform as before.** `overlayOf` computes the list with `pl` from the profile's one environment, where `gate.Run` used the image's. `gate.Run` still refuses an image whose platform differs from the environment's (`ErrSpec`).
- **A non-`go_test_json` gate** (no list) is refused by `gate.Measure` first (`ErrSpec`), as before.
- **The backstop is right.** `gate.Run` refuses an overlay given no list (`errNoTest`, `internal/gate/gate.go:218`), mapped to `errContent` → `runner: failed`.
- **No false pass:**
  - a list naming a test the overlay does not declare makes the candidate fail (`found/gate_test_failed`), and the new gate row pins this;
  - a list missing a test the overlay declares would leave that test unexpected. It still counts if it fails (`judge`: Fail or Skip in any package), but it would pass vacuously if never reported. No production path can build such a list, since both come from one call.
  - `gate.Run` no longer checks itself what `go test` never runs. `In.Acceptance`'s comment states that the caller does, and the only caller does.

### 2. The bound
- **It covers every input to `doc.Examples`.** `doc.Examples` is called only on active test files, after the `!g.test` skip. The count (`internal/gate/acceptance.go:177`) runs on that same file first. Methods count, and `init` counts. Non-test files never reach `doc.Examples`.
- **Is 1000 sound?** Yes as a policy. It refuses only machine-made acceptances (go-mini's hidden file has four functions). The refusal is the task's (`errContent` → `runner: failed`; the acceptance is immutable, so recovery is a new task). Its text is fixed ("a Go test file of it declares more than 1000 functions"), and it is stated in both the plan and `acceptance.go`.
- **The remaining worst case** is larger than the PR's 0.33 s figure (L1). Within the bound, `doc.Examples` still scales with examples × all other declarations and comments in the file, which `MaxFuncs` does not count. Measured, 999 examples plus 1 MiB of filler:

  | package | filler | time per file |
  |---|---|---|
  | internal | any | 26–85 ms |
  | external `_test` | `var` declarations | 1.65 s |
  | external `_test` | `type` declarations | 1.40 s |
  | external `_test` | comment groups | 1.07 s |

  Fifteen such files (within `MaxOverlay`): 20.8 s (`var`), 18.8 s (comments).

  Computed once per run, this is about 20 s of one core where it was about 4–5 min. It is bounded, and only the operator can author it.

### OBLIGATION

**L1 (Low). The PR's measure (0.33 s for 15 000 examples) is not the worst case within the bound.**
- **Measured worst:** an external-package test file with 999 examples and about 1 MiB of other declarations or comment groups costs 1–1.7 s. Fifteen such files cost about 20 s, once per gate run, with no deadline.
- **Fix:** state the measured worst case beside `MaxFuncs` in `acceptance.go`. Alternatively, count every top-level declaration (`len(f.Decls)`) and the comment groups against the bound. With all three at 1000, the worst case is milliseconds.
