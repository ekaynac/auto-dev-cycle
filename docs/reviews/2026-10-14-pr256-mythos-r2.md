## External review of #256, round 2 (Mythos, 2026-10-14)

Verdict: GO with changes

Reviewed 1be5a99 read-only, against `docs/reviews/2026-10-14-pr256-astra.md`, `git diff b0b4e48 1be5a99`, and the PR's "Round 3" section. No tests run. No Critical or High finding. One Medium should land before merge because the fix is two lines.

### Judgements

**H1 is closed.** Every accounting field is now read by exact key from `map[string]json.RawMessage` (`object`, `count.go:106`), and every failure to read keeps the floor, which never settles. I looked for a response the gateway reads *successfully* with less content than the adapter (`adapters/http-chat/src/adapter.ts:222-229`, `JSON.parse` on `Buffer.toString("utf8")`), and found none:

- Duplicate keys, identical case: Go's map decode and JavaScript `JSON.parse` both keep the last value.
- Unicode-escaped key names (`"\u0063hoices"`): both parsers decode escapes before key comparison. An escaped case variant decodes to `Choices` and is refused by the fold check.
- BOM: Go `json.Valid` is false, Node `Buffer.toString` keeps the BOM and `JSON.parse` throws. Gateway falls to the stream path, finds no `data:` line, keeps the floor.
- Trailing data after the object, NaN, floats, `1e3`, numbers past int64: Go fails, floor stands. The adapter either throws or reads a number the gateway would not; both directions are conservative.
- `n>1`: the gateway sums content over all choices; the adapter reads `choices[0]` only. Gateway ≥ adapter.
- `choices` as an object with key `"0"`: the adapter reads it as `choices[0]`; the gateway cannot decode it as a slice and keeps the floor.
- Nested `choices` in unexpected places: the adapter reads top-level only.

**H2 is closed except for one spec corner (M1 below).** `event:`, `id:`, `retry:` and comment lines are ignored as the spec says. `data` without a colon is an empty value, per spec. Data lines are joined with LF, one leading space stripped, CR/LF/CRLF handled, a CR split from its LF across writes handled (`count.go:212`). An event cut at EOF is read rather than discarded as the spec says, which only adds usage or content and is the right call for an upstream that closes without the trailing blank line. `incomplete` is permanent and `[DONE]` is the only event exempt from parsing.

**M1 is closed, and nothing breaks.** `redactable` (`gateway.go:195`) refuses backslash, any rune above 0x7e (so DEL and all non-ASCII, including invalid UTF-8 which ranges as U+FFFD). `Holds` returns an error naming the reference only; `dispatch/launch.go:77` records that error as not-ready, no crash, no value. The only `Secrets` implementation is `EnvSecrets`; the registry binds a reference to an origin and never sees the value. Real provider keys (`sk-`, `sk-ant-`, AWS, OpenRouter) are ASCII without backslash.

**No regression in round-2 work.** The only matcher change removes the `c == '\\'` branch, now unreachable. `count` still commits only when `result` is ok, the dial-failure zero and `count_unrecorded` paths are untouched, and `contentType` is untouched. I also checked whether Go's transport could retry a POST after writing it and then surface a dial error: it cannot, since a POST without `Idempotency-Key` is not replayable and the `nothingWrittenError` retry is by definition unsent.

**The "under-validated floor" argument holds.** `Reconcile` (`ledger.go`) replaces a floor only with a `gateway_count` at the same sequence and sets `Floored` otherwise; `trusted` refuses to settle a floored call; `owed` (`liability.go:211`) charges `max(reservation, measured)` where `measured` already includes the count. A tiny `max_tokens` therefore lowers one addend inside a max whose other term is the reservation. Once usage is read, `Out = max(completion_tokens, content/16)` and `max_tokens` plays no part.

**S1–S13 discriminate** by inspection: each mutation flips a case whose expected result is "no count after the floor" or a specific count. Gaps are listed under Low.

### Findings

**Medium**

- **M1. A leading UTF-8 BOM hides the first stream event.** `internal/gateway/count.go:229-233`. The SSE spec strips one leading BOM from the stream; a compliant streaming reader sees `\xEF\xBB\xBFdata: {...content...}` as a data line. `line` cuts the field as `\xEF\xBB\xBFdata`, which is neither `data` nor empty, so the event is dropped silently without setting `incomplete`. A later `data: {"usage":{...,"completion_tokens":0}}` then commits an observed count with that content uncounted. Same class as Astra's H2 but narrower: only the first line, and only for a hostile adapter that requests `stream: true` (the in-repo adapter sends `stream: false` and cannot read SSE), which is why this is not High. Fix: in `Write`, before the loop, on the first call only, `t.pending = bytes.TrimPrefix(t.pending, []byte("\xEF\xBB\xBF"))` guarded by a `started bool`. Add a fixture to `TestTheGatewayCountsWhatItSent`: Astra's H2 stream with a BOM prefix, expecting the 300/100 floor.

**Low**

- **L1. The case-variant refusal is now redundant.** `internal/gateway/count.go:111-115`. With exact-key reads, a `Choices` key is invisible to the gateway and to the JavaScript adapter alike; there is no differential left to refuse. It is a defence for a future adapter with a case-insensitive parser (Go struct decoding, .NET). Keep it if that adapter is foreseen, otherwise drop the loop and the `names` parameters (about 8 lines and 12 string literals).
- **L2. Dead map entry.** `internal/gateway/gateway.go:283`. `shortEscapes['\\']` can never match now that `redactable` refuses backslashes. Remove it, or leave a comment.
- **L3. Quadratic rescan on a body without line endings.** `internal/gateway/count.go:211`. `bytes.IndexAny(t.pending, ...)` scans from the start of `pending` on every write. An 8 MiB JSON body arriving in 32 KiB chunks scans about 1 GiB in total. Keep a `scanned` offset and search `t.pending[scanned:]`.
- **L4. Fixture gaps.** `internal/gateway/count_test.go`. (a) Deleting `count.go:269-270` (the unterminated final event) stays green; add a stream whose usage event has no trailing blank line, expecting an observed count. (b) The CR-split guard at `count.go:212` is untested; drive `tally.Write` byte by byte as `TestEveryJSONSpellingIsRedacted` does. (c) No BOM case (see M1). None of these gaps hides a charge reduction; they are the conservative direction.
- **L5. `floor` still decodes the request through a struct.** `internal/gateway/count.go:68-73`. Harmless, since `pinned` re-encodes exact allowed keys and a floor never settles, but it is the one reader left that does not follow the "read exactly" rule stated at `count.go:26`. Reading `max_tokens` through `object` would make the rule uniform at no extra length.

**Size.** 673 lines is fair for the fixes asked. The one real candidate for removal is structural, not local: the SSE tally (`count.go:194-275`, about 80 lines) and `stream`/`stream_options` in `allowed` exist for a streaming adapter M1 does not have. Refusing `stream` until P13 streams would delete the tally and M1 above with it. That is the lead's call; if the tally stays, apply M1.
