### High

**H1. A literal passed to a followed helper is counted even when the helper no longer calls it.** `internal/accept/integrity_cases.go:385-391`
- **Input:**
  - `func withFn(t *testing.T, f func()) { t.Log("with"); f() }`
  - `TestArgLit` calls `withFn(t, func() { t.Run("x", func(t *testing.T) { if Add(1, 1) != 2 { t.Fatal("x") } }) })`.
  - Replace `f()` in `withFn` with `_ = f`.
- **What happens:**
  - The literal is read in place because it is an argument of a followed helper. So `run x` is kept, although subtest `x` never runs again.
  - Main's count still includes the `t.Fatal` inside the literal, and the print does not change.
- **Probe result:** silent here and on main.
- **Why it is in scope:**
  - This is the nearest variant of H2, inside the promise "a function literal names cases only where it runs".
  - The "argument of a followed helper" rule came from the fix I suggested in round 1, and that suggestion was incomplete.
  - A multi-declaration helper has the same gap. Its digest identity exists only when it runs cases itself, so removing `f()` from one variant is also silent.
- **Fix:**
  - In `helperSum`, record which parameter indices the helper calls: by `f()`, `defer`/`go f()`, `t.Cleanup(f)` or `t.Run(_, f)`, outside dead branches.
  - For a multi-declaration helper, use the indices every declaration calls.
  - Read a literal argument in place only at those indices. Otherwise it is opaque and adds no cases.
  - Add this input as a row.
  - A helper that passes `f` on to another helper needs the same rule, applied transitively or treated as opaque.

### Medium

**M1. The case bound is per scan, so the total work grows with the number of packages a patch adds.** `internal/accept/integrity_cases.go:100-104`, `:161`, `:166-167`
- **The PR's claim is inaccurate.** It says the bound mirrors P14d-a, but #315's `maxSkipWork` is per run (`s.r.skipWork`) and scaled: `4 * len(platforms) * maxRead`.
- **Here,** `cs.work` restarts at 0 for each `pkgScan`, and there are up to 8 scans per directory (2 package names × 2 platforms × 2 versions). So total work is bounded only by `scans × 16 Mi`.
- **Measured:** a 47 KB package whose helper's 1,000 subtests are composed 1,000 times charges about 15.9M and takes 0.46 s.

| New packages | Charged work | Time |
|---|---|---|
| 1 | 15.9M | 0.46 s |
| 4 | 63.6M | 1.1 s |
| 8 (376 KB) | 127M | 2.1 s |

  - That is about 340 units of work per byte, and none of these hits a bound.
  - At `maxRead` (64 MiB of such files) I extrapolate about 10–20 minutes of CPU. The case code does not observe `listEnd`, only `ctx`.
- **Not a false block.** It is a regression in bounded work.
- **Fix:** match P14d-a. Use one per-run counter (`r.caseWork`) with a bound scaled to `maxRead`, for example `4 * len(platforms) * int(maxRead)`. The whole-tree replay (about 19M) stays far under it. Update the comment at `:100-103`.
