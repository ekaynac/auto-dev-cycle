### High

**H1 (BLOCKING). The gate's own `could_not_run` leaves the node claimed with no hold, so the gate re-runs with no end, and a candidate can trigger it.**
- How it happens:
  - `gate.Run` returns a verdict of `could_not_run/runner_fault` when it cannot read the candidate's results: no results file, a stream that does not parse, or a run that did not end on its own.
  - `gateNode` commits that verdict as the gate's result (`internal/daemon/gate.go:162`). A `could_not_run` result is never selected, and no hold is raised in that command. `graph.Commit` raises none; the reason's hold (`wrong_owner`) is only raised by `graph.Retry`.
  - The run returns nil, which nudges the loop. The gate node is still claimed, so it is decided again at once.
- **Probe:** the build rewrites `gate-events.json` to `not a stream`, and the base is green. Under `Loop.Run` for 4 s: **64 gate runs, 64 results recorded on the gate node**, node claimed, no holds.
- In production each run is two sandbox runs of up to 30 minutes, so the loop is slower than in the probe, but it never ends. It records a result, a receipt, a report and blobs each time.
- A builder can cause it by a test that calls `os.Exit` or kills its own process, or by making `go test -json` emit garbage.
- **Fix:** in the same command as a `could_not_run` gate result, raise a hold:
  - `graph.Retry` with the reason's `wrong_owner`, or
  - the runner's `holdOn`, a bounded retry ending in `runner: failed`.
  
  Add a row: an unreadable candidate stream gives one result and a hold, and no second run.

**H2 (BLOCKING). If the build's seal never lands, accept spins hot with no bound.**
- `errNotSealed` returns nil with no hold (`internal/daemon/accept.go:117`). That nil nudges the loop (`start`), and `Executor.Run` counts the action as applied (`ran++`, another nudge). So the loop re-decides Accept at once.
- That is harmless for the one-command window between the build's commit and its seal. But if the seal fails, the build's node is completed and its attempt stays `finishing`, and nothing seals it before 5c-2c. Examples: `SealMinimal`'s blob put fails on a full disk, or a store error.
- **Probe:** I skipped the seal step in a copy, which stands in for a failed seal command. Under `Loop.Run` for 2 s: **1,468 accept runs started**, node claimed, no holds.
- Each run opens a store view and reads the whole patch blob, up to 64 MiB, before the checkpoint check. That is a hot CPU and I/O loop, silent because nothing is logged, until the operator restarts adcd. A restart does not fix it either, because a `finishing` attempt is left for 5c-2c.
- **Fix:** have `Observe` decide Accept only when the input result's attempt has a checkpoint. Or treat `errNotSealed` as a short `runner: retry` hold, as a non-nil error that does not nudge. Also read the checkpoint before the patch. Add a row: an unsealed input gives no runs in N passes.

### Medium (OBLIGATION, for 5c-2c)

**M1. A clone blip or a late image pull now strands accept and gate for good.**
- `checkout` makes every clone and image failure `errConfig` (`accept.go:268`, `:272`). That holds the node `runner: profile <digest>`, which clears only when the profile's digest changes (`run.go:682`), and M1 has no profile change.
- So a network blip on the clone, or an image pulled after the first try, leaves the task stuck until its approval is revoked.
- Before this PR, `TestAnAcceptRetryClears` showed an image miss clearing. The row now uses a guard cut instead.
- **Fix:**
  - clear an image hold when the image resolves (`cleared` checks `Images.Resolve`);
  - for clones, keep URL refusals (`sandbox.ErrSpec`, `ErrRemoteMismatch`) as configuration, and send `ErrGit` network failures to the bounded retry.

**M2. A red base is classed as transient** (`gate.go:141`). It gets five retries, each re-measuring the base for up to 30 minutes, about 5 hours in all, before `runner: failed`. The base does not change, so no retry can help.
- **Fix:** hold a red base at once (`runner: failed`, or the `wrong_owner` the environment owner clears), with the measure's `Why` in the detail.
