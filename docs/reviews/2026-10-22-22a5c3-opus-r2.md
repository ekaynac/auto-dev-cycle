### 3. Is the deferred refusal fail-closed?
Yes. When the task's record makes no brief, or its project has no profile, the cause is recorded (`noBrief`, `noPolicy`). Any plan ref met afterwards is refused. Non-plan refs are not affected, which is right, since only a plan ref can claim to be the brief. ### 4. New findings

**Medium**

**M1. The stated remedy for a policy change, "a refusal that needs a re-plan" (body line 61 and the doc comment of `own.check`), does not exist, and would not work if it were added.**
- No M1 path claims a completed plan node again. `graph.Repair` makes new build and review nodes, not a plan. There is also no action that changes a project's profile.
- If a re-plan were added, the new brief would have the **same id**: the content digest does not depend on the policy. It would carry other restrictions. `graph.Records` now marks the same id with unequal restrictions as ambiguous (`internal/graph/records.go:114`). Both refs would then fail to resolve (`ErrAncestryUnresolved`) for good.
- It is reachable today through an upgrade. `brief.Restriction` computes the policy digest over `json.Marshal` of the Go struct (`internal/brief/brief.go:51`). A build that adds a field to `ProjectProfileDataPolicy` therefore changes the digest of an unchanged stored profile. Every planned task's build is then refused at its intent, and the admitted task occupies the single admission slot until its approval is revoked.
- **Fix:**
  - State the real recovery: revoke the approval, which abandons the task. Drop "re-plan".
  - Compute the digest from the recorded profile's `data_policy` bytes, canonicalised, not from the Go struct.
  - When re-plan lands, either put the policy digest into the brief's bytes, so a re-plan gets a new id, or leave restrictions out of the ambiguity rule for plan refs.

**Low**

**L1. A storage or decode error becomes an acceptance refusal.** `ownBrief` turns an error from `authority.ProjectProfile` into `noPolicy` (`internal/intent/intent.go:181`). A plan ref met afterwards is then refused as `ErrNotTheBrief`, which is an `ErrAcceptanceInput` (an outcome of failed), when it should be a `could_not_run` error.
- **Fix:** return a real read error from `Load`, and defer only "no adopted profile".

**L2. The scope is not checked.** I recorded the own brief with the own restriction but `scope.project` set to another project, and it was **accepted** (my probe). The bytes are the task's own and the restriction is the project's, so nothing leaks. But the ref names another project's scope, and a later consumer that keys on scope would misfile it.
- **Fix:** carry `Scope.Project` in `RefRecord` and require it to equal the task's project. Add a row.

**L3. The ambiguity check uses `reflect.DeepEqual`** (`internal/graph/records.go:114`). It tells nil destinations from `[]`, because `cloneRestrictions` keeps nil as nil. Today every recorded ref is decoded from JSON, and `intent.Load` has no production caller yet, so nothing is affected now. A controller extra ref built in Go, with nil destinations, would become ambiguous against its recorded twin, which reads `[]`.
- **Fix:** compare restrictions with `sameRestriction`'s rule (`slices.Equal` treats nil and empty as equal), applied element by element.
