# PR #50 (projection rebuild): review

## Review of #50 (Opus subagent, 2026-10-04)
Verdict: GO with changes

Reviewed commit 3b4cd10 (`internal/eventstore/rebuild.go`, `rebuild_test.go`) against `docs/design/m0/03-event-store.md` (lines 34-35 and rule 3, line 99). I found no Critical or High issues. The shadowing approach is correct with the driver as it is used here (modernc.org/sqlite v1.60.1, writer pool `SetMaxOpenConns(1)`, `_txlock=immediate`).

### What I checked and confirmed (from code and probes in a clean copy, `rv50/`)
- **Shadowing:** all four unqualified `Tx` statements (`Get`, `Put` upsert, `Delete`, `Keys`) resolve to `temp.proj_kv` inside the rebuild transaction. A throwaway probe projector that used all four ops, with batch sizes 512, 1 and 3, rebuilt with zero diffs. A `Submit` right after the rebuild projected into `main.proj_kv`, so neither the temp table nor a statement compiled against it outlived the transaction. modernc only reuses a statement inside one `database/sql` Stmt, and SQLite re-prepares a statement when the schema changes, so no statement cache carries the shadowing over.
- **Rollback drops the temp DDL:** a second `CREATE TEMP TABLE proj_kv` succeeds on every later rebuild. It succeeded after a projector error, after a projector panic (the deferred `Rollback` runs) and after a context cancel mid-replay. On a cancel, `database/sql` rolls back and throws away the connection itself.
- **No path to main or to commit:** the transaction is only ever rolled back. All writes go through the shadowed `Tx`, and `Tx.store` is nil, so `IntendEffect` cannot append (effects.go:76).
- **Concurrency:** 20 `Submit`s ran alongside 20 `RebuildProjections` under `-race`. All rebuilds returned zero diffs and none raced. `Close` during a slow rebuild waits for it (`s.do`), and the rebuild finishes cleanly. The single writer connection keeps the rebuild exclusive.
- **Replay:** every event is replayed in seq order, effect events included, with keyset paging (`seq > ? ORDER BY seq LIMIT ?`). The paging cannot skip or repeat an event.
- **Comparison:** it reports changed, missing-live and extra-live records, sorted by (projection, key). Taking `&v` / `&r` of loop variables is safe on go 1.27.
- **Mutants I ran myself:** committing, stopping after the first batch, skipping `Verify`, and dropping the last event of each batch all make the tests fail.
- **Test runs:** `go vet` is clean, `gofmt` is clean, and `go test -race` passes for every package that does not need the sandbox. `make ci` could not run in the copy because `check-spdx` needs git.

### Medium
1. **The chain that is verified is not necessarily the chain that is replayed (rule 3).** See `rebuild.go:35` and `rebuild.go:39-40`.
   - `Verify` reads through the reader pool (`s.r`) in its own `s.do`. The replay then reads `events` inside a separate writer transaction that starts later.
   - Anything appended or changed between the two snapshots is replayed without being verified. Appends through the store are hash-checked. The only real gap is an out-of-band edit of the database file, which is exactly what rule 3 guards against.
   - **Fix:** verify inside the writer transaction. Make `verify` take a `querier`; `effects.go` already defines one. Then verification and replay read the same snapshot.
   - **Cheaper alternative:** verify while replaying. Chain-check each row as it is read in `eventsAfter`'s batches, and check the meta/genesis rows in the same transaction. This also halves the I/O.

### Low
2. **Shadowing depends on name resolution, and nothing guards against a leaked temp table.** See `rebuild.go:62` and `writer.go:85-123`.
   - Today it is correct. But if anyone ever qualifies a `Tx` statement (for example `main.proj_kv`), or a schema-qualified trigger appears, the rebuild silently reads or writes the live table.
   - If a rollback ever fails without `ErrBadConn`, `database/sql` returns the connection to the pool. In that case the temp table could stay on the connection, and later live projection writes would land in it instead of the real table.
   - **Fix (preferred):** give `Tx` an unexported table name (`proj_kv` normally, `temp.proj_rebuild` for a rebuild). No resolution trick is needed then.
   - **Minimal fix:** if `tx.Rollback()` fails in `RebuildProjections`, discard the writer connection, for example via `s.w.Conn(ctx)` plus `Raw` returning `driver.ErrBadConn`. Also add a comment on `Tx`'s methods that every statement must stay unqualified.
3. **The tests cover only `Get` and `Put` under shadowing.** See `rebuild_test.go:18-41`.
   - If `Delete` or `Keys` were qualified to main, no test would fail.
   - **Fix:** extend `counting` with a `Delete` and a `Keys` (for example, keep a "latest subject" key and delete the previous one).
   - **Also:** assert that a `Submit` after a rebuild still changes the live rows. A temp table leaking across transactions shows up there directly, not only through the second `CREATE TEMP TABLE` failing.
4. **"Always rolled back" cannot be told apart from committing.** A mutant that drops `temp.proj_kv` and then commits passes all three tests. In practice it is harmless, because only temp is written. If the guarantee matters, assert it with a hook or by checking that `Tx` writes never touch main. Otherwise drop the claim from the mutation list in the PR description.
5. **The fold contract is documented in the wrong place.** The rule "a fold over events and projections, replayed one event at a time; do not depend on `SubjectVersion`" is only in `RebuildProjections`' doc comment (`rebuild.go:30-33`). Projector authors read `Hooks.Project` at `writer.go:156`. Put the contract there too.
6. **Live runs batch events; the rebuild does not.** `Submit` passes a command's events and intents as one slice (`writer.go:291`). The rebuild passes one event at a time. A projector that is not a fold shows up as drift, not as an error. This is the intended behaviour, but `adc dev rebuild-projections` should mention it when it reports drift, to save debugging time.
7. **Rebuild cost.**
   - The rebuild holds the writer lock (an IMMEDIATE transaction) for the whole replay, so every `Submit` waits.
   - Both projection sets are loaded fully into maps (`rebuild.go:69-76`). Only the event batches are bounded.
   - This is acceptable for a dev command in M0. Note it in the doc comment, or compare with a merge over two `ORDER BY projection, key` cursors.
8. **The effects table is never checked.** The effects table is also derived from the effect events, but the rebuild does not compare it. Note 03 limits projections to `proj_*`, so this is in scope as written. Consider a follow-up that checks `effects` against the effect events with the same diff shape.
9. **The rebuild batch size is a mutable package `var` (`rebuildBatch`, `rebuild.go:21`).** Tests change it without a lock, so it is not parallel-safe if a test ever calls `t.Parallel()`. This is fine as long as none does.

### Lead notes (applied before merge)

- Medium 1: the chain is verified inside the rebuild's own writer transaction (`verify` reads through a querier), so
  the log replayed is exactly the log verified.
- Low 2: the preferred fix. `Tx` names its projection table (`main.proj_kv`, or `temp.proj_rebuild` for a rebuild),
  from two constants, so nothing relies on shadowing; a leftover scratch table from a failed rollback is dropped
  before the next rebuild creates it, and live writes never touch it.
- Low 3: the test projector also uses `Keys` and `Delete`, and a `Submit` after a rebuild still reaches the live
  table (and rebuilds clean again).
- Low 4: with the scratch table connection-local and nothing else written, a commit instead of the rollback changes
  nothing durable: an equivalent mutant, noted in the PR; the rollback stays.
- Low 5: the fold contract is documented on `Hooks.Project`.
- Lows 6–9 (CLI wording on drift, the writer lock and memory for an M0 dev command, comparing the effects table,
  the package variable in tests) are left for the CLI step or noted; none changes behaviour today.
