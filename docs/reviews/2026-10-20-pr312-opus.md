### Answers to the brief
1. **Decide** is pure and deterministic.
   - `Runnable` comes in node-id order (`graph.Nodes`), and Decide clones it.
   - Admission is global FIFO by task id. The controller mints the id, a TypeID (UUIDv7); a request cannot choose it.
   - A cancelled task (state) or an unapproved one (status) is never chosen. `admissible` excludes it in `NextAdmission`, `AdmitTask` checks again in its own command, and the fold `admitTask` checks a third time.
   - Nothing starves: the Ready backlog is bounded, and the oldest admissible task always wins.
2. **Commands:**
   - Each action expects the versions its snapshot read, and checks again in its own transaction (`AdmitTask`, `AbandonTask`/`endable`, `evaluate`'s admitted-task and `Claimable` checks).
   - A stale snapshot cannot cause a wrong abandonment: an approval never goes from `revoked` back to `in_force`; those are the only two statuses.
   - An abandoned task is Done, never Ready again, so the loop cannot abandon and re-admit it.
   - Abandonment while an attempt runs: see M3.
3. **The loop:**
   - Shutdown is right: `<-reconciled` (`internal/daemon/daemon.go:248`) comes before `srv.close()` and `d.Close()`.
   - `Nudge` never blocks: a buffer of 1 with a `default` case. A nudge that arrives during a pass is kept.
   - A panic in a pass: see M2. An error storm: see L5.
4. **Authority:**
   - The actions are in `systemActions` and pass through `authorizeSystem` (the actor must be a system actor) and `identity.Recheck`.
   - They are not registered, so the HTTP command path refuses them.
   - `d.system` is the principal.
5. **Behaviour change:**
   - `TestIntake` and `installed-smoke.sh` still exercise cancel, on the second task.
   - Only `TestIntake` creates tasks against a running adcd. The other callers of `Run` (https, bootstrap, socket, commands, daemon tests and `internal/cli/bootstrap_test.go`) create none, so the loop appends nothing there.
   - The `seeder`-based tests run no loop.
   - The smoke's final check needs `adcd: stopped` as the last log line, and the loop stops before that line is written.
6. **Mutations and #309:**
   - The 12 rows cover the PR's promises.
   - The stated gap (the commands' nudge) is real, and the self-nudge and the shutdown wait are also unmutated (L2).
   - #309's L5 is addressed in the loop's own check (`Claimable` before `graph.Evaluate`). #309's M3 is addressed for the revocation case.

### Medium

**M1. A command that changes nothing counts as applied, and the loop nudges itself into a hot loop of empty commands.**
- Where: `internal/reconcile/reconcile.go:205-210`, `:286-289` and `:263-264`.
- `Applies` with zero events commits an applied command: the commands row is written (`internal/eventstore/writer.go:607`) and `Applied()` succeeds. `Pass` then counts `ran++`, and `Run` calls `Nudge()`. The next snapshot is the same, so the same action runs again with no pause, writing one commands row each time.
- Input (once evaluation is on): a runnable goal that `graph.Evaluate` leaves alone. Examples:
  - a stale answer (`internal/graph/evaluate.go:201-202`);
  - a missing input that is not an answer (`:208-209`, where `await` does `continue`);
  - the key holder still running (`:294-295`).
- [INFERENCE] I did not build such a goal on the candidate template. Nothing guarantees that every runnable goal emits an event, and the loop's liveness depends on it.
- Fix: in `Executor.Run`, when the logic returns no events, return a sentinel such as `errNothing` so nothing commits. `Pass` should treat it like stale: not counted, not logged. Alternatively, count `ran` only when `Outcome.LastSeq != 0`. Add a row: a pass whose Evaluate yields nothing returns `ran 0`, and the head and the commands table do not change.

**M2. A panic in a pass kills adcd, and the pass at start makes it crash-loop.**
- Where: `internal/reconcile/reconcile.go:257-296`; `internal/daemon/daemon.go:240`.
- Nothing recovers a panic in the loop's goroutine. Any panic in `Observe`, `AdmitTask`/`graph.Candidate`/`RecordTemplate` or `graph.Evaluate` (for example the unchecked type assertion at `internal/graph/resolve.go:71`) ends the process.
- On restart, the first pass reads the same state and panics again. adcd never stays up, so the operator cannot cancel or revoke over the API to get out of it. By contrast, the same panic in a command handler only costs one 500, because `net/http` recovers it.
- Fix: recover per action in `Pass`, log the action and the panic, return it as an error, and skip the self-nudge, so the timer paces retries. If fail-fast is the intended policy, record that decision and make the start pass skip the action that panicked.

**M3. Abandonment uses "no live lease" for "no attempt runs", and the two differ once launch exists.**
- Where: `internal/authority/admit.go:177` through `internal/lease/wiring.go:187-188` (#309's code, which this PR's Abandon relies on).
- `LiveOn` counts only requested, waiting, granted and active leases. It ignores releasing, settling, restoring, restore_failed and settling_verified.
- Input (P22a-5): an attempt is active; the operator is revoked; the lease is revoked or expires (active → settling, `internal/lease/lease.go:70-72`) while the attempt is still stopping and unsealed, or an evidence restore is running. The next pass's `AbandonTask` passes. The task is Done(abandoned), the slot frees, and the next task is admitted while the old attempt is still running.
- #226 entry 100 requires "once no attempt of the task runs". This cannot happen today, because no attempt can start.
- Fix (a P22a-5 obligation; record it in the inventory): in `endable`, refuse abandonment while any lease on the task's units is not `settled` or `released`, or while any of its attempts is not sealed.

### Low

**L2. Untested wiring.**

**L3. Shutdown logs a refusal.**
- Where: `internal/reconcile/reconcile.go:291-292`.
- Input: SIGTERM while an action is in `SubmitApplied`. `Pass` logs `reconcile.admit refused: context canceled`, while `Run` stays quiet about errors after the context ends.
- Fix: skip the log when `ctx.Err() != nil`.

**L4. Admission is not tied to the `admission` capability.**
- Where: `internal/daemon/wiring.go:65-73`.
- The comment says the loop "admits under the admission capability's command", but only `launch` gates anything. If `admission` ever gained a `Pending`, the loop would still admit.
- Fix: pass `capability.Of("admission").Active()` into the loop, and have Decide skip Admit when it is false.

**L5. No backoff, and `adcd`'s Env is not ready for evaluation.**
- Where: `internal/reconcile/reconcile.go:257-273`; `internal/daemon/wiring.go:71`.
- A persistent refusal logs one line every 5 s plus one per applied command. For example, if launch is activated with `adcd`'s `graph.Env` still lacking `Need`, `internal/graph/resolve.go:64-65` refuses every Evaluate.
- This is acceptable for M1.
- Fix: log a repeated identical refusal once until it changes. Record "Env.Need and Blobs before `launch.Active()`" as a P22a-5 check.
