## Opus pre-review of #295 (2026-10-20)

Verdict: GO with changes

I found nothing Critical or High and no regression against main. The three counts come from records that an invalidation never rewrites:
- **Attempts:** the unit's fencing token. The `attempt.started` fold enforces token-1-then-+1 per unit.
- **Rounds:** `Round`. The fold enforces predecessor+1.
- **Merge operations:** the earlier keys, rebuilt from the claim's fixed `Inputs`. `invalidated` keeps `c.Inputs` and bumps only `Generation`. `effectRequest` takes every other field from the inputs and params, so the rebuilt request matches each earlier one byte for byte.

Each hold is re-checked on its next try (evaluator, `Launch`, `Operate`), so a hold cleared without a raise is put back. `go test -count=1 -race` passes in a copy for `internal/{graph,authority,dispatch,vocab,cli}`, `schemas` and the affected caller `internal/fixtures`. Two mutations the PR does not list survive (Medium 1 and 3). Two of the listed ones, R1 and R2, were re-applied and are caught.

### Medium

1. **`authority.Rails` reading the profile is untested.** `internal/authority/rails.go:55`, with the test at `internal/authority/rails_test.go:52,68`.
   - **Input:** replace `caps := graph.CapsOf(profile.Budget.Rails)` with `caps := graph.DefaultCaps`. `TestTaskRaiseRail` still passes (I ran it).
   - **Why it survives:** the fixture profile sets 3/5/2, which are also the defaults, so the test cannot tell the profile's values from the defaults. R8 is caught only inside `CapsOf` (`TestCapsOf`), not where the authority reads it.
   - **Fix:** give the test a profile whose caps differ from the defaults (for example 2/3/2, see item 2). Assert them, and keep the "to the profile's cap" case at that value.

2. **`py-mini`'s count rails contradict the slice plan's stub benchmark.** `fixtures/m1/profiles/py-mini.json:42` against `docs/design/m1/00-slice-plan.md:465,469,472`.
   - **Input:** the plan says "The rails are P17's: 2 attempts per round, 3 rounds per task, and 2 merge operations per generation". Its cases expect `fault-lying-runner` to hold after round 3 and `fault-provider-4xx` to hold after 2 attempts.
   - **What happens:** with this PR's `py-mini` (3/5/2), the first holds only after round 5 and the second only after 3 attempts.
   - **Fix:** set `py-mini` to 2/3/2. The operator's 3/5/2 stays the default for profiles that name none. Or amend lines 465, 469 and 472 if the operator meant 3/5/2 for the benchmark too. Doing the first also closes item 1.

### Low

4. **A rail is enforced only by the commands that check it.** The folds do not enforce it, and the exported building blocks below skip it:
   - `graph.Claim` (`internal/graph/events.go:256`) claims a build of any round;
   - `lease.StartNext` and `lease.SupersedeAttempt` (`internal/lease/wiring.go:239,285`) start an attempt past the rail;
   - the `hold_cleared` fold (`internal/graph/holds.go:289-292`) lets any command clear a `budget_rail` hold by its `rail:<name>` signal, with no raise.

   Today only fixtures call the first two, and the re-checks put a cleared hold back. **Fix:** record in I16's consumption row, as a P22a obligation, that builds are claimed only through `Evaluate`, attempts start only through `dispatch.Launch`, and merges operate only through `Operate`. Alternatively, have `Claim` take `Rails`.

5. **Replacing a review restarts its attempt count.**
   - **Input:** a review with 2 attempts against a cap of 3 is superseded after a roster change (`internal/graph/supersede.go:385`, `replaces` keeps `Round`). Its replacement has a fresh unit, and `attemptRail` reads only that unit (`internal/dispatch/launch.go:194-213`), so the same round can take 3 more attempts.
   - **Limit:** each replacement needs a different roster. A `budget_rail` hold already in place does transfer (`holdsFor`).
   - **Fix:** add up the tokens along the `Replaces` chain, or list this in the PR's Residual section.

6. **The hold registry describes the old signal.** `schemas/vocab/holds.yaml:62-63` still says `signal: approval`, "An approval raising the rail". The raise now records `task.rail_raised/v1` and clears on `rail:<name>`. **Fix:** update `signal_detail` to name `task.raise_rail` and the `rail:<name>` signal instance.

7. **A literal string instead of the vocab constant.** `"budget_rail"` appears at `internal/graph/rails.go:90,103,152`, where `vocab.HoldBudgetRail` exists (`internal/vocab/vocab.gen.go:164`). **Fix:** use the constant.

### Checked, no finding
- **Holds:**
  - the round rail is checked before the claim, and a held node gets no second hold (`clear` reports it held first);
  - the merge rail is checked after a resumed operation of the current key returns early, so a crash between intent and effect counts once;
  - a refused launch or a lease released before start starts no attempt and does not move the token;
  - `invalidated` carries a `budget_rail` hold over, because it retires only retry waits.
- **`task.raise_rail`:**
  - the derivation refuses anyone but the operator (`operator_only`);
  - the logic requires a value above the cap in force, which is the larger of the profile's and the last raise;
  - the fold requires a recorded task, a matching subject, project, actor and time, a live operator, and a value above the last raise;
  - the projections rebuild;
  - the `rails/` keys do not collide with `TaskIDs` (`tsk_`) or the `ready/` and `approver/` prefixes.
- **Profile:** the three fields are optional `*int64` with `omitempty`, 1–1000. #226 entry 10 is met. The defaults are 3/5/2.
- **Inventory I16:** four rows go from GAP to kept + GAP, and the count of 15/37 still adds to 52. The handler is deferred in `daemon/matrix.go`, and `wiring.go` is untouched. `Evaluate`, `Operate` and `Launch` have no non-fixture callers, so the change is inert.
