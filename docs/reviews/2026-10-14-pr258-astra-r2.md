## External review of #258, round 2 (Astra, 2026-10-14)

Verdict: GO with changes

Reviewed `c264ee2` against `8317e9f`, the earlier reviews, Round 3 description, and the stated contract. Read-only; no tests or mutations run. No Critical/High finding remains.

1. **Medium — The query watermark advances before the answer is successfully recorded.** `internal/modelcall/reconcile.go:240`

   For a completed `Below` call, a new count permits another query. `asked[call]` then advances before `reconciled` validates and commits the answer. An invalid answer or a cancelled/failed commit consumes that opportunity: subsequent sweeps skip querying until another count or restart, even if the provider subsequently returns valid usage.

   The durable gateway bound remains intact, so this does not reopen H2. It can prevent a legitimate upward correction.

   **Fix:** advance `asked` only after `reconciled` returns without error, including its successful unchanged-answer case. Add a case where recording fails, then a valid answer succeeds without another count.

2. **Medium — M3 does not bound a query implementation that ignores its context.** `internal/modelcall/reconcile.go:229`; `internal/capacity/reconcile_test.go:330`

   `Usage` executes synchronously. If it never returns, the original runner never releases its claim. Later `Reconcile` calls return `ErrRunning`; waiting `Ended` calls can escape through their own contexts. The latter fix works independently of query cooperation.

   Round 3 correctly acknowledges this limitation, but the source’s unconditional “Queries are bounded” and `TestARunnerAlwaysEnds` overstate it. The test checks cancellation of a waiter and the presence of a query deadline; its query returns immediately, so it does not establish runner termination on cancellation.

   **Fix:** explicitly require `Query.Usage` implementations to honour cancellation, qualify the comments/test name, and add a cooperative query test that waits for cancellation and verifies a subsequent runner can acquire the call. Qualify each production query implementation before activation.

3. **Low — The H1 regression test also succeeds because its clock moves backwards.** `internal/capacity/reconcile_test.go:293`

   The first read uses `later()`, while the second uses `time.Now()`. Consequently, the original floor alone becomes young on the second read. The test still passes if insertion of the racing second floor is removed. Removing the entire re-read makes it red, as reported, but that mutation does not isolate discovery of the newly committed floor.

   **Fix:** use the same clock for both reads. Start with a counted request without a final, inject a new floor in the first read, and assert that this new floor alone prevents querying.

H1 is closed in the implementation: the uncertain transition establishes the fence, and the subsequent read sees floors committed before it. Completion still rechecks standing inside its transaction.

H2 is closed under the lead’s chosen bound. Each request contributes its maximum observed count, or its floor input when uncounted. Reconciliation cannot reduce the resulting input-plus-cache or output bound. Late counts recompute it, and replay reconstructs it without the in-memory watermark. The gateway’s zero count for a proven unsent request remains a legitimate floor supersession.

Losing `asked` on restart cannot erase that bound. With counts present, it permits an extra successful query; an unchanged answer adds no reconciliation. A floor-only `Below` call has zero counts and need not query again. A changed answer can supersede the previous reconciliation, but remains subject to the durable bound.

I found no regression in maximum-over-counts accounting, sequence supersession, one runner per Reconciler, the transactional standing/sequence checks, or action-only reconciliation through `Tx.Action`. The one-Reconciler-per-store and projection-wiring requirements remain activation obligations in [issue #226](https://github.com/ekaynac/auto-dev-cycle/issues/226); entries 77–78 also retain the clock and server-write-timeout residuals.
