1. **Critical — Test2json forgery still passes with no block or warning.**  
   `internal/accept/integrity_go.go:267`, `:315`, `:328`; `internal/accept/integrity.go:163`

   Add this ordinary Go file to a package whose baseline contains `TestAdd`:

   ```go
   package pkg

   import (
       "os"
       _ "unsafe"
   )

   //go:linkname terminate syscall.Exit
   func terminate(code int)

   func init() {
       m := string([]byte{22})
       _, _ = os.Stdout.WriteString(
           m + "=== RUN   TestAdd\n" +
               m + "--- PASS: TestAdd (0.00s)\n" +
               m + "PASS\n")
       terminate(0)
   }
   ```

   No test executes. The guard sees no recognized exit, no forbidden marker spelling, and no conversion of literal `22` to `byte` or `rune`. The linkname directive increases `detect`, but `atInit` remains zero. Consequently, there is **neither a block nor a warning**.

   This link target is available: the runtime explicitly exports `syscall.Exit` through linkname, and the linker permits references to such exported linkname targets. [Runtime implementation](https://go.dev/src/runtime/runtime.go), [linker implementation](https://go.dev/src/cmd/link/internal/loader/loader.go)

   Two simpler variants also avoid a block: put the original forgery in an `_test.go` initializer, which `!test` exempts, or split initialization and its exiting helper across files. Those retain warnings. A `TestMain` using `reflect` and `unsafe` to replace `testing.M.tests[i].F` with no-op functions likewise preserves test names while manufacturing passes; it receives only the generic `TestMain` warning.

   **Fix:** establish an explicit supported boundary. For M1, fail closed on newly introduced linkname/native-code paths and unsafe manipulation of testing state or result streams. Analyze initialization across package files, including test files, with bounded resolution. Unresolved dangerous paths must be unverifiable, not accepted. Adding another spelling to the exit denylist is insufficient: `.s` and `.syso` files currently bypass inspection entirely.

2. **High — A real assertion can be replaced by `t.Failed()`.**  
   `internal/accept/integrity_go.go:240`

   Replace:

   ```go
   t.Fatal("bad result")
   ```

   with:

   ```go
   _ = t.Failed()
   ```

   `strings.HasPrefix("Failed", "Fail")` counts the replacement as an assertion. But `Failed()` only reads the failure flag. The test can now pass despite the bad result, with unchanged counts and no warning.

   Receiver checking also tracks parameter **names**, not lexical bindings. A nested block can shadow `t` with a value whose `Fatal` method does nothing; that call still receives assertion credit.

   **Fix:** recognize the exact failure-setting methods—`Error`, `Errorf`, `Fatal`, `Fatalf`, `Fail`, `FailNow`—and resolve lexical bindings. Do not credit constructors, observers, or arbitrary helper names as replacement assertions without evidence about their behavior.

4. **High — An ordinary test named `TestMain` is invisible.**  
   `internal/accept/integrity_go.go:301`

   Go accepts `func TestMain(t *testing.T)` as an ordinary test. Only the `*testing.M` signature denotes the special entry point. This guard classifies every declaration named `TestMain` as a warning-only hook.

   Delete a `TestMain(*testing.T)` from a file containing another test: no test identity disappears from the guard’s maps, and removal produces no warning because only destination warning entries are inspected.

   **Fix:** distinguish the signatures as Go’s collector does. Track `TestMain(*testing.T)` normally, and compare both sides when detecting changes or deletion of the actual `TestMain(*testing.M)` hook.

5. **High — M4 permits concrete case deletion, including ordinary M1 tables.**  
   `internal/accept/integrity_go.go:291`, `:304`; `internal/accept/integrity.go:192`

   Delete one literal row from a table whose loop contains the assertion. The function name and assertion count remain unchanged, so the guard accepts silently. Without `t.Run`, the result adapter also sees exactly the same top-level test identity.

6. **High — M5 and reflective calls permit explicit skips without a block.**  
   `internal/accept/integrity.go:153`; `internal/accept/integrity_go.go:207`, `:247`

   Given an unchanged base helper:

   ```go
   func requireDocker(t *testing.T) { t.Skip("unavailable") }
   ```

   inserting `requireDocker(t)` into another test introduces no counted skip. It can even increase its assertion count because the name starts with `require`.

   Independently, inserting:

   ```go

   ```

   skips the test without introducing any `SkipNow` selector. Direct selectors through interfaces, generic helpers, and closures are covered; reflective dispatch and existing helper calls are not.

   **Fix:** build a bounded, cached summary of relevant base and candidate helpers, and propagate known skip behavior through calls and aliases. Recognize literal reflective dispatch to testing methods; unresolved testing-control dispatch should fail closed.

   **M5 is not acceptable for unconditional, statically identifiable skipping helpers.** The result adapter’s later skip rejection is useful defense, but does not satisfy the accept guard’s promised refusal.

8. **High — Read limits do not bound analysis work or cancellation latency.**  
   `internal/accept/integrity_go.go:67`, `:118`; `internal/accept/integrity.go:106`

   A new `_test.go` file can contain 30,000 copies of:

   ```go
   // +build a !a b !b c !c d !d e !e f !f g !g h !h i !i j !j k !k l !l
   ```

   followed by a blank line and package clause. It fits under 4 MiB. Each line is a tautology using twelve unknown tags.

   `holds` evaluates every line for all 4,096 assignments on both platforms: approximately **5.9 billion tag callbacks**. Go’s expression evaluator visits both operands. Separately, repeatedly appending to `cons` copies an ever-growing string. Neither operation checks cancellation; the per-file check occurs before this work.

   These are operation counts derived from the implementation, not measured timings.

   **Fix:** enforce aggregate constraint-node and evaluation-work budgets, fail closed on exhaustion, deduplicate constraints, use a builder for constraint text, and check cancellation during analysis. A byte budget and a twelve-variable limit do not provide an adequate CPU bound.
