# PR #57 (flaky coverage-budget test): review

## Review of #57 (Opus subagent, 2026-10-05)

Verdict: NO-GO

The PR is right that a 50 ms wall-clock bound measures the runner, not the property. But the replacement ratio check is still timing-based, and I measured it as flaky in both directions. It fails on a correct tree, and under load it misses the regression it exists to catch. A fix for a flaky test that stays flaky should not merge. A deterministic check exists, and I verified it. It is one small edit to this same test (see H-1).

Setup: I tested a tar copy of 76eb20d without `.git`, on go1.27.1 linux/arm64 with 20 cores. The only change in the copy was a `t.Logf` of the ratio. The worktree was not modified.

### High

**H-1. The ratio check is still flaky on a correct tree, and worse under load.** `internal/profile/profile_test.go:446-454`

| Condition (unmodified code) | Runs | Failures (ratio > 8) | Ratio p50 / p99 / max |
|---|---|---|---|
| Idle machine, new process per run | 200 | 1 (0.5%) | 3.64 / 6.75 / 10.36 |
| Idle, `-count=100` in one process | 100 | 2 | max 8.90 |
| Idle, `-cpu 1 -count=100` | 100 | 1 | max 9.32 |
| 24 copies at once on 20 cores (a busy CI runner) | 360 | **41 (11%)** | 3.89 / 14.53 / 18.34 |

Fastest-of-three does not remove the noise. The two sizes are measured in separate time windows, so noise in one is not cancelled by noise in the other. Garbage collection and heap state also move the small measurement by 3x or more on an idle machine (1.8 ms to 7.5 ms), and the ratio divides by that number.

I tried two variants in my copy:
- Interleaving the two sizes, with `runtime.GC()` before each load and the fastest of seven: still 13% failures under load.
- Measuring the thread's CPU time (`RUSAGE_THREAD`) instead of wall time: 2% failures under load.

Neither variant makes a timing ratio reliable.

**H-2. Under load, the check misses the regression it exists to catch.** `profile_test.go:452`

I injected the regression into `profile.go`: the `anyCovers` loop now runs before the `coverageWork` refusal.
- Idle machine: the test fails as it should, ratio 9.6 to 17.0 (median about 14.8, which matches the PR's 14.2x). The lowest value, 9.6, leaves little margin above 8.
- Under the same 24-copy load: **21 of 192 runs (11%) passed**, with ratios as low as 3.98.

So the check is unreliable as a regression guard, not only as a pass condition.

**Fix for H-1 and H-2: a deterministic check of the order, with no timing.** The regression is that the coverage checks run before the budget refuses, and that order shows up in the error text. Put one entry that `protected_paths` does not cover into the 4000-entry fixture. Then require the budget refusal, and require that no "not covered" error appears:

```go
d := doc(4000)
d = strings.Replace(d, "protected_documents: [p0,", "protected_documents: [uncovered/x.md, p0,", 1)
_, err := Load([]byte(d))
if err == nil || !strings.Contains(err.Error(), "steps") || strings.Contains(err.Error(), "not covered") {
	t.Fatalf("coverage checks ran before the budget refused: %v", err)
}
```

I verified it in my copy. It passes on 76eb20d and fails when the injected regression is present. Keep the existing exact `coverageWork` checks, including the saturation check: they already cover the cost of computing the budget itself. Then:
- drop the ratio check, or keep it only as a `t.Logf`;
- keep only a generous absolute backstop, such as the existing 2 s.

If a test for a quadratic `coverageWork` is wanted, time `coverageWork` directly on about 100k entries. There is no parsing in that call, so a 1 s bound gives orders of magnitude of headroom.

### Medium

**M-1. The 1000-entry load's error is ignored.** `profile_test.go:446` (`small, _ := best(doc(1000))`)

The 1000-entry fixture does currently hit the same 'steps' refusal path. I probed the threshold:

| Entries per array | Refused for 'steps' |
|---|---|
| 300 | no |
| 400 | yes |
| 500 | yes |
| 1000 | yes |

So today the ratio compares like with like: parsing, glob compilation and the budget, all linear. But nothing enforces that. If `maxCoverageWork` (currently `1<<22`) is raised by about 16x, the 1000-entry load would go down the real coverage-check path and the ratio would compare two different paths, with no failure to say so.

Fix: assert that the small load's error also contains "steps". This finding goes away if H-1's fix drops the ratio.

### Low

- **L-1.** The `max(small, time.Microsecond)` floor (`:452`) is harmless. The small load takes milliseconds, and the timer has nanosecond resolution on Linux. Small loads on a fast machine are not a real risk.
- **L-2.** The comment at `:448-451` says the ratio "is the check". After H-1's fix, reword it so the order assertion is the check and the time bound is only a backstop.
- **L-3.** The PR says the test takes 64–69 ms locally. Here the fastest 4000-entry load is 12–25 ms when idle; the 4000-entry document's parse alone (`toJSON`) took about 7.7 ms. That is fine, but it shows the absolute numbers depend on the machine, which is one more reason to avoid timing.

### Answers to the four questions

1. **Robust against runner noise?** No. 0.5–2% failures on an idle machine and 11% under parallel load (H-1).
2. **Still catches the regression?** On an idle machine, yes (about 14.8x, matching the PR's 14.2x). Under load it misses about 11% of the time (H-2).
3. **Is the 1000-entry fixture on the same path?** Yes, it is refused for 'steps' (the threshold is between 300 and 400 entries), but the test doesn't assert it (M-1).
4. **Other weaknesses?** Garbage collection and heap state drive most of the variance in the small measurement. Division by a tiny duration and timer resolution are not issues (L-1).

### Lead notes on round 1 (applied)

- H-1/H-2: the timing ratio is gone. The test now checks the order: the 4000-entry fixture carries one protected
  document no pattern covers, and the load must give the budget refusal and no "not covered" refusal, so any coverage
  check that runs before the budget refuses fails it, deterministically, whatever the runner's load. Running the
  coverage checks regardless of the budget fails it; 20 consecutive runs pass. The 2 s bound stays as a backstop; the
  exact `coverageWork` arithmetic and saturation checks are unchanged.
- M-1 and L-2 go with the ratio. L-1 and L-3 need no change.
