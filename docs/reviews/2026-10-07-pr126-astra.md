**Medium M1 — Duplicate admission trusts the incoming proposal’s creation time.**  
[internal/authority/proposals.go:233](/tmp/claude-1000/-home-mega/d7e41cde-3883-4e5c-8d98-04b890c5f4c4/scratchpad/wt-s9-6a/internal/authority/proposals.go:233)

`pendingFor` evaluates the existing proposal at the incoming payload’s `CreatedAt`, rather than the authoritative event time. I reproduced admission of a second proposal with the same binding by dating its creation beyond the first proposal’s expiry—even though the first was still unexpired when committed. Both could then receive approvals, and the history rebuilt successfully.

**Fix:** evaluate duplicate liveness against `ev.At`; reject creation timestamps later than the event timestamp. Add a regression proving a future-dated payload cannot displace a currently pending proposal.

**Medium M2 — One approval ID can identify multiple approvals.**  
[internal/authority/proposals.go:350](/tmp/claude-1000/-home-mega/d7e41cde-3883-4e5c-8d98-04b890c5f4c4/scratchpad/wt-s9-6a/internal/authority/proposals.go:350)

The uniqueness check reserves `approval/<proposal>`, but never reserves `a.ID`. I reproduced two different proposals receiving approvals with the same `apr_…` ID and different objects. Both persisted and rebuilt successfully. References such as `grant.approval` or `supersedes` would consequently lack a unique record identity.

**Fix:** persist a unique approval-ID record/index alongside the proposal index and reject reuse atomically. Test reuse across proposals while retaining the existing byte-identical-first-approval assertion.

Both findings concern fold admission; neither demonstrated a current target-effect bypass. Probes and mutations used temporary Go overlays. Repository files remain unchanged.
