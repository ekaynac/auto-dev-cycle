What holds:
- Every row of the exit-code table matches note 08: applied 0, refused 1, could_not_run 2, proposed 3, the three stale reasons 4, usage 64. could_not_run is checked before the stale reasons, so the probe `{refused, could_not_run, stale_expected_state}` exits 2. Transport errors and invalid responses exit 2, with stdout empty.
- Unknown flags, an extra argument, a missing or unknown verb, and an unknown top-level command all exit 64 without calling the client. A negative version, 2^53, a malformed digest, an empty reason, a non-object scope, a spaced key and a duplicate key inside the scope are all refused by the request schema before sending.
- The response goes through contract.Validate, which is strict: no duplicate keys, no trailing data, integers only, registered reasons only. The generated union decoder runs after it. Both orders of validation are sound.
- The command table equals the registry, and each noun equals the action's family.

### Medium

**M1. A generated idempotency key is never shown, so after an ambiguous transport failure the user cannot retry safely.** (internal/cli/cli.go:81-88, 97-100)
- When `--idempotency-key` is omitted, the CLI makes a random `cli-<hex>`. On a transport error it prints only `could_not_run: <err>` (probe: stderr `adc grant revoke: could_not_run: timeout after write`, key not printed).
- Scenario: the next PR's Unix-socket client times out after the controller committed `grant.create`. The user re-runs the command and gets a new key.
  - If the object's version moved, `--expect` catches it (exit 4).
  - Otherwise the command runs twice. This applies to any action whose `expected` names an object that the action does not bump.
- The PR text says "a given key is passed through, so a retry is safe". That holds only when the user supplied the key.
- Fix: print the key on stderr in every could_not_run path that happens after the request was handed to the client (e.g. `retry with --idempotency-key cli-...`). Also put it in the JSON document, if M3 is adopted.

**M2. The request that is validated is not the request that is sent, and invalid UTF-8 in `--reason` is silently changed.** (internal/cli/cli.go:89-97)
- The CLI builds `body` with `encoding/json.Marshal` and validates it with `contract.Validate`, which checks a document being read. It then hands the typed `req`, not `body`, to `Client.Command`.
- Probe: `--reason $'bad\xffbyte'` exits 0 and calls the client. `req.Reason` still holds the raw 0xFF byte, and any marshal writes `"bad�byte"`. The recorded reason is not what was typed, and nothing refused it.
- The contract package says outright that writers must use `contract.Encode`, which refuses non-UTF-8 strings and validates its own output (contract.go header).
- Trap for the transport PR: the transport will re-marshal `req` its own way, so the bytes on the wire are never the bytes that passed validation.
- Fix: build the body with `contract.Encode("api/command-request", req)` and pass those bytes to the client (`Command(ctx, action, body []byte)`). The client then sends exactly what was validated.

**M3. `--json` emits no document on could_not_run, which conflicts with note 08 and with this repo's own precedent.** (internal/cli/cli.go:98-110)
- Note 08: "Every command supports `--json` (stdout = one JSON document ...)". `internal/entry`'s `adc dev vocab check --json` writes a bootstrap `{outcome, reason, detail}` document on could_not_run (entry.go:93-108), and its comment cites note 08.
- In this CLI a transport failure or an invalid response under `--json` leaves stdout empty (TestOutput:163 pins that).
- Scenario: a supervisor script runs `adc seat take --json ... | jq .disposition`. On a socket error jq gets nothing and the script must special-case exit 2. With `vocab check` the same script would get a document.
- The PR states this choice, but nothing in note 08 supports it. Either emit a could_not_run document (`disposition: refused, outcome: could_not_run`, a registered reason, the detail, and the idempotency key from M1), or amend note 08 to exempt client-side failures. Decide before the transport PR fixes the behaviour in place.

**M4. The tests do not pin the verb-to-action table; only `grant extend` is checked by meaning.** (internal/cli/commands.go:10-27; cli_test.go:54-76, 78-97)
- TestEveryActionHasOneCommand checks that the sets are equal, that the noun is the family, the verb's form, that commands are unique, and round-trip lookup. It never checks that a verb names *its* action.
- Mutations that survived (all tests green):
  - swapping `seat.take` and `seat.release`'s verbs;
  - swapping `agent.enrol` (`enrol-agent`) and `actor.revoke` (`revoke-actor`).
- With the second swap, `adc admin enrol-agent` sends `actor.revoke`.
- The equivalent swap of grant extend/revoke is caught only because TestEnvelope happens to use `grant extend`.
- Fix: a golden table in the test (action -> "noun verb"), or derive the verb from the action's name, with an explicit exception list for `adopt-profile`, `request-review`, `confirm` and the rest.

### Low

- **L1. The human proposal output misses what note 08 asks for** (cli.go:164-166). Note 08: "prints the proposal, its effective change and the dashboard link". The output says "on the dashboard" with no link and no effective change. CommandProposed (#61) carries neither, so this is a schema gap. Record it as deferred in the PR or the note.
- **L2. A failed stdout write does not change the exit code** (cli.go:111-119). With `--json` and a closed pipe, the document is lost but the exit is still 0/3/... . entry treats the same case as could_not_run (entry.go:65-68, 153-155). No test covers it (the mutation "write error silent" survived).
- **L3. `-h`/`--help` on an action exits 64** (flag.ErrHelp, cli.go:63-65). `adc grant --help` says `unknown verb "--help"`. `adc help` lists only `version`, not the action commands. Help should exit 0, and a noun alone could list its verbs.
- **L4. A repeated flag is accepted, and the last one wins** (`--expect 1 --expect 2` sends 2). The single-dash forms and `+7` are also accepted. For the flag that pins the revision under review, a repeated `--expect` is better refused.
- **L5. A newer controller's reason makes a real refusal look like could_not_run.** A reason this CLI's registry does not know yields "invalid response", exit 2, instead of 1 (probe with `no_such_reason_xyz`). This is consistent with note 02's readers-accept-registered rule. Still, the transport PR should decide whether the CLI and controller versions must match.
- **L6. Outcome and reason are not cross-checked.** `{refused, failed, quota_exhausted}` exits 1 although quota_exhausted is registered only for could_not_run. This is a schema/#61 gap; the CLI just follows the outcome.
- **L7. The controller's `detail` goes to the terminal unescaped** (cli.go:170). Control or ANSI escape sequences from a compromised or buggy controller reach the user's terminal. Quote the detail (`%q`) in human mode.
- **L8. Several messages have no test.** Mutations that survived:
  - flag errors sent to io.Discard (the unknown-flag message never reaches stderr);
  - no "unknown verb" message;
  - no diagnostic for an invalid response;
  - the "(a repeat; nothing ran again)" note removed;
  - `ExitCode`'s fallback for a nil variant changed to 0.
  
  Each one is low impact, but the claim of 16 out of 17 mutations killed does not cover stderr content.
- **L9. Interface shape the transport PR will hit:**
  - `Client.Command` returns `([]byte, error)` with no status. An HTTP 401/403/5xx body that is not an envelope can only become "invalid response", exit 2. Decide the mapping of a non-envelope status (auth refusal is arguably exit 1) before the client is written.
  - `cmd/adc` passes `context.Background()`: no signal cancellation and no timeout.

### Lead notes (applied before merge)

- M1: once a command is sent, every could_not_run message names its idempotency key and says to retry with `--idempotency-key <key>`. Tested.
- M2: the body is built with `contract.Encode` and the Client receives exactly those bytes; the interface now takes `body []byte`. `contract.Encode` validates in the writer direction, where invalid UTF-8 is an error, so a reason that is not UTF-8 is a usage error. Tested.
- M4: `TestCommandsReachTheirActions` pins every command to its action by meaning.
- Low (help): `-h`/`--help` on an action command exits 0.
- **Deferred:**
  - M3 (a `--json` document on could_not_run) needs a registered transport reason such as `controller_unreachable`, which is a vocabulary change. It lands with the transport in step 9, part 3.
  - The dashboard link and the effective change for a human proposal come from a proposal read (`GET /v1/proposals/{id}`), which lands with reads. The response union stays small.
  - Context cancellation and timeout, the HTTP status in the Client, and escaping the controller's `detail` for the terminal land with the transport.
  - A reason code an older CLI does not know gives exit 2 under the vocabulary's reader rule (an unregistered code is invalid). Recorded as a compatibility note for the release.
  - A repeated `--expect` keeps the last value, as the flag package does for every flag.
- Mutation: 18 points, all killed by a failing test.
