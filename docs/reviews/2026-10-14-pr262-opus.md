## Opus review of #262

Verdict: GO with changes

The new row still catches the H3 defect, and the property "nested ≤ flat" is sound. On clean code the flat input does all the work the nested input does, plus a scan of the whole 4 MiB string. But the margin is only about 10 to 25 ms locally. Under heavy oversubscription, the median of 3 sequential runs still failed once on clean code. The fix below costs very little, and with it I saw no failures across the same loads.

Setup: arm64, 20 cores, Go 1.27.1, head a584851. I built and ran test binaries in a scratch worktree and changed nothing in the PR. The worktree is removed. gofmt and go vet are clean.

### 1. Does the row catch the H3 defect? Yes.
- **Mutation A** (`pyField`'s `need(depth <= maxNest)` removed): the row FAILED 5 of 5 runs. Nested took 157 / 158 / 374 / 394 / 402 ms against flat at 16.6 / 17.4 / 29.1 / 17.3 / 15.9 ms. The smallest ratio was about 5.4×.
- **Mutation B** (the `:` spec descent keeps `depth` instead of `depth+1`): `TestPyTokensBounded` PASSED 3 of 3, as expected. With this mutation, depth still grows by one per `{:` pair, so the input is refused after about 128 bytes. That is not a DoS, so a timing row cannot see it. `TestPyTokensRefuses` catches it, at integrity_py_test.go:319 (`specDeep(maxNest/2 + 1)` is read, not refused). Both H3 mutations are therefore covered by the suite, and no change is needed.

### 2. Flake robustness

**M1. The median of 3 sequential runs can still invert on clean code under bursty load.** integrity_py_test.go:385-400

- **Why the property holds.** `pyTokens` does the same setup work on both inputs: `string(src)` copies, `utf8.Valid`, `slices.Contains`, the `ReplaceAll`s, the anchored cookie regexp and the `+"\n"` copy in `pyLex`. That setup takes about 3 to 5 ms. After it, the nested input is refused within about 128 bytes. The flat input must still be read through all 4 MiB by `pyString`, which runs `HasPrefix` checks on every byte. Both inputs allocate the same buffers, so GC cost is the same on average. The flat run can only be slower, and an inversion can come only from noise that is not spread evenly over the two windows.
- **Why it can still invert.** The noise is uneven because all 3 flat runs finish before any nested run starts. One burst of preemption or GC across the nested window flips the result.
- **Clean runs, PR as written (60 runs, 1 failure):**

| Condition | Runs | Failures | Highest nested/flat ratio |
|---|---|---|---|
| Quiet | 7 | 0 | about 0.29 |
| `GOMAXPROCS=1` | 6 | 0 | 0.43 |
| 24 competing `clean.test` loops on 20 cores (load avg 44 to 61), default and `GOMAXPROCS=1` | 25 | **1** | 1.005 |
| `taskset` to 2 CPUs with 2 competing test binaries | 12 | 0 | 0.63 |
| `taskset` to 1 CPU with 3 competing test binaries | 10 | 0 | 0.38 |

  The one failure: `nested specs refused in 37.031533ms, a flat f-string of the same size in 36.85377ms: not at once`. That run's nested times were [24.8, 37.0, 37.1] ms and its flat times were [34.9, 36.9, 51.9] ms.
- **Why this matters on CI.** The CI runner is much slower than this box. In the #261 failing attempt, `TestPyTokensBounded` took 33.53 s, against about 2.5 s locally (about 13×). It also runs beside other package binaries, because `go test` runs packages in parallel.
- **Fix (prototyped and measured):** interleave the two inputs, call `runtime.GC()` before each timed call, take the **minimum** of 5 runs for each input, and keep `nested > flat` as the failure condition. Load only adds time, so the minimum is the right estimate. With interleaving, a burst hits both sides.
  ```go
  refusedIn := func(src []byte) time.Duration {
      runtime.GC()
      start := time.Now()
      if _, why, err := pyTokens(context.Background(), src); err != nil || why == "" {
          t.Fatalf("%.12q…: %q %v, want refused", src, why, err)
      }
      return time.Since(start)
  }
  flat, nested := time.Duration(math.MaxInt64), time.Duration(math.MaxInt64)
  for range 5 { // interleaved; the fastest of each: load only adds time
      flat, nested = min(flat, refusedIn(flatSrc)), min(nested, refusedIn(nestedSrc))
  }
  ```
  - Under the same three loaded conditions, the prototype PASSED 34 of 34 clean runs. Its highest ratio was 0.54, and usually it was 0.1 to 0.36.
  - Against Mutation A under the 24-loop load, it still FAILED 3 of 3, with nested at 0.91 to 1.17 s against flat at 30 to 37 ms (ratio 25 to 39×).
  - The cost is about 10 calls of 5 to 30 ms each, which is negligible.

### 3. Other parts of the test that are likely to flake (do not block)

**L1. The 20 s context is shared by all six runs of one generator.** integrity_py_test.go:360
- For "deep brackets" and "one logical line of many tokens", the six runs take about 0.8 s locally. At the about 13× CI slowdown seen on #261, that is about 10 to 11 s, so the headroom is only about 2×. If the deadline fires, `pyTokens` returns ctx's error, and the test reports it with `t.Fatalf("… (not linear)")`. So a slow runner shows up as a false "not linear" failure.
- **Fix:** raise the deadline to 60 to 120 s, or remove it and rely on `go test -timeout`. A quadratic regression at 4 MiB would take far longer than either. The 8× ratio check already catches non-linearity.

**L2. The linearity check uses medians of sequential runs: all 1 MiB runs first, then all 4 MiB runs.** integrity_py_test.go:362-377
- The threshold is `8×` plus 500 ms. Linear scaling gives about 4×, and quadratic gives 16×. The check therefore has about 2× headroom on each side, and the 500 ms term counts for less on a slow runner.
- It never failed in my loaded runs, which is about 20 runs that recorded the linearity timings.
- It has the same weakness as M1: a load burst during the 4 MiB window counts against linearity.
- **Fix:** use the same method as M1. Interleave the two sizes and compare the minimum of each.

### Summary
- The row catches the H3 defect. Mutation A failed 5 of 5. Mutation B is caught by `TestPyTokensRefuses`.
- "nested ≤ flat" is sound: on clean code the flat input does strictly more work.
- Only how the row measures time should change. Use the interleaved minimum of 5 with `runtime.GC()` (M1) before merge, or as a quick follow-up.
- L1 (the 20 s shared context) is the larger remaining CI flake risk in this test. It is worth a follow-up, but it does not block this PR.
