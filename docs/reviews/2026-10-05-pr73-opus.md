### Findings

**High:** none.

**Medium:** none.

**Low**

1. `internal/fixtures/mutation_test.go:97` (from #72, but this PR relies on it): the tagged test asserts only `!r.Pass`. It does not check that the mutation turned the fixture red for the right reason, meaning the targeted step. For second-daemon the probe shows the right step flips, but nothing pins that. Suggestion: also assert `r.Got != nil` (the fixture ran and did not error out), or name the expected mutated sequence or the index that must differ in the golden or the test. Today a mutation that made the runner return an error would fail with `t.Fatal`, which is acceptable, but a mutation that flipped an unrelated step would also count as red.
2. `internal/fixtures/eventstore.go:126-153`: the in-process stand-in is faithful for `flock`. On Linux `flock` locks belong to the open file description, `AcquireLock` opens a new one on every call (`lock.go:57`), and the probe confirms that a real second process gets the same result. Two limits are worth one line in the runner comment:
   - (a) If the lock moved to POSIX `fcntl` record locks, which are per-process, this fixture would go false-red even though cross-process exclusion still worked. That failure is conservative, but it is a coupling to `flock`.
   - (b) It cannot tell a real kernel lock from a process-local guard, such as a package-level "held dirs" map. Such a guard would pass this fixture and `store_test.go:155` while giving no cross-process exclusion, and the named mutation only covers removing the `flock`.

   No test in the repository takes the lock from a second process. A small re-exec test in eventstore would close this. Not blocking: the design (03) specifies `flock`, and the fixture exercises it.
3. `internal/fixtures/eventstore.go:136,139,143,147`: the runner discards the return values of `Release()`. The codebase does this elsewhere too (`eventstore.go:26,33,36`), and a failure at line 143 would surface as a red third step. Still, under the "never silently swallow errors" default, line 143 could return the error (`if err := first.Release(); err != nil { return nil, err }`). Then a failed release would read as "fixture could not run" instead of as a contract breach.
4. `internal/mutation/mutation.go:18-20` and the PR text ("the lock succeeds without the exclusive flock"): the mutation still calls `flock` and only ignores its failure. Without contention it does take the lock. Under contention it also truncates and rewrites the holder's record (`lock.go:80-90`), which 03 forbids for probes. That is acceptable for a deliberately broken build, but "ignores a failed exclusive flock" would describe it more accurately. Informational.
5. `fixtures/contract/m0/second-daemon.json:3` and the runner test the lock layer (`AcquireLock` → `ErrAlreadyRunning` → mapping). They do not test 03's "A second daemon exits with `could_not_run/controller_already_running`" at the `adcd` process or exit-code level. That fits M0's scope as long as no daemon entry point exists. When one exists, the fixture name promises more than it checks, so consider a follow-up to drive the real entry point.

### Checks against the brief

- **Proves the invariant through the real lock:** yes. All three steps call `eventstore.AcquireLock` on the same scratch `state` directory, and step 3 also proves that a release frees the directory.
- **Mutation site inert when off:** yes. `err != nil && !mutation.Is(...)` (`lock.go:73`) is identical to the original whenever `Is` is false. In ordinary builds `Is` is a constant-false function (`mutation_off.go`), so the condition reduces to `err != nil`. `TestOrdinaryBuildsHaveNoMutations` covers the new constant through `Known`.
- **Red for the right reason:** yes, by probe. Only step 2 flips, to `empty/completed_clean`. `second.Release()` runs `LOCK_UN` on its own unlocked open file description, which does not drop the first holder's lock.
- **Leaks:** none found. Every path releases what it acquired: first-acquire failure (nothing held); unexpected error on the second attempt (first released, line 139); mutated second (released, line 136); third (released, line 147). The descriptor delta was 0 in all modes and under concurrency. `Run`'s `RemoveAll` removes the lock file with the temp directory.
- **Order independence and parallel safety:** yes. Each `Run` uses its own `MkdirTemp`. No global state is touched apart from the `ADC_MUTATION` environment variable, which only the tagged test sets, through `t.Setenv` without `t.Parallel`. 64 concurrent runs were clean under `-race`.

### Lead notes (applied before merge)

- **L3:** release errors are no longer discarded. A failed `Release()` is an error of the run, not a step.
- **L4:** the mutation comment now says what it does: it ignores a failed exclusive `flock`.
- **L1** (asserting which step a mutation changes) belongs to the framework, #72. It is recorded for the framework review.
- **L2 and L5 are follow-ups.** L2 is a cross-process lock test, through a re-exec'd binary, which this review already probed successfully. L5 is a daemon-level fixture once `adcd` has an entry point that opens the store.
