### Question 2: the two-run rule (#226 entry 110)

### Medium

**M1. The order and single-execution evidence are the caller's claims.** (`internal/qualify/route.go:56`, `:182`; `qualify.go:534`)
- `Review(ctx, run, seq, prompt)` records whatever `seq` it is given, and lets one case be reviewed again and again within a run.
- **Input 1 (probe):** a driver ran the cases in suite order, defects first, while passing each case's seeded `seq`, against an upstream answering no_go to the first four requests and go afterwards. Two such runs: `Check` returned `nil`.
- **Input 2 (probe):** a driver kept the best of three random answers per case. Two runs: `Check` returned `nil`.
- **Fix:**
  - Make `Run` a pointer with a cursor. `Review(ctx, run *Run, c Case, prompt)` takes `seq` from the cursor.
  - It refuses a case other than `Order(run.Seed)[cursor]`, and refuses `digest(prompt) != c.PromptDigest`.
  - `Record` refuses a run whose cursor is not at the end, or one with a case reviewed twice.

**M2. An aborted run leaves no record, so the latest-run rule never sees it.** (`internal/qualify/live_test.go:82-87`)
- The live test logs each case's expected and decided answer as it goes, and writes a record only at the end. A `t.Fatalf` on a Review error also leaves nothing.
- **Input:** the operator sees a defect decided go at sequence 2, presses Ctrl-C, and runs again. No file is edited and no record is deleted, yet the failure leaves no trace.
- **Fix:**
  - Write a record with `qualified:false` and no cases yet (a schema state such as `"complete":false`) before the first review, and complete it at the end.
  - `Check` treats an incomplete latest record as failing.
  - Log `expect` only after `Record`.
  - State in the residuals that deleting a committed record (not an edit) is for PR review to catch.
