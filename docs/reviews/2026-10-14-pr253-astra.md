**High — H1. Late overflow can silently lose liability; settlement order changes the accounting.**  
Locations: `internal/capacity/liability.go:117`, `:128`, `:150`; `internal/capacity/ledger/ledger.go:113`.

`StandingOf` can change a previously settled call back to uncertain when additional deltas overflow. However, `settle` indexes only calls originally listed in `Settlement.Liabilities`, and `owe` revisits only that list. Calls originally listed in `Settlement.Calls` cannot acquire liability afterward.

Concrete counterexample: reserve 400 tokens, then receive these schema-valid reports for the same binding:

- `final`, input tokens = 1;
- delta sequence 0, input tokens = `9007199254740991`;
- delta sequence 1, input tokens = 1.

| Settlement timing | Final group liability |
|---|---:|
| After the final, before the deltas | **0** |
| After all three reports | **9007199254740991**, inconsistent |
| Before all three reports | **9007199254740991**, inconsistent |

In the first history, late usage is durably recorded, but `lateUsage` returns immediately because the call has no liability index. `StandingOf` now says uncertain, while `LiabilitiesOf` reports nothing and admission can reuse the group’s capacity.

This violates I9 and the explicit report-order guarantee. It does not require fabricated bindings or store edits. Each history can replay consistently with itself; replay therefore does **not** detect the accounting discrepancy.

**Fix:** recompute liability for every bound call of a settled lease, including calls originally classified as settled. Resolve late reports through the binding and settled lease, or index every settled call; update `owe` to examine the full bound-call set. Add the three permutations above, followed by provider reconciliation and replay.

**Medium — M1. The gateway-count deferral needs an explicit pre-activation deadline.**  
Locations: `internal/capacity/ledger/ledger.go:99`; `internal/adapterhost/submit.go:315`; `docs/design/m1/00-slice-plan.md:593`.

An adapter can report zero deltas and a zero-token final. That releases the reservation fallback and produces a zero priced charge. Ignoring adapter-reported cash does not prevent this.

For P17, repeated calls whose individual reservations fit the rail can consume real money while recorded cumulative spending remains zero. Attempt/round caps may limit repetition, but they do not enforce the USD limit.

I would **not require P12b alone to reject adapter finals**, given the explicit inert staging and existing final-report contract. This is nevertheless unacceptable for activated M1. [Entry 69](https://github.com/ekaynac/auto-dev-cycle/issues/226) assigns “P11b or P30,” but P30 follows P22a; that is too late for checkpoint (a).

**Fix:** assign authoritative counting or conservative bounding to a definite owner before `launch` activates, and make it an explicit P17/P22a acceptance gate. The hostile-zero-final fixture must retain a conservative charge or use independently established usage. Simply relabelling upstream counters `gateway_count` is insufficient against a hostile upstream.

**Low — L1. The fold-order comment promises an unsafe alternative.**  
Location: `internal/capacity/liability.go:34`.

Keeping settlement in its own command is insufficient when projectors otherwise run batch by batch. For an already liable call, a command containing two late deltas runs capacity twice before either delta reaches the ledger. Each recomputation sees only its own extra report; the second overwrites the first’s contribution. Replay processes events individually and derives a different amount.

The daemon and new liability tests correctly use `ProjectEach`, so this is not another blocker on their composition.

**Fix:** require event-by-event composition across capacity, bindings, and usage for **all** commands. Remove the “settlement in a command of its own” alternative and add a two-delta late-report batch regression.

**Low — L2. Binding-refusal recovery loses durable diagnostic evidence.**  
Location: `internal/adapterhost/submit.go:255`.

The retry now closes the attempt and preserves existing accounting or the reservation fallback. That is an acceptable nonblocking recovery behavior. However, the returned `ErrRecord` is transient; `attempt.lost` records the generic disconnect reason, not the rejected binding.

**Fix:** persist a usage-rejection diagnostic identifying the call and expected/received binding, using a suitable diagnostic event rather than forcing it into the output-handle refusal schema.

**Low — L3. Q8 still states the superseded rule.**

X3 and the implementation use `max(positive reservation, deduplicated delta sum)`, but Q8 still says “delta sum or its positive reservation” and names only provider reconciliation as the release condition.

**Fix:** update Q8 to state the approved maximum and both accepted settlement conditions, with the pre-activation trust requirement above.
