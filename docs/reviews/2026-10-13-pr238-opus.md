### High

**H1. The answer fold re-validates the scope against the current schema on replay, so a later schema change could stop `adcd` from starting.** (`internal/authority/answer.go:148`)
- `recordAnswer` calls `answerInputOf(a.Scope)`. That is `contract.Decode`, which validates the scope against the live `api/scope/input-answer` schema and then decodes it strictly.
- Payloads are validated only on append (`eventstore/store.go:526`). But `checkProjections` (`daemon/startup.go:139`) replays every event at startup.
- So any later tightening would make stored answers fail replay. Examples: the `answer` payload typed per kind (it is already marked `x-adc-open-payload`), or `owed_revision` raised to minimum 1. Startup would then refuse with `ambiguous_state`.
- This breaks the binding-fields-only rule that P1 follows (`project.go:23-28`, "validated … at command time only") and P3 follows (`task.go:294-296`).
- **Fix:** in the fold, read only `{owed_input, owed_revision}` with plain `json.Unmarshal` and refuse if either is missing. Keep `answerInputOf` for `Derive` and the logic only.
- **Fix:** add frozen replay goldens for an `owed_input.recorded/v1` payload and an `input.answer` `approval.recorded` payload, like `TestTaskGoldensReplay` and `testdata/project-created-v1.json`. A frozen golden is needed here; P5 is the only one of P1, P3 and P5 without one.

**H2. A granted supervisor can answer any ruling, including one owed to the operator. The responder's authority is never checked against the kind or the owner.** (`answer.go:49-52`, `answer.go:80-110`; deviation 5)
- Note 04 "Owed inputs" says authority validates "that the responder may answer **this kind** for this project".
- What the PR checks: the generic grant covers `input.answer` on the project, plus the seat. Nothing reads `o.Owner` or `o.Kind`.
- Consequence: a supervisor (the autonomous orchestrator) with an `input.answer` grant can answer a `ruling` whose owner, and whose `awaiting_input` hold owner, is the operator. That is a question owed to "an outside party", answered by the actor the question was meant to go around.
- Merge approval (P28) is correctly kept out. But nothing here leaves a seam for operator-only inputs, so P28 would have to add the first owner check.
- **Fix (recommended):** in `answerable` (shared by the logic and the fold), allow the answer when `by.Kind == operator`, or when `by.ID == o.Owner`; refuse otherwise with `action_not_granted`. Add a test: a granted supervisor answering an operator-owned ruling is refused.
- **Alternative:** if the operator prefers "any granted supervisor", record that as an operator decision in slice plan §5.2 or the inventory, and say how the per-kind clause in 04 is satisfied.

### Medium

**M1. `Answers.Approval` returns a Ref for an answer that is no longer in force.** (`internal/authority/owed.go:203`)
- It checks only the stored approval's scope, project and answers. It does not check that the approval is the owed input's current `o.Answer`, that its actor is live, or that the node declares the input (`declared`).
- `graph.Context` checks only that the revision is current (`successor.go:213-222`). So between a claim and its commit, a revoked supervisor's answer, or one replaced after a revocation, is still delivered to the model as an input. The commit catches it later, but the model has already seen it.
- **Fix:** in `Approval`, call `declared` and `answerInForce`, and require `a.Approval == approval`.

**M2. A supervisor's answer approval records no grant.** (`answer.go:166`, `answer.go:AnswerApprovalOf`)
- The fold refuses any `a.Grant != nil`, so the grant the supervisor answered under is never recorded. Note 04's approval record has `grant: grt_…|null` for exactly this audit link.
- The rule "revoking the grant does not withdraw the answer" is consistent with applied proposal approvals, which also survive a grant revocation. But no test exercises a grant revocation after an answer; only actor revocation is tested.
- **Fix:** record the covering grant for a supervisor (nil for an operator). In the fold, require it to be non-nil exactly when `ActorKind == supervisor`. Add a test that revoking the grant after an answer leaves the answer in force.

### Low
