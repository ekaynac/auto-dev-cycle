### The answers to the five questions

1. **H1: closed.**
   - **Command and fold:** both `done` (`internal/authority/admit.go:154`) and `doneTask` (`:246`) go through `endable` (`:170-190`). For either disposition it calls `lease.Unended` on the unit of every node in `graph.TaskNodes`. That list includes superseded nodes, because the index only ever grows: `putNode` is the only writer and nothing deletes from it.
   - **What counts as running:** `unit_open` is written inside `lease.put` (`internal/lease/wiring.go:62-68`), which is the only writer of leases and attempts. An entry stays while a lease is in any of its 9 non-ended states or an attempt is running, stopping, finishing or lost. A lease's or attempt's unit never changes, because each fold compares the record with what the previous one derives.
   - **Replay order:** adcd folds with `eventstore.ProjectEach` (`internal/daemon/wiring.go:205`), one event at a time, so appending and replaying see the same state.
   - **A result recorded another way:** a reuse needs a waiting or runnable node. A result naming an older sealed attempt passes `attemptBound`. Either can still complete a node whose attempt runs, but `endable` reads `unit_open`, not the node's state, so the end is still refused.
   - **Liveness:** sealing never asks for the task's authority (`Units.ProjectTask`), so a revoked task's lost or stopping attempt can still be sealed, and abandonment can still happen.
   - **The no-attempt rule** (`internal/graph/content.go:94-107`) is enforced in the fold, on both append and replay.
