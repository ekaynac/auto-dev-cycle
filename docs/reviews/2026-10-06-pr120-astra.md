## Review of #120, round 2 (Astra, 2026-10-06)

Binding and replay checks:

- `BindObject` rejects an empty subject, rebinding, View transactions, and rebuild transactions (`internal/eventstore/writer.go:112`). An expectation without a binding or record definition fails closed.
- Binding is callable by any trusted code holding the command transaction; it is not an authorizer-only capability. In the current wiring, an earlier bind makes the real authorizer’s bind fail, and command logic runs after expectations. No bypass found.
- Binding occurs before the authorization decision, but a denial immediately aborts submission; a bound object does not confer authorization (`internal/authority/derive.go:80`, `internal/eventstore/writer.go:453`).
- Each submission creates a fresh `Tx`; bindings are neither persisted nor carried into subsequent commands. Idempotent replay rechecks identity, then returns before authorization and both expectation checks. Projection rebuild likewise runs neither and rejects binding.

The existence rules are coherent with `SubjectVersion`: deletion retains its historical event sequence, while record absence governs the version-0 sentinel. Recreation receives a new sequence. The older `Command.Expected` remains a historical subject-version check.
