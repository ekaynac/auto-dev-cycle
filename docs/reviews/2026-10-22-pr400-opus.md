### Medium: OBLIGATION

**M1. The scan can be dodged in three ways, so the class "a hold the loop raises that nothing clears" can come back unnoticed.** `internal/daemon/holds_table_test.go:28,70-124`
1. **It checks only that the named clearer calls `graph.Clear` somewhere,** not that the loop ever offers it the hold.
   - The filter that decides what the clearer is offered is `reconcile.Observe`'s, by kind and signal prefix (`reconcile.go:467-468`).
   - This PR's own bug was exactly that kind of filter miss, and C1 shows the scan does not catch it.
2. **It sees only holds built in a `FuncDecl` of the loaded packages.** C2 dodges it with a `NodeHold` built in a package-level function literal. The same works with a field assignment after the literal (`h.SignalInstance = …`), or a helper in a package it does not load.
3. **It loads only `daemon`, `dispatch`, `reconcile` and `authority`,** but the loop also raises holds through `graph`:
   - `graph.Evaluate`: `awaiting_input` (`evaluate.go:252`), `reviewer_unavailable` (`evaluate.go:294`), and `rail:rounds_per_task` (`rails.go:191`);
   - `graph.Operate`: `rail:merge_operations_per_generation` (`effects.go:264`).

   Each is cleared today, by answers, `reviews.Unheld` and `ClearRail`, but none is pinned. So "every hold the loop raises" is promised and not tested.

**Fix:**
- For each row, give a sample signal. The test runs it through the same predicate `Observe` uses: expose `reconcile.Offered(kind, signal) bool`, use it in `Observe`, and assert it is true for each row whose clearer is `Unblocked`, `Reopened` or `Unheld`.
- Also scan `FuncLit`s in package-level `var` declarations, and load `../graph`, with rows for its four raises.
- Or state the scan's scope in the PR and the inventory.

**M2. A second implementation of "the gateway holds this executor's credential", whose answer can differ from the launch's.** `internal/dispatch/reserve.go:127` vs `internal/dispatch/launch.go:65-82`
- **Search:** I looked for `Credentials.Holds` callers and "credential" readiness in `internal/dispatch`. `Dispatcher.Observe` already decides it.
- **The difference:** `Observe` treats an unregistered executor, and an error from `Holds`, as "not held". `credentialHeld` returns the error, so `Unblocked`'s command is refused and logged instead.
- **Fix:** one helper, `credentialReady(ctx, e) error`, used by both.
- **Also:** `credentialBound` repeats `imageResolveBound` (`run.go:677`), so share one "readiness bound".

### Low: OBLIGATION

**L2. A credentialed executor's other placement holds now stay up after their own cause is fixed, and their signal names a cause that is gone.**

- **Effect:** bounded and visible. A launch would miss on the credential anyway, so this is no false block.
- **Fix:** when `Configured` fails on the credential, replace the hold with `placement: destination <id>` (clear and raise in one command). Or state it in `Unblocked`'s comment.

**L3. `imageReady` checks the profile's pin, while the hold names `card.Image`.** `internal/daemon/run.go:680-698`
- The two are the same today: `placer.card` takes the image from the profile's one pin.
- **Fix:** resolve the hold's own image (decode it from `imageSignal`, or keep the ref in `Pages`), or note the tie in a comment. Otherwise a future card whose image is not the profile's would clear on the wrong image.

### The four questions
1. **Can the scan be dodged?** Yes:
   - a hold the loop is never offered (C1);
   - a hold built in a function literal, or after the literal (C2);
   - the loop's raises in `graph`, which it never loads.

   A signal built dynamically from a parameter is matched by its expression's text, so any value passes.
2. **Can any of the three holds clear while its cause stands, or never clear?**
   - **Clear early:** no.
     - The credential clears only when `Holds` is true.
     - The image clears only when `Resolve` succeeds, the same call as the launch's readiness (`launch.go:60-64`).
     - The changed placement clears only when the current placement passes, and Match then records it again.
   - **Never clear:** only in a configuration that cannot launch at all. With no gateway, or no image store, the launch also misses, and adcd always passes both once a runner exists.
   - **Spin:** none found, since the card and checks are deterministic.
3. **Does `Configured`'s credential check change placement for executors without credentials, or add a false block?**
   - **Executors without a credential reference:** unchanged (`CredentialRef == nil` → held).
   - **Credentialed executors:** their placement holds now wait for the credential too (L2). That is no false block, because the launch would miss.
   - **Inside the writer's command:** `Holds` reads memory, and its 5 s bound is stated.
4. **Regression on active paths?** None.
   - `Place`, `Launch` and the loop's `Unblock` and `Launch` actions run only under the `Evaluates` gate (`launch` inactive).
   - The renamed signals are read nowhere else; I grepped for `"destination "` and `"executor "`.
