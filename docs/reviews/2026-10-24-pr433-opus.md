### Answers

1. **The image hold.**
   - **Is the right thing held?** `imageMissing` (`internal/daemon/run.go:882`) is `ErrImage` except `ErrUnqualified` (a profile fault, kept in `configFault`) and `errHost`.
     - `ErrManifest` and `ErrAdapter` do not wrap `ErrImage` (`internal/sandbox/adapter.go:212`, `image.go:34-37`), so a present-but-wrong image stays a profile fault. It is never a `wrong_owner` that `imageReady` (Resolve only) would clear into a relaunch loop.
     - A build is held on an image at its digest only when podman itself errors; see L2.
     - A podman that hung past `resolveTimeout` on the build's launch is `errHost` (`internal/daemon/adapter.go:108-109`), so it is retried.
   - **The lease:** the build's resolve is in `adapters.Start` (`run.go:317`), before the launch. Its failure goes to `endLease`, which refuses and releases the lease and raises the hold in one command. `TestTheRunnersImageHoldClearsOnceItResolves` and `TestALaunchMissStartsNothing` cover this.
   - **The clear:** `imageReady` (`internal/daemon/place.go:269`) re-resolves the profile's pin through the same `sandbox.Host` that the runner resolves with. Production passes `*cfg.Sandbox` to both (`wiring.go:92,146`). A `podman pull` that sets the RepoDigest therefore clears it on the next pass.
   - **Accept and the gate:** both call `checkout` (`internal/daemon/accept.go:298`), then `notRunOrHold` → `holdOn`, so the same rule applies. Accept has a row. The gate had none; probe 3 shows it behaves the same (L1).
2. **402 and 429.**
   - **Data flow:**
     - `forward` sees the upstream's status (`internal/gateway/gateway.go:535-537`);
     - `observeReset` records `resetAfter` while bound (`:600`);
     - `Unbind` hands `Observed` over whole (`:200`);
     - `egress.open`'s `end` (`internal/daemon/egress.go:152`) passes it to `endGateway` (`run.go:306`);
     - `complete`/`completeReview` pass it to `providerHold(…, obs.Reset)` (`run.go:1052`, `:476`);
     - `record`'s `hold` step (`:1161`) calls `graph.Retry`.
   - **The reason** comes from the statuses through `exitmap.Reason`: a 402 or 429 outranks a stop and a protocol break (`internal/vocab/exitmap/exitmap.go:54-60`).
   - **Only the upstream's 429 is counted.** The gateway's own 429 (`in_flight_cap`, `serve.go:97`) is never `observe`d, and http-chat classes it `other` by `RefusalHeader`. Neither can raise a hold.
   - **Bounds:** a forged or huge header delays a task at most `quotaWaitMax` (1 h) per 429 (probe 6). Each relaunch spends an attempt of the rail (entry 195), so a provider that keeps refusing reaches `budget_rail` (operator-owned) after the round's attempts.
   - **Early clearing:** a hold cannot clear early. `Until` is fixed from `tx.Now()` at the raise, and only `placer.Unblocked`'s `!tx.Now().Before(Until)` clears it.
   - **The two-command window:**
     - the lease is live between the result's command and the hold's, so no pass places the node;
     - if the hold's command fails, `endAttempt` still revokes the lease, and the node, claimed with an unselected result, is placed again (probe 5): not a stall;
     - a crash in the window does the same through the start sweep;
     - either way the 429's wait is lost and the relaunch is immediate, bounded by the rail, as the PR states.
   - **The #423 catch-all:** `StallOf` counts a claimed or held node as busy (`internal/reconcile/reconcile.go:205`). The window (claimed, lease live) and both holds therefore read as busy, never stalled. That is correct, since none is a stall.
3. **`Offered`** (`reconcile.go:333-334`) still returns `false` for every hold with `Reason` set, except `Hold == quota_reset`. That one is then offered only when `ParseQuotaReset` round-trips the signal exactly (UTC, RFC 3339).

### Medium: OBLIGATION

**M1. `observeReset` (`internal/gateway/gateway.go:600`) is a second copy of `observe`'s "record only while the attempt is bound" rule (`:583`).** It re-implements the lock, the bound scan and the hand-over comment.
- **Effect:**
  - a reuse failure (the rubric's floor is Medium);
  - one 429 is recorded in two critical sections. An `Unbind` between them hands over the 429's status without its reset, so the hold waits 1 min, not the named reset.
- **Fix:** give `observe` the reset as a parameter (zero: none), and call it once per response at `:535`. One lock, one bound check, one record.

### Low: OBLIGATION

**L1. Rows for paths the PR wires but does not test.** Probes 1–3 and 5 show each works:
- **(a) The reviewer row** (answer 4): `TestAProviderRefusalHoldsTheReview`, for 429 and 402.
- **(b) The gate's own image miss:** `wrong_owner` naming the image, held while absent, cleared and completed once it resolves. The accept row exists; the gate shares `checkout`, but nothing pins that.
- **(c) The hold's own command failing:** the node is placed again, never left claimed with no lease. Only the comment states this (`run.go`, `record`'s doc).

**L2. "A podman that never answered is still retried" holds only for the build's launch.**
- **The bound is the launch's alone:** `adapter.go:108-109` wraps a resolve past `resolveTimeout` in `errHost`. `checkout`'s resolve (`accept.go:298`), which accept and the gate use, has no such bound. A hung podman there waits out `acceptBound` (15 min) or `gateBound`. It is then classed `wrong_owner` on the image, assigned to the toolchain image's named owner.
- **Podman errors read as a missing image:** in every path, podman failures (`internal/sandbox/image.go:134`, `:153`, `:160`, for example storage or lock errors) are `ErrImage` and so `wrong_owner`. The row "an image podman did not list" (`run_test.go:473`) makes this the stated rule.
- **Not a regression:** before this PR it was `runner: image`, also not a retry. `imageReady` clears it on the first pass where podman answers, so it is bounded and visible.
- **Fix:** state it in `imageMissing`'s doc and the PR body, or give `checkout` the launch's bound and `errHost` wrapping (one helper for both).

**L3. The reset bound is not monotonic.**
- **Example:** a `Retry-After` 6 days ahead holds 1 h (capped), but 8 days ahead reads as none and holds 1 min (`gateway.go:613-637`, then `quotaWait`). A present but unreadable `Retry-After` also suppresses a valid `RateLimit-Reset` (probe 6). Bounded by the attempts rail.
- **Fix:** read a reset past `maxReset` as `quotaWaitMax`, not as none. Either state the `Retry-After`-first rule, or fall through to `RateLimit-Reset` when `Retry-After` is unreadable.

**L4. The live-run checklist gains two items, untestable here:**
- a real provider's 429 headers (which of `Retry-After`/`RateLimit-Reset` it sends, and in what form), on the live route;
- a `podman pull` of the pin clearing a real `wrong_owner` image hold on the next pass (with #427 L1's empty RepoDigests).
