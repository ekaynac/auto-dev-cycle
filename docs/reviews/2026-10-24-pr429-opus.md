## Opus review of #429, the acceptance overlay (2026-10-24)

Verdict: NO-GO (one BLOCKING, H1; the fix is small and reuses accept's own helpers)

The data flow is complete. The acceptance reaches the gate for every task path, including after a repair round and after a restart. The base is measured without it. A hidden test that fails or never reports is the candidate's. No operator read, reviewer input or builder input carries it.

**H1:** a hidden test the gate can never run is recorded as every candidate's `found/gate_test_failed`. This happens for a hidden test under `testdata/` or `_x/`, one excluded by a build constraint or a `_GOOS`/`_GOARCH` file name, one in a nested module, and every hidden test in a project whose `go.mod` module line carries a comment. Each candidate is then paid repair rounds until the rounds rail stops them.

There are five Medium and two Low obligations.

Scope: `wt-r429` (b5079a5 on main 7ae3926d), `git diff 7ae3926d..HEAD`. Everything ran in a `/tmp` copy with its `.git` removed and `TMPDIR` unset, one at a time with `-race`. Probes ran only in that copy and in a scratch module under `/tmp`; all are deleted. The live rows were not run.

### 1. Does the acceptance reach the gate? Yes, on every path.
**Operator input to the gate's check (production wiring):**
1. `adc task create --attach REPO_PATH=FILE`:
   - `internal/cli/cli.go:144-152` splits the value on `=` and checks the path against the schema's `AcceptancePath` (`:42`). A bare FILE or a duplicate path is refused before any upload.
   - `:183` lists `{name: REPO_PATH, digest}`.
2. The server's `task.create` scope already requires `AcceptancePath` (`schemas/api/scope/task-create.json:21`). `authority.acceptanceOf` (`internal/authority/task.go:250`) records it in `Task.Acceptance`, and `Uploads.Publish` puts the upload into the same store as the runner's `r.blobs` (`internal/daemon/wiring.go:161`).
3. The gate run:
   - `gating` reads the task's record in the claim's snapshot, `authority.TaskOf(tx, g.view.Task)` (`internal/daemon/gate.go:273`);
   - `gateNode` calls `overlayOf` (`:156`) and sets `in.Overlay` only for `gate.Run` (`:179`), after `gate.Measure` (`:162`);
   - in `gate.run`, `overlayTests` adds the expected tests (`internal/gate/gate.go:196-203`), `writeFiles` places the files (`:204`), and `ParseGoTestJSON(…, expected, …)` (`:241`) marks an unreported expected test `missing`, which `judge` counts as the candidate's (`x.Expected`).
4. The result derives from the acceptance: `gate.Subject{Acceptance: digests}` (`internal/daemon/gate.go:201`).

**Every task path:**
- A repair round's gate reads the same task's record through its own node (`g.view.Task`).
- A restart re-reads the store.
- Any API client goes through the same `task.create` handler.

**Rows, all ok:** `TestTheGateOverlaysTheAcceptance` (pass, fail and never-reports, each with `noLeak` after a restart), `TestTheGateRefusesAnAcceptanceItCannotOverlay`, and `internal/gate` `TestGateOverlaidTestsAreExpected`.

### 2. Can the candidate defeat or read the overlay?
**What fails closed** (the hidden test is not reported, so it is `missing`, which is the candidate's):
- `TestMain`, a `-test.run` or `-test.skip` set in the candidate's code, or an `os.Exit` in an init: the hidden test never reports, so it is missing.
- A changed package name, or a removed or renamed package directory: the package does not build.
- A nested `go.mod` or `go.work` the candidate adds.

**What is replaced:** a file or a link the candidate put at the hidden path is removed first (`writeFiles`, `internal/gate/gate.go:568`), and the base is checked to hold nothing there (`overlayOf`).

**Forgery:** the gate trusts the stream.
- I wrote a helper package whose init reads `*_test.go` in its working directory, builds the 0x16 marker at run time, prints `=== RUN`/`--- PASS` for every test it finds, and calls `os.Exit(0)`. Under real `go test -json`, it made a wrong `Sum` pass `TestHiddenSum`. `ParseGoTestJSON` with that test expected read it as pass, green and clean.
- The defence is accept's guard, and it holds. I put the same code in a dependency of a tested package, and as the hidden test's own new package with no visible tests. Both were **blocked**: "unverifiable: the package's initialization (tests included) reaches a call it cannot resolve", plus warnings on `os.Exit`, `os.Args` and `os.Stdout`.
- The gate rebuilds only the guarded accepted tree (`gateNode`'s rebuild check), so this holds. It is worth one sentence in the gate's comment: the overlay's guarantee rests on the guard.

**Reading the hidden bytes:**
- The builder: never. A build takes plan, review and patch only (`internal/daemon/wiring.go:187`).
- The reviewer: never. It sees the gate's verdict and counts (`internal/review/prompt.go:23`, `:101`), and `Why` holds only counts (`internal/gate/gate.go` `whys`).
- The candidate's code can read the file inside the gate sandbox, which has no network. Its outputs are the restricted stream and the report, whose lineage withholds them.

### Findings
- **H1** (BLOCKING, High: a fault that is not the candidate's, recorded as the candidate's; the rubric's recurring class, paid rounds): `overlayTests` expects every declared top-level test, but four placements that `go test ./...` never builds go undetected. I confirmed each with real `go test -json`; none is reported:
  - a hidden test under `testdata/` or a `_`-prefixed directory (`AcceptancePath` allows both);
  - a file excluded by a `//go:build` line or a `_windows`/`_arm`-style name in the gate environment;
  - a directory inside a nested module of the base;
  - a base `go.mod` whose module line has a trailing comment. `checkout` returns `example.com/m // c` as the module (`internal/gate/gate.go:501-503`), so *every* expected package is wrong and every hidden test is "missing".

  Each yields `found/gate_test_failed` for every candidate. The builder learns only counts, so repair rounds are paid until the rounds rail stops them, and the operator sees a candidate failure, not a task fault.
  
  **Fix**, in `overlayOf` before any run, held as the task's (`errContent`, "runner: failed"):
  - refuse a hidden `_test.go` whose path has a `testdata`, `vendor` or `_`-prefixed segment;
  - refuse one that `build.Context{GOOS, GOARCH: the environment's runtime}.MatchFile` excludes (reuse accept's pattern);
  - refuse one with a `go.mod` in a directory between it and the root (the `cat-file` batch already walks those directories);
  - read the module with `modfile.ModulePath`.

  Add a row per case.
- **M1** (OBLIGATION, Medium): an acceptance that declares no test the gate expects passes on the visible tests alone, yet its result claims derivation from the acceptance. This covers only non-Go files, only `Example`/`Fuzz`/`Benchmark` functions, or a `T` that is dot-imported. That is the pre-PR gap, silently. For a `go_test_json` gate, refuse an acceptance whose `_test.go` files declare no expected test (data files beside one stay allowed), or state it.
- **M2** (OBLIGATION, Medium; recurring class: an unreadable read): `overlayOf` wraps *any* `readBlob` error as `errContent` (`internal/daemon/gate.go:301-303`), so a transient I/O error in the blob store ends the task on the terminal `runner: failed`. Accept reads the patch through the same `readBlob` and retries (`internal/daemon/accept.go:241`). Uploads are digest-checked at upload, so a later missing or mismatched blob is the store's. Use a plain error, the bounded retry, and keep the row's "blob not in the store" ending `runner: failed` after `maxTries`.
- **M3** (OBLIGATION, Medium): a candidate's directory at the hidden path, or a file where its parent directory should be, fails `writeFiles` with a plain error. My probe gave `removeat …: directory not empty` and `mkdirat c: file exists`, both non-`ErrSpec`. The daemon reads that as the host's (`notRun`, five retries, then `runner: failed`), with no repair. `overlayOf` has already shown that the base holds nothing there, so anything there is the candidate's. Use `root.RemoveAll` on the leaf, and replace a non-directory parent, or report the hidden test as missing (the candidate's).
- **M4** (OBLIGATION, Medium): launch has been active since #423, and tasks recorded since then with `--attach FILE` carry base names. At this head their acceptance is overlaid at the repository root. A Go `x_test.go` there either clashes with the root package, so every candidate gets `found`, or names a base file, giving a terminal hold. State it in the PR and changelog (re-create such tasks), or check the live store's tasks before merging.
- **M5** (OBLIGATION, Medium): name the hidden-test residuals the gate cannot detect. A hidden test in the package's own (internal) test package can collide with a candidate's identifier, and it fails to compile as the candidate's; recommend external `_test` packages. A hidden test needing anything the gate environment lacks (network, a module not in `go.sum`) is likewise the candidate's. State both in the slice plan's `--attach` step.
- **L1** (OBLIGATION, Low): an acceptance test that does not parse, or a candidate tree with no root module, is `ErrSpec`. That maps to `errConfig` and the hold `runner: profile <digest>` (`internal/daemon/gate.go:182-184`), which clears only on a profile change and does not fix it. Make the acceptance's parse failure `errContent`, the task's. A candidate that removed a module the base has should be the candidate's `found`.
- **L2** (OBLIGATION, Low): in the gate's comment and in the I12/I13 rows, state that a hidden test's result is only as sound as accept's forgery rules. The gate reads the stream as written: my forged stream was green, and the guard blocked the same code at accept.
