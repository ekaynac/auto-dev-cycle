### Findings

**Medium. The fold re-runs the live profile schema and `profile.Check` on every replay, so the first tightening of the profile schema wedges every store holding a project.**
`internal/authority/project.go:472`. `addProject` calls `profiles.Load(ev.Payload)`, which validates against the current `config/project-profile` and runs the semantic checks. The notes fold decodes with `json.Unmarshal` only (`internal/authority/notes.go:129`). The store validates payloads at append only (`internal/eventstore/store.go:526`), so this fold is the only replay-time validator. Slice plan §2.6 says P17 "adds the cap fields to the schema"; every top-level profile key is currently `required` with `additionalProperties: false`, so if P17 follows that convention, every stored `project.created/v1` refuses replay and `checkProjections` refuses start with `ambiguous_state` (`internal/daemon/startup.go:126`). The frozen golden fails CI first, so this is a trap rather than a live defect, and the threat it defends against (a fabricated event) is out of scope until M7-S.
Fix: in `addProject`, decode only what the record needs (`id`, `name`) with `json.Unmarshal`, keep the subject, project, actor and duplicate checks, and leave `profile.Load` at command time. If re-validation is wanted, validate against a frozen copy of the v1 schema. Keep `TestProjectCreatedV1Replays` either way. Add a line to the P17 row: profile additions are optional for stored v1 events.

**Low. `Derive` validates the whole profile before checking the actor kind.**
`internal/authority/project.go:391-397`. A system actor, or any future kind, gets the full schema and semantic pass and its messages before the `actor_kind_refused`. No leak, but the cheap check belongs first. Fix: move the kind check above `profileOf`.
