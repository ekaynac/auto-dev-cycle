## High

### H1. Claim-numbered test ids and the product phase id remain, which contradicts the README rule
- `closure-record-finding-r4/closure-record-finding-r4.json:17`: `tests/test_<claim>_labels.py`
- `closure-record-finding-r4/closure-record-finding-r4.json:26`: `test_<claim>_no_raw_thread_or_executor_hops`
- `f16-walk-demand/packet-1524-5eed002400000000.json:7` and `packet-1538-5eed002a00000000.json:7`: `"phase": "<phase id>"`
- **Problem:** `README.md:63-64` says claim-numbered test names lose the claim number. The anonymiser did this only for
  the edge log (`test_<claim>_*` → `test_*`). The closure record keeps two product claim ids (two
  claim-numbered names). Together with `"phase": "<phase id>"`, these are the product roadmap's ticket-like ids. `TASK-0001`/`TASK-0002`
  were introduced to hide exactly this.
- **Failure scenario:** someone who knows the product links TASK-0002 back to its original task id and its claims. The README's
  anonymisation claim is also false as written, so later reviewers will trust it and skip checking.
- **Fix:** rename them to `tests/test_labels.py` and `test_no_raw_thread_or_executor_hops`. Set `phase` to a neutral
  value (e.g. `"1"`) or drop it, because no golden step depends on it. Extend the scan with the claim-id pattern and
  `"phase"`.

### H2. Product component names and the product CLI remain in the closure record (the operator decides whether this is Critical)
- `closure-record-finding-r4/closure-record-finding-r4.json:8-11,17`: <component names and module paths
  (six), a registry constant, three principal names, and a product CLI verb> (listed in the original review; redacted
  in this copy).
- **Problem:** only one storage module (→ `keystore/`) and the package name were replaced. The other product components are kept
  verbatim. The review brief lists "product name or its components" as identifying. They do not name the product, but
  together they fingerprint its architecture for anyone who has seen it, and the repository is meant to go public.
- **Failure scenario:** the public repository ships the internal module map and principal names of a private product.
- **Fix:** replace them with neutral names that keep the class intact (e.g. components → `module-a`…,
  principals → `principal-a…d`, the CLI verb → `rebuild-all`). The golden depends only on
  `surface: closure`, the absolute non-repo path in the remedy, and P2/P3 severities, so nothing in `expected`
  changes. If the operator considers the product's internals confidential, treat this as Critical.

## Medium

- **Problem:**

- **Failure scenario:** a T0 loader cannot derive `candidate_owned_setup_error` from the artifacts. It hardcodes the

  - Correct the note: the FAILED test is the same environment-fact mismatch, surfaced in the call phase.
  - Optionally add a `variants` list for the untouched-file case (expected: a runner-fault hold).

### M2. `f16-inline-fallback`: the scope that makes the fallback out of bounds is not in the data
- `f16-inline-fallback/golden.json:3,15`; `usage.json` (`mode: "process"`, `authorization: "2026-09-18"`).
- **Problem:** `fallback_scope` (note 05) compares the chain entry's authorised **role and mode** with the lease's role
  and mode. No artifact records that the openrouter/glm route is authorised only for a learning digest. That fact comes
  from the golden's prose.
- **Failure scenario:** the T0 loader has to invent the chain configuration, so the golden does not prove the refusal
  from data. A loader that defaults to "authorised" yields only step 1 and passes silently.
- **Fix:** add a synthetic `inputs.fallback_chain` entry, e.g.
  `{route: fallback, provider: openrouter, model: z-ai/glm-5.3-flash, authorised_for: [{role: learner, mode: learning_digest}]}`,
  plus the lease's `role/mode` (`reviewer/phase_review`).

### M3. `f16-walk-demand` step 4 depends on an unstated definition of the demand key
- `f16-walk-demand/golden.json:18`; `walk-1790902623…json:53` (`review_event …-5eed0036`) vs `walk-1790943778…json:53`
  (`…-5eed0037`).
- **Problem:** the two "same plan" walks were made for different review events. Note 06 rule 2 and the M0C fixture
  "a receipt for another demand with identical conclusions does not apply" forbid reuse across demands. Note 13 reuse
  equivalence also requires the same demand. Step 4 (`empty/conclusions_unchanged`) is right only if the demand key is

  Also list it under "Open points for the vocabulary PR" with the grant-rebind question.
