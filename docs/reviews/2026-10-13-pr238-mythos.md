### Judged questions

1. **Stale revisions.** Closed on every path. Logic: `answerable` (`answer.go:135-161`) requires the current revision and no answer in force. Forged event: `recordAnswer` runs `answerable` on the scope's revision, then independently requires scope revision, `object.version` and `expected_state.version` all equal to the owed input's, loads the owed input by the scope id, and requires `answers == [scope.owed_input]`, so a scope/object mismatch is refused. `Answers.Answer` and `Approval` require the current revision and `answerInForce`, which also requires `o.Answer.Revision == o.Revision`; `recordOwed` writes a new revision with `Answer: nil`. Replay reads liveness, revision and the duplicate id from projections at the event's log position under `ProjectEach`, so a rebuild reaches the same records. `--expect` as the revision works because `Derived.Version` returns `o.Revision`; X6's `R=0` with `--expect 1` is refused by the logic as `stale_expected_state`.
2. **Authority.** Correct and complete for P5. `answerable` refuses anyone who is neither an operator nor the owner, shared by logic and fold, so no non-owner supervisor can answer even under a covering grant (tested, logic ran, nothing recorded). An owner supervisor still needs a covering grant and the seat. Merge approval stays out: nothing lets a supervisor answer an operator-owned input, which is the seam P28 needs. The grant is recorded as Decide chooses it (same inputs, deterministic sort), nil for an operator, and the fold requires one exactly for a supervisor. A later grant revocation leaves the answer in force because `answerInForce` reads only the actor's `RevokedAt`, consistent with applied proposal approvals and P3. See L1 for the fold's weaker coverage check. No existence oracle: `Derive`'s refusal for an unknown id is byte-identical to `supervisor()`'s for an uncovered project, and the test compares the whole `Refusal`.
3. **Binding.** Yes: owed id (scope, object, answers), revision (scope, object, expected_state), project (event and approval, equal to the owed input's). Node binding runs through `requested_by` and the graph's lineage check, where note 13 puts it. `recordApproval` checks subject and actor before the dispatch; a proposal-bearing approval with this action can only land as a proposal approval, which `Answers` never reads.
4. **Replay.** The fold reads `{owed_input, owed_revision}` with plain `json.Unmarshal` and never runs today's schema over a stored scope. The golden with an extra scope field replays. Startup is protected on the operator path; see L2 for the supervisor path.
5. **`graph.Authority`.** `await` raises `awaiting_input` on `<owed>@<rev>` with the owed input's owner, and `clear` plus the claim happen in the same evaluation once `Answer` returns the approval. A revoked or replaced answer never reaches a model input: `Answer` and `Approval` both require the answer in force at the current revision for a node that declares it, `renderContext` calls `Approval` at render time, `revalidate` re-runs `answers()` at commit, and `answeredNow` at reuse. `Owed` excludes `receipt`, so a successor declaring one is `ErrNotOwed`.
6. **Inert.** No handler in `handlers()`, no logic in `logics()`, the matrix keeps the action deferred, and `TestInputAnswerStaysDeferred` drives the installed CLI to `action_deferred` with nothing appended. Kind and projector are registered, so a store written by P6 later replays on today's binary.
7. **Contract changes.** All sound. `records/owed-input` had no producer or consumer; `requested_by` as a node is what 13's lineage needs, and `project` and `owner` are what the hold and the fold need. `--expect` as the revision is consistent because the scope must match too. `owed_revision` minimum 0 is harmless since 0 is never a current revision. Receipt refusal: see L3.
8. **Fault evidence.** Discriminating: M1 to M3 each hit one layer, and each review mutation hits exactly its fix. Two Low gaps: no mutation exercises the fold's grant coverage (L1), and no supervisor golden (L2).
