### 1. Can a candidate be accepted without the guard verifying it? No.
- **A hung or killed child:** past the guard's own 10 minutes it becomes an `unverifiable` block (`test_integrity_violation`). A cut at `acceptBound` makes the guard return `ctx.Err()`, which is recorded as `could_not_run` and never selected. A binary that does not dispatch the child is also `unverifiable`.
- **A failed `go list`:** refused `test_integrity_violation` (row).
- **A missing patch, checkpoint or brief blob:** an error before `Accept`, so the node is held and nothing is recorded.
- **The wrong base or another build's patch:** the input is the result the claim fixed (`graph.ClaimInputs`). The base is the base of the attempt that recorded that result, which is the base the runner diffed against. A result that is not `patch`, or has no attempt, is refused as `errContent`.
- **An empty build:** no patch, so the base itself is accepted, with the guard run over no changes.

### 2. Is it exactly the build's patch on exactly its base? Yes, by the claim's input and the attempt's base. On the integrity of the blob bytes, see L1.

### High

**H1 (BLOCKING). A runner hold on an accept node never clears, so the task is stuck for good.**
- `Observe` collects held nodes for Unblock only when the kind is in `Placed`, which is the build only (`internal/reconcile/reconcile.go:333`).
- `accept.go` holds an accept node with the runner's `holdOn` (`retry n until t`, `dirs`, `profile`) on every failure path. No pass ever offers those holds to `Unblocked`. So the promised bounded retry never happens, the claimed node stays held, and the admitted task keeps the only admission slot until its approval is revoked.
- **Probe:** the image misses once (`runner_fault`, `runner: retry 1 until t` with `retryBase` of 200 ms). Then the image resolves, the time passes, and I ran 8 passes. The result: **still held, same hold, no result.**
- With `n.Node.Kind == types.NodeKindAccept` added to that case, in the copy: the hold cleared and the next Accept recorded a selected result at the same claim. The node **completed**.
- `TestAFailedAcceptRunCouldNotRun` checks only that the hold is raised, so it never exercises the retry.
- **Fix:** collect runner-signal holds on accept nodes, for example a `ControllerRun` kind set `{accept}` next to `Placed`, used for the held case only. Add a row: a transient failure, then the time passes, then a pass, then the node completes.

### Medium

**M1 (OBLIGATION). A race between the build's result and its seal gives a false hold.**
- The runner's `record` commits the build's result (`CommitAttempt`) and seals the attempt in **separate** commands, commit first (`internal/daemon/run.go:789`).
- The selected result completes the build, so a loop pass in between can claim the accept node and start its run. `acceptance` then finds `checkpoint == nil`, "the build's attempt is not sealed" (`accept.go:211`). That is classified as transient and held `retry 1` for a minute; with H1 unfixed, for good. [INFERENCE: not reproduced. The tests wait for the run before the next pass.]
- **Fix:** treat "not sealed yet" as a no-op (return without a hold; the next pass retries), or decide Accept only once the input's attempt is sealed.

**M2 (OBLIGATION). `runner_fault` is the wrong reason for accept's failures** (`accept.go:259`).
- Its registry entry is a **gate** domain reason, "Gate output that is not candidate-owned", and it names the hold `wrong_owner`.
- Accept records it for:
  - a clone failure (network or URL);
  - an image miss (configuration);
  - a guard cut at the bound (unverifiable).
- Meanwhile the node is held `source_invalid_config`, a different hold from the one the reason names. Anything that later maps reason to hold (`graph.Retry`) gets the wrong hold.
- **Fix:** register an accept-domain could-not-run reason (or reuse `ambiguous_state` / `store_unreadable` by case) whose hold matches the runner's. Classify the image miss and an unreachable repository as configuration (`errConfig`), not transient.

### Low (OBLIGATION)

**L1. A blob is not checked against its digest.** `runner.readBlob` (`accept.go:226`) reads the patch and the checkpoint by digest through `blobstore.Open`, which does not re-hash. A blob damaged on disk would be applied as the "recorded" patch. The store is the controller's own, so this is defense in depth.
- **Fix:** hash the bytes and compare, as `intent.readBlob` does.

**L2. Which image is used is unchecked** (`accept.go:120`). `Toolchain.Images` is a map:
- with two images, which one `go list` uses depends on map iteration order;
- with none, `Resolve("")` is a `runner_fault`.

Placement refuses two images only for builds.
- **Fix:** refuse anything other than exactly one image as `errConfig`, as the placer does. This also answers the builder's open point on the single pinned image.

**L3. Nothing mutates the `Acceptor` wiring** (`internal/daemon/wiring.go`: `x.Runner, x.Acceptor = run, run`).
- **Fix:** a wiring row (for example, `reconciler(…)` with a runner gives an executor whose Acceptor is that runner), so that dropping it is killed.

**L4. A failed hold write can spin.** If `couldNotRun`'s command is refused, for example because `graph.Commit`'s revalidation fails, no hold is written. The Accept action itself returned nil, so the loop nudges and starts a new clone and accept straight away. [INFERENCE: not probed; it needs a persistent commit refusal.]
- **Fix:** if the commit is refused, still write the hold alone, as the build path does since round 3.
