# PRs #95 and #96 (WebAuthn): Astra reviews

## Review of #95 and #96 (Astra, 2026-10-05)
Verdict: GO with changes

No Critical/High findings under D43. The core authorization boundary holds; the findings below are nonblocking.

1. **Medium — PR #95: client-data parsing accepts malformed security fields.**  
   `internal/authority/webauthn/webauthn.go:102–118`: signed probes accepted uppercase `"TYPE"`, duplicate `"type":"webauthn.get","type":null`, and `"crossOrigin":null`. Go’s struct decoding supplies case-insensitive matching and null-handling semantics that are inappropriate here. Challenge decoding also accepts embedded newlines and nonzero base64url padding bits.

   **Fix:** parse security fields with exact names, enforce their types, and reject duplicate security fields while allowing unknown extension fields. Compare the challenge string against its canonical unpadded base64url encoding. Preserve the original bytes for hashing. These are verification-contract defects, but changing an intercepted assertion this way still invalidates its signature.

2. **Medium — PR #96: replay coverage does not prove challenge single use for counterless credentials.**  
   `internal/fixtures/webauthn.go:134–138`: replay fails because counter `1` does not advance past stored counter `1`; challenge consumption is never reached. Removing the used-challenge check would leave this fixture green. The verifier’s zero-counter test only exercises `Verify`, where repeated zero-counter assertions correctly remain acceptable.

   **Fix:** add a counterless confirmation/replay sequence, plus an isolated used-challenge refusal with an otherwise-open proposal. Assert the intended refusal explicitly: a normal replay against the confirmed proposal currently produces `proposal_not_open` once the counter check permits it. Update the golden invariant to include the documented 0/0 exception.

3. **Medium — PR #96: “refusals consume nothing” is only partially asserted.**  
   `internal/fixtures/webauthn.go:32–37`, `:162–167`: the helper discards returned state on errors, and the final successful assertion has an advanced counter. Thus an erroneous counter advance during a refusal could escape the fixture’s checks. Final proposal/challenge checks do not establish unchanged state after each refusal.

   **Fix:** snapshot proposal, challenge, and credential before every refused step and compare afterward, including `SignCount`. Check the final successful counter too. The current implementation is safe by inspection; this finding concerns the claimed regression protection.

4. **Low — PR #95: authenticator-data structure and backup flags are unchecked.**  
   `internal/authority/webauthn/webauthn.go:119–132`: signed probes with AT or ED set but no corresponding data, trailing bytes without either flag, and BS set without BE all passed.

   **Fix:** define M0’s extension policy and validate the corresponding structure. Reject AT for assertions; either parse supported extension data or explicitly refuse it. For modern backup support, reject BS without BE and bind BE to registration metadata. Backup checks belong to later WebAuthn revisions, so their absence is not itself a Level 2 violation. [WebAuthn authenticator-data rules](https://www.w3.org/TR/webauthn-3/#sctn-authenticator-data)

5. **Low — PR #95: the raw assertion contract omits `userHandle`.**  
   `internal/authority/webauthn/webauthn.go:65–70`: credential ownership is checked correctly, but the API cannot validate a supplied user handle against that owner, as §7.2 requires.

   **Fix:** carry the optional handle and validate it against the registered account mapping when that record lands. This does not currently permit impersonation because credential ID, registered key, and confirmer ownership remain checked. [WebAuthn Level 2 §7.2](https://www.w3.org/TR/webauthn-2/#sctn-verifying-assertion)

6. **Low — PR #95: `Static` freezes the counter rather than guaranteeing zero.**  
   `internal/authority/fakeauthn/fakeauthn.go:75–79`: enabling it after an assertion emits the previous nonzero count, contrary to its “always zero” documentation.

   **Fix:** emit zero in counterless mode, or separate counterless and frozen-counter fault modes. Existing tests initialize it early and therefore miss this discrepancy.

The remaining checks are sound: challenge construction matches #95’s additional documentation commit; origin and RP hash comparisons are exact; UP and UV are mandatory; counter advancement and the 0/0 exception are correct. Rejecting `crossOrigin:true` prevents conforming cross-origin ceremonies, so accepting such ceremonies through an unchecked `topOrigin` is not a demonstrated bypass.

SPKI parsing, P-256 restriction, ES256 hashing/DER verification, and Ed25519 verification are appropriate. ECDSA’s alternate valid S value does not bypass replay protection because consumption tracks the challenge, not signature bytes.

`ConfirmHuman` verifies before constructing consumed state and returns no updated records on refusal. Credential/confirmer ownership, allowed-confirmers membership, operator kind, and revocation checks are correct. Registration, credential persistence, and RP configuration are acceptable M0 follow-ups, provided production integration obtains them from trusted server state and persists confirmation, challenge consumption, and counter advancement atomically.

The fake faithfully signs the principal RP/origin/UP/UV faults. Expiry and the other advertised fixture refusals execute. The signature mutation is realistic and red for the intended reason: step 5 wrongly confirms; the final confirmation then encounters an already-confirmed proposal.

Both requested test commands passed using Go 1.27.1, `GOTOOLCHAIN=local`, and `scripts/test-sandbox.sh`. Additional sandbox-only overlay probes confirmed the findings above. Checkout files were not modified.
### Lead notes on round 1 (applied)

- Medium 1 (#95, client data): clientDataJSON is read as one JSON object token by token. `type`, `challenge` and `origin` must be strings and `crossOrigin` a boolean if present, under their exact names, each at most once. `topOrigin`, trailing content and a missing security field are refused; unknown extension fields are skipped. The challenge string is compared with the canonical unpadded base64url encoding of the expected bytes, so embedded newlines and nonzero padding bits are refused. The original bytes are what gets hashed. Signed probes cover each case (uppercase `TYPE`, a repeated `type`, null `type` and `crossOrigin`, `topOrigin`, trailing content, newline and non-canonical challenges) and an accepted extension field.
- Medium 2 (#96, single use): the fixture adds a counterless credential that confirms one proposal and then replays against it; with the counter at 0/0 the refusal comes from the challenge (the proposal is confirmed, so `proposal_not_open`). It also adds an isolated used-challenge refusal on an otherwise-open proposal: a fresh assertion answering an already-used challenge is refused `confirmation_refused`, and that refusal's detail is asserted. The golden invariant names the 0/0 exception. Removing the used-challenge check turns the fixture red (checked locally, then reverted).
- Medium 3 (#96, nothing consumed): the fixture snapshots the proposal, the challenge and the credential (`SignCount` included) before every refused step and compares them after. It also checks the counter after each successful confirmation.
- Low 4 (#95, authenticator data): M0 supports no extensions. An assertion with AT or ED set is refused, and so is authenticator data longer than 37 bytes or BS set without BE. BE is not yet bound to registration metadata, because no credential record exists; that binding lands with the record.
- Low 5 (#95, user handle): the raw assertion carries the optional `UserHandle`. Until a credential record maps handles to accounts, `webauthn.Credential.UserHandle` stands for that mapping: a present handle must equal it, and an absent one is accepted.
- Low 6 (#95, fake counter): `fakeauthn.Counter` separates `Counting`, `Counterless` (always 0, even after counting) and `Frozen` (repeats the last value). Unit tests switch modes mid-sequence.
