### Medium

**M1. One bad card fails the board for every reader, including readers who cannot see that card** (`internal/api/board.go:58-91`, `internal/api/reads.go:76-88`).
- `List` derives every card before `ReadsRecord` filters by project and domain. So one task in project A that cannot be derived makes `/v1/board` return 503 for everyone.
- I tried these grant combinations, each with a node recorded on A's Ready task:

| Grant | `/v1/board` | `/v1/holds` |
|---|---|---|
| `board` on A | 503 `store_unreadable` | 200, empty |
| `board` on B only | 503 | 200, empty |
| `hold` only on A (no `board` grant) | 503 | 200, empty |

- With healthy records, the same grants behave correctly: `board` on A sees A's card only, `board` on B sees B's only, and `hold`-only sees an empty board.
- The 503 body is generic, so no detail leaks. But a reader scoped to B, or a reader with no `board` grant at all, learns that something elsewhere is damaged, and loses the board they are entitled to.
- During an incident the operator also loses the whole board. That is when they need it most.
- F requires that a card is "never placed" in a guessed column. It does not require hiding the rest of the board.
- **Fix (pick one):**
  - (a) Filter tasks by scope before deriving them. Attribute an orphan node to its own recorded project. A reader whose scope does not cover the damaged record then gets a normal read.
  - (b) Better for D51: keep the good cards and return the bad one as an "unplaced" entry with no column and a coarse reason, visible only to readers whose scope covers it. A column is still never guessed, and the operator keeps the board.
- This cannot happen until P22a, so it can land here or be a tracked P22a precondition. It should not be left implicit.

**M2. `store_unreadable` is not the honest reason** (`internal/api/reads.go:173`).
- The store is readable. The records are inconsistent with each other. An operator who sees "the event store could not be read" will start checking disk and permissions.
- **Fix:** use the existing `ambiguous_state` reason, which `CheckHistory` already uses for records that disagree with each other. Or record a backlog item for a dedicated reason. Either way, say so in the PR's deviation 4.

### Low

**L1. Cross-domain disclosure (the scan finding): real, but it is the plan's design** (`internal/api/board.go:184-185`, `schemas/api/board.json`).
- A `board`-only grant on project A will, after P22a, show A's hold `id`, `hold`, `signal_instance`, `owner`, `owner_ref` and `since`, without any `hold` grant.
- It does not show the hold's `reason`, `escalate_to`/`escalate_ref`, `page_after` or `pages`.
- Today no hold badge can appear at all: any node makes the read fail (M1's table), so nothing leaks yet.
- There is no `task` read domain or resource yet (`task show` is P22a). So task state and approval are not hidden behind any other grant today.
- Project scoping is sound: a card's project is re-read from the task record, and a node in another project fails the card (`board.go:149`).
- Of the three fixes offered:
  - Requiring `hold` (and a future `task`) grants as well contradicts the P4b row and 01 §2.2. Its card schema explicitly carries "hold owner and signal" and approval digests, and granted supervisors are expected to read the board.
  - Making `board` operator-only contradicts the same section.
- **Fix:** document `board` as an intentional summary that reaches into the task and hold data of the projects it covers. Put this in the `board.go` header and the `board.json` description, listing exactly which hold fields appear and which are withheld. Add a test that pins the badge's field set as a strict subset of `api/hold.json`.
  - Optional: redact `owner_ref` (an actor id or named owner) unless the reader's scope also covers `hold`.
  - When P22a adds the `task` domain, record how `board` relates to it.

**L2. Possible false "done (candidate)"** (`board.go:160-161`).
- A review that completed GO counts while it is unsuperseded. This depends on a repair superseding the earlier review.
- The tests cover a superseded go review and a claimed repair build. They do not cover a repair build that has completed while a new gate is merely waiting or runnable. If the old review is not yet superseded at that point, the card reads done_candidate.
- **Fix:** add that case, or require the GO review to be in the task's latest round.

**L3. Fragile index skip** (`board.go:73`): `strings.Contains(k, "/")` skips the `ready/` and `approver/` index keys by string shape.
- **Fix:** export the index prefixes from `authority`, or a `TaskIDs(tx)` helper, and use them here.

### Answers to the seven questions

1. **Derivation.** Columns come only from the task record, approval status, node kind and state, and the selected result's outcome. Every example in the row is matched. Unknown task state, unknown approval status, a deferred kind, a cross-project node, an undeclared wait and an orphan node all fail rather than get a column.
   - Treating GO as outcome `empty` matches 06 rule 4 and 13:598.
   - "accept counts as Verifying" is sound: in the (a) template, accept sits between build and gate and checks the candidate. Leaving it out would make the (a) flow underivable.
   - The only soft spot is L2.
2. **Confidentiality.**
   - No attachment names or digests, spec digest, requirement, or hold `reason` or pages appear. The schema is closed, and `TestBoardRead` checks the body.
   - Errors reach the client only as a generic 503. Server-side error text names node ids, kinds, projects and input names, never acceptance data.
   - An accept node waiting on an input that is neither a result nor an answer fails the read rather than show it.
   - Grant and project scoping are correct for cards (see the grant results under M1). The cross-domain point is L1.
3. **Failure mode.** Failing closed is defensible for F, but failing the whole read for everyone, including readers who cannot see the bad card, is too broad (M1). The reason code is not honest (M2).
4. **`TaskAdmitted`.** Unreachable today. The only writer of task state is P3's fold, which writes `ready` (`task.go:186,276`). `graph.Record` outside tests runs only in `internal/fixtures`, which uses temporary stores.
   - So "any node on a Ready task fails the read" is safe until P22a, and it is the right guard.
   - P22a must write exactly `"admitted"` in the same fold that records the nodes, or the board will 503.
5. **`Resource.List` signature change.** Purely mechanical. All six existing resources and the two test helpers ignore `now`, and the one call site passes `Events{Now: h.Now}.now()`. No behaviour change.
6. **Fault evidence.** It discriminates. `TestBoardUnderivable` covers six cases, `TestBoardRefusesAnUnderivableCard` covers two at the API level, and `TestBoardCommand` covers the CLI exit. The four mutations listed in the PR each turn a named test red.
7. **Size and deviations.** About 330 lines of hand-written production code against a ~300 budget and a 500 ceiling: acceptable. Deviations 1, 2, 3, 5 and 6 are acceptable. Deviation 4 should change its reason (M2) and narrow its failure (M1).
