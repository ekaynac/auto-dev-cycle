### High

**H1. The acceptance test is only in the lead's private store, so the CI stub cases this fixture exists for cannot use it.**
- **Where:** `fixtures/m1/go-mini/README.md:15-17`, `fixtures/m1/go-mini/task.json:5-7`.
- **Why it breaks:**
  - #226 entry 94 makes go-mini the project for checkpoint (a)'s CI stub cases. Those run as `make installed-cycle-stub`, which is part of `make ci` (`docs/design/m1/00-slice-plan.md:450`).
  - To create the task, CI has to upload the attachment's bytes (P2/P3). CI cannot read the lead's store, so no stub case can create this task or overlay its acceptance test.
  - The slice plan's rule is `docs/design/m1/00-slice-plan.md:425-432`: build the base remote from the fixture's `repo/`, and use the task's committed `hidden/` files as its acceptance tests.
- **The "as #170" reason does not apply:**
  - #170's target is this repository itself, so anything committed would reach a builder's clone. go-mini's remote is built from `repo/` only. A sibling `tasks/<id>/hidden/` never reaches a builder, which is exactly how T0 works.
  - The stub provider's scenarios have to contain a passing patch anyway (`00-slice-plan.md:422`), so the reference change cannot stay private.
  - In stub mode the canary only proves that the controller does not forward the acceptance blob, and T0's canaries are public.
- **No CI check:** nothing in CI proves "fails at base, passes with reference". The builder did not rerun it after the header edit; the check is reproducible only by the lead. (I reran it; it holds today.)
- **Fix:** commit the test and the reference change using T0's layout: `tasks/<task-id>/{task.json,hidden/money/accept_test.go,reference.patch}`. Cover it with a `check.sh` so `fixtures-check` proves well-formedness, or reuse `fixtures/t0/go-mini` (M1). Keep the digest in the m1 `task.json`. Keep a private store only for live targets like #170.

### Low

**L1. The baseline's `image_id` is checked against itself.**
- **Where:** `internal/gate/gomini_test.go:70`. The test builds `sandbox.Image{ID: b.ImageID, OS: b.OS, Arch: b.Arch}` from the baseline, so `in.check` compares `image_id` with itself. The pin string and the OS/arch are bound (`:71`, and the profile's runtime). The platform image ID is not: changing `image_id` alone still passes, which I confirmed. #170's row has the same gap.
- **Fix:** assert `b.ImageID` against an independent record of the pin's arm64 ID. `fixtures/m1/issues/170/baseline.json:14` holds one, or use a constant.

**L2. The profile row requires a pin that #226 entry 97 has already decided to replace.**
- **Where:** `internal/profile/gomini_test.go:38` requires `p.Toolchain.Images["go"] == self.Toolchain.Images["go"]`. #226 entry 97 decides that go-mini gets its own prepared image before 22a-5, because `CheckManifest` (`internal/sandbox/image.go:102-112`) would refuse this repository's image for go-mini.
- **The problem:** neither `README.md:8,13` nor the profile says the pin is provisional. The open item about the image manifest exists only in the PR body.
- **Fix:** add a provisional-pin note that cites entry 97 to the README and the baseline's `note`. When the image is re-pinned, change `:38` to the go-mini image's own digest and re-record the baseline.

**L3. The reference change breaks rule 1 at `math.MinInt64`.**
- **Where:** `task.json:4` (rule 3, "like its absolute value"). The reference returns three positive parts for `Split(math.MinInt64, 3)`, so the parts do not add up to `c`. I confirmed this in a probe. The hidden test does not cover the case, but the package says it adds "without overflow" (`money.go:3-4`).
- **Fix:** either state the domain in the requirement (`c > math.MinInt64`, or return `ErrOverflow`), or compute the magnitude as `uint64`, as `String` does (`money.go:56-59`).

**L4. The acceptance record is not machine-readable, unlike #170's.**
- **Where:** `fixtures/m1/go-mini/README.md:19-29`. #170 keeps `reference_digest`, the counts at the base and the counts with the reference in `baseline.json`. go-mini has them only in README prose.
- **Fix:** if H1 commits the files, this goes away. Otherwise add an `acceptance` block shaped like #170's.

**L5. py-mini's profile, not go-mini's, is the inconsistent one.**
- **Where:** `fixtures/m1/profiles/py-mini.json:5`, and the golden `internal/authority/testdata/project-created-v1.json:5`. Both still use `file:///var/lib/adc/remotes/py-mini.git`, which the sandbox refuses (#226 entry 28, still open).
