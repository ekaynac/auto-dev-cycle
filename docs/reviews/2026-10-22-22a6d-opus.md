### High

**H1. A reviewer that repeats its decision stops the repair at round 3, under an operator configuration hold. BLOCKING.** `internal/review/review.go:614` (`seal`: a decision's ref ID is its content digest), `internal/graph/records.go:122` (an ID with two lineages is ambiguous), surfaced by `graph.Successor`'s accumulated inputs and `intent.Build`
- **Input:** `TestANoGoRepairsTheBuild`'s reviewer, which returns the same `noGoDecision` bytes every round, run until round 3 runs.
- **Result:**
  - Rounds 1 and 2 run.
  - Round 3's builder intent is refused: "intent: an acceptance-derived ref among the inputs: its ancestry is not resolvable: sha256:…7d5010fd (ancestor sha256:…24125dd5)". Here `…7d5010fd` is round 1's findings view, and `…24125dd5` is its decision, whose content round 2's decision shares.
  - The build is held `source_invalid_config` on "runner: failed" (`ErrAcceptanceInput` is a `contentFault`), owned by the operator. Nothing clears it: a retry meets the same refusal.
  - With a different decision each round, the same run reaches round 6 and the rail.
- **Cause:**
  - Both rounds' decisions have the ID `sha256:…24125dd5`, the content digest, but different lineages: each round's gate refs.
  - `graph.Records` marks that ID ambiguous and resolves it to nothing. The builder-safe check of `findings-1` therefore cannot resolve its decision, and the I18 walk refuses it.
  - Round 3 is the first round that takes two rounds' findings.
- **Why it blocks:** the promise is that "the rounds rail bounds repeats". A reviewer that keeps finding the same defect, because the builder failed to fix it, is the ordinary case for repeated no_go. In that case the repair stops at round 3 under a hold that names the operator's configuration, and no change of configuration clears it.
- **The row:** `TestANoGoRepairsTheBuild` checks only that round 3's build node is recorded, not that it runs.
- **Fix:** one of:
  - give a decision ref an ID that is unique per result (for example, sealed over its lineage, or the result's id);
  - have `graph.Records` treat a content-addressed ID with several lineages as several records, resolved by lineage;
  - have a repair round take only its predecessor's findings and candidate, not accumulate them (a change to 13's design: the lead's decision).

  Then extend the row: round 3 must **run** with the repeated decision, and a third repeat must reach the rail.
