### Medium: OBLIGATION

**M1. The cleanup can remove a pre-existing image, including the pinned one this host's gate resolves.** `scripts/prepare-go-image.sh:277-284`
- **Cause:** `rmi -- IDs` removes every instance of the list by ID. A build that reuses its layer cache, with unchanged inputs (a rebuild of one project while the other changed, or a retry), adds the *existing* image to the new list. The image keeps its old ID.
- **On this host:** the pinned `prepared-go` instance (`d1a29857…`) is exactly such an image, already shared by several local lists.
- **Input:** rebuild with unchanged inputs, and any check after the build fails or is cut, for example `PREPARE_GO_IMAGE_TIMEOUT` on `cp`.
- **Effect:** the cleanup's `rmi` removes the image, unless podman refuses it for its names. Whether `RepoDigests`-only names make podman require `--force` is [INFERENCE], untested here.
  - `sandbox.Host.Resolve` never pulls, so the gate and any launch on this host then fail `ErrImage` until the pin is pulled again.
  - It fails closed, but this is the "image that is not this build's" that question 2 asks about.
- **Fix:**
  - Record `podman images --all --quiet --no-trunc` before the build. In the cleanup, `rmi` only the IDs not in that set, and say which pre-existing ones were kept.
  - Keep `rmi` without `--force`, as now.
  - Add a fake row where an instance ID was already in storage before the build: it must not be removed.

### Low: OBLIGATION

**L1. `Resolve` can refuse a correct pin on a host that holds both platforms' instances under the index digest.** `internal/sandbox/image.go:68-102`
- **Probe (real 4.9.3, this arm64 host):** `image inspect name@<index>` returned the **amd64** instance when both instances carry the index in their `RepoDigests`. `Resolve` would then refuse it (`ErrImage`, "the image is linux/amd64").
- **Fails closed:** the wrong platform never runs, and the run is by the resolved ID with no `--platform` (`run.go:194`). So the run-time claim "never the wrong platform" is true.
- **But "resolves to the host platform's ID" is not always true.** It is a false block on any host that pulled both instances, which this host has done for the Go base.
- **Fix:** when the inspected image is not the host's platform, list the images whose `RepoDigests` contain the pin (`podman images --digests --format json`, filtered by reference). Take the one whose OS and architecture are the host's, and refuse only if there is none or more than one.

**L2. `instances` refuses a correct list in two real storage shapes.** `scripts/prepare-go-image.sh:108-118`
- **The same ID on two rows:** `podman images` prints one row per repo:tag, so an instance image that also has a tag appears twice. `awk` prints its ID twice, and the `^…$` regex refuses it as "two images".
- **An instance pulled through a list:** its `.Digest` is the list's digest, not the instance's, as both of the golang base's instances show. So `.Digest` finds nothing.
- **Effect:** both fail closed, as "cannot find each image".
- **Fix:**
  - De-duplicate the IDs (`awk '$1 == d && !seen[$2]++'`).
  - Map by `podman image inspect --format '{{json .RepoDigests}} {{.Digest}} {{.Id}}'` over the candidate IDs, or match any `@<digest>` in `RepoDigests`. Do not use `.Digest` alone.

**L3. The fake `podman images` omits two things real 4.9.3 shows.** `cmd/adc/adapter_test.go:230-330`
- **Missing:**
  - the list itself, as a row of its own with its own digest;
  - unrelated images, including list-pulled ones whose `.Digest` is a list digest shared by two IDs;
  - a tagged instance on two rows.
- **Fix:** add these rows to `STATE/images`. The happy path must still pass with them, and M1's and L2's rows build on them.
- **What the fake does model correctly:** create and run by NAME give the native platform's image; by ID, that image.

**L4. A partial cleanup tells the operator to do something that no longer works.** `scripts/prepare-go-image.sh:284`
- **Input:** `manifest rm` succeeds and `rmi` fails.
- **Effect:** the message says "run podman manifest rm NAME, and podman rmi its images". But the list is gone, so the operator can no longer find "its images".
- **Fix:** print the instance IDs in that message.

### The four questions
1. **Can a check run on the wrong platform's image, or one not in the list?**
   - **Not in the list:** no. Each ID is mapped from the list's own instance digest, and an image manifest digest names one config, so one ID.
   - **The wrong platform:** no. The per-platform checks run by ID. If the list's annotation disagreed with the image, the per-platform adapter digest (Node's bytes differ) would refuse it.
   - **What remains:** only false refusals (L2).
2. **Can the cleanup remove an image that is not this build's?** Yes: a pre-existing image the cached build reused, the pinned one on this host included (M1). The list it removes is this build's, because a pre-existing NAME is refused before the build.
3. **Is the run-time claim true, including a two-platform list on an amd64 host?**
   - **No wrong platform runs:** true. `Resolve` checks OS and architecture, and the run is by ID.
   - **On an amd64 host that pulled only its native instance:** it resolves that instance [INFERENCE: symmetric to the arm64 behaviour seen here].
   - **On a host holding both instances under the index digest:** it can refuse (L1, shown on this host with the Go base).
4. **Do the fake-podman rows model 4.9's behaviour faithfully?**
   - **The bug itself:** yes (NAME → native, ID → its own platform). The old script fails the happy path.
   - **`podman images`:** too clean (L3).
