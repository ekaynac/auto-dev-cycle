## Opus pre-review of #230

Verdict: **GO with changes**. No Critical or High findings. The tests pass at head: `go test` of blobstore, api, daemon and cli, run in a scratch worktree that has since been removed.

**What I checked and found sound**
- **Bounds:**
  - `Upload` holds `s.up` from the per-actor count and byte check through the rename (`uploads.go:74-101`).
  - I ran 40 concurrent distinct 1 MiB uploads by one actor under `-race`. Exactly 32 were accepted, so no race lets an actor exceed the bounds.
  - A repeat of the same digest is not double-counted. Claimed and purged files drop out of the accounting because it is computed from the directory.
  - Removing the early 413 is safe today: `MaxBytesReader(lim.bodyBytes = 1 MiB)` plus `LimitReader(1 MiB + 1)` still caps the read. Authentication happens before the body is read.
- **Path safety:** the actor has to match `^act_[0-9a-z]{26}$` and the digest has to match `digestRe`, so the path cannot be walked out of. A `../` actor is tested.
- **Claim:**
  - It refuses at exactly `PT1H` (`!now.Before`), and that boundary is tested at `uploads_test.go:46`.
  - It re-verifies the digest through `Put(f, digest)`.
  - An actor can only claim its own directory.
- **Authorization:**
  - Only operators and supervisors may upload; other kinds get `actor_kind_refused`. Only operators may list (`operator_only`).
  - `blob.purge_upload` goes only through `authorizeSystem`.
  - Revoked actors are refused through `p.Live`.

### Medium

**1. A HEAD request creates an upload (`internal/api/blobs.go:69-82`).**
- Go's mux sends HEAD to the `GET /v1/blobs` pattern. HEAD is not `MethodGet`, so it falls through to the `default:` branch and calls `Upload` with an empty body.
- I confirmed it against the daemon: an operator's HEAD returned 200 and stored an upload of `sha256:e3b0…b855` (0 bytes).
- So a read verb changes state, the route is not in `routeList` or the parity harness, and non-uploader kinds get `actor_kind_refused` instead of `operator_only`.
- **Fix:** make the upload case `case r.Method == http.MethodPost:`, answer anything else with 405, and add a HEAD test.

**2. A purge event can contradict the state on disk (`blobs.go:126-137` with `uploads.go:137-172`).**
- `PurgeExpired` lists the uploads, then commits the event, all outside `s.up`. Two things can then slip in before `Purge` takes the lock:
  - A renewal (a re-upload of the same digest) changes the mtime. `Purge` then keeps the file, although the log says it was purged.
  - A `Claim` whose `now` was taken just before expiry, and which was waiting on `s.up`, publishes the bytes after the purge event.
- In both cases the log records a purge that did not happen. This matters once P3 references uploads.
- **Fix:** under `s.up`, re-check the mtime and rename the upload to a tombstone such as `uploads/<actor>/.purging-<hex>` that `Claim`, `Upload` and the count all ignore. Then commit the event, then remove the tombstone. At start, finish any leftover tombstones by replaying the same key. Alternatively, have `Claim` take a clock function and read the time under the lock.

**3. `Claim` cannot be retried after a failed commit; this needs settling before P3 (`uploads.go:135-157`).**
- `Claim` publishes the bytes and deletes the upload in one call.
- If P3 calls it inside the command and the transaction then fails, the upload is gone. A retry with the same idempotency key gets `ErrNoUpload`, which P3 turns into `stale_expected_state`.
- **Fix:** split it into a check-and-publish step that keeps the upload, and a `Drop(actor, digest)` called after the commit. Or document that P3 must claim only after its commit succeeds.

**4. The purge event borrows the API schema (`blobs.go:36`).**
- Every other event kind is validated against a `records/` schema, for example `records/note` and `records/approval`.
- Pinning the log's payload to `api/blob-upload` means any later change to the API answer silently changes how old log entries are typed.
- **Fix:** add `schemas/records/blob-upload-purged.json`. It can be a thin `$ref` or a copy. This costs about 15 lines.

**5. One bad entry stops all purging (`uploads.go:113-114, 125-130`; `blobs.go:121-123`).**
- A stray non-directory under `uploads/`, a non-regular file, or a file with a non-hex name makes `Uploads` return an error.
- `PurgeExpired` then skips every upload (`if err != nil … continue`), so expiry stops for every actor and `GET /v1/blobs` returns 503 indefinitely. It does log the failure every minute.
- **Fix:** skip and log malformed entries one by one, and keep purging the well-formed ones.

### Low

**6. Clocks (`blobs.go:82`).**
- The upload time comes from `time.Now`, while the purger uses `d.clock`.
- In production these are the same clock. Under an injected clock, though, uploads never expire, or expire at once.
- The mtime is also the source of truth. On a filesystem with coarse timestamps, or after a restore that resets mtimes, the `expires_at` the client was given drifts from what is enforced.
- **Fix:** add a `Now func() time.Time` to `api.Blobs`, wired from `d.clock`, and return the `UploadedAt` read back from the file.

**7. Two separate constants hold the 1 MiB cap (`server.go:257-261`).**
- With the early 413 skipped, the upload cap is really `lim.bodyBytes`. If it ever drops below `MaxUploadBytes`, uploads under 1 MiB would be refused as over-bound.
- **Fix:** give the blobs route its own `MaxBytesReader(MaxUploadBytes)`, or add a test that `bodyBytes >= MaxUploadBytes`.

**8. `--attach` shape (`cli.go` attach block).**
- `{name, digest}` is a reasonable start for P3. Two problems:
  - `filepath.Base` drops directories, so `hidden/a/test.py` and `hidden/b/test.py` both become `test.py`.
  - The flag is offered on every action command, although only `task.create` will accept it.
- **Fix:** refuse duplicate names now, and record that P3 owns the field name and path form, which will likely be relative paths.

**9. Purge events reach non-operators.**
- `blob.upload_purged` streams digest, actor and size to anyone holding a `blob`-domain read grant, while the upload list is operator-only.
- **Fix:** either note this as intended, or limit the streamable paths to digest and expiry.

**10. Fault evidence is discriminating for the F case but has one gap.**
- M1 (foreign actor) and M2 and M3 (bounds) each fail the right test.
- Nothing covers the commit-then-remove order. A mutation that removes the bytes before committing the event would pass every test.
- **Fix:** add a test seam (for example, make `remove` fail after the event) asserting that the event is committed and the bytes stay.

### Contract questions
- **`upload_bound_exceeded`:** justified. No existing `failed` reason fits a size or quota refusal, and `stale_expected_state` and `action_not_granted` would mislead.
- **Reusing `api/blob-upload` for the purge event:** acceptable only as a stopgap. I prefer the small `records/` schema (finding 4).
- **`attachments: [{name, digest}]`:** reasonable for P3, with the caveats in finding 8.
- **Allowing supervisors to upload:** fine, and consistent with P3's supervisor-created tasks. Record it in the row.
