### Medium

**M1. A record whose id is an acceptance digest but whose content differs hides the acceptance parent.** `internal/intent/intent.go:151`
- The walk checks only `rec.ContentDigest`. The restored `9462b0d6` also checked `hidden[id]`, and this PR deleted that check as "redundant: no row can distinguish it".
- This row distinguishes it. Input `tree-1` has lineage `[sha256:eee…]`. The store holds `rec("sha256:eee…", "2", "build")`: id equals the acceptance digest, content is another digest. Probe result: `Builder` returns `err=<nil>`.
- Nothing enforces "a blob ref's id is its digest": `knowledge.Seal` and `schemas/records/ref.json` don't check it, and fixtures seal blobs under names.
- It is not reachable today, because every producer records `Lineage: []string{}` and blob ids equal their digests. But this is the "alias / id equal to a digest" route the contract names.
- **Fix:** `case w.hidden[id] || w.hidden[string(rec.ContentDigest)]:`. Add the row above. Rename rows `intent_test.go:97-98` ("by its id"): they pass only by fail-closed resolution, because the acceptance id has no record.

**M2. The edge bound is checked after a whole lineage has been enqueued.** `internal/intent/intent.go:160-170`
- `enqueue` adds `len(parents)` to `w.edges`, then fills `walked` and the queue for every parent. `over()` only runs at the next `resolve` or at the end of `start`.
- Lineage has no `maxItems` in `schemas/records/ref.json`, so one record can carry any number of parents.
- Probe: `maxEdges=10`, one input with 200,000 parents. It is refused, but only after `walked=200001` entries and a 200,000-entry queue have been allocated.
- Ids are also not counted toward the byte bound until they are resolved.
- **Fix:** have `enqueue` return an error, and refuse when `w.edges+len(parents) > maxEdges` before the loop. Count `len(p)` toward `idBytes` when a parent is enqueued. Add a row with one wide lineage that asserts `len(w.walked)` stays within the bound.

**M3. The PR body's residual tells P22a to drop the acceptance edge from gate lineage, which would let acceptance test ids reach the repair builder.** PR body "Residual", item 3; `docs/design/m1/01-invariant-inventory.md:250`
- The gate's D55 report lists blocking test ids. These include failing acceptance tests from the overlay (`internal/gate/receipt.go:205-212`).
- `gate.go:20-26` makes those failures a builder repair (`found/gate_test_failed`).
- If P22a follows the residual and records the overlay "as a run input, not a lineage parent", the report's record is clean. `Builder` then admits it, directly or through a review decision, since a builder may take a decision. Acceptance-derived ids reach the builder, which is I18's core route. It would also break KA1, which inherits restrictions through lineage.
- **Fix:** replace the residual. Lineage stays truthful. The reviewer's admission of the sanitised gate report becomes an explicit controller declassification on the record (for example `RefRecord.Sanitised`, set only by `gate.Result`), honoured only by `Reviewer`. The builder never takes an acceptance-derived gate report. Name this in #226 for P22a.

**M4. `TestRecords` does not check the lineage and producer terms of the ambiguity rule.** `internal/graph/records_test.go:46-48`
- The ambiguity rule compares digest, lineage and producer, but the only row ("twice") differs by digest.
- Probe: with the rule reduced to `prior.ContentDigest != rec.ContentDigest`, `TestRecords` still passes.
- Under that mutation, a review's ref re-recorded by an `integration` node with the same identity would resolve as last-write-wins with producer `integration`. That defeats the freshness check at `intent.go:89`, and an empty-lineage re-record could hide a parent.
- **Fix:** add rows for the same id and digest with a different lineage, the same id and identity with a different producer, and a result ref that conflicts with an `extra` ref. Each must resolve to nothing.

### Low

**L1. The "no dedupe before enqueueing" mutation (I5) is not really caught.** `internal/intent/intent_test.go:168-174`
- Probe: moving dedupe to dequeue (`enqueue` appends every parent; the loop skips walked ids) keeps every id at one lookup. `TestIntent*` passes.
- So "deduplicated before enqueueing" is not asserted, and the body's claim for I5 overstates it.
- **Fix:** have the test resolver record the peak queue length, or check `len(queue) ≤ distinct ids` inside `start`.

**L2. Freshness is decided by producer only.** `internal/intent/intent.go:89`
- Probe: a review's decision content re-recorded under `relay-1` by an `integration` node passes `Reviewer` (`err=<nil>`).
- No current producer re-emits review content (the carry_over attestation holds a tree), so this is not reachable today.
- **Fix:** have `Records` expose the content digests of review-produced records, and have `Reviewer` refuse any resolved input whose content digest is one of them.

**L3. `graph.Records` decodes every result of every task on each call.** `internal/graph/records.go:41`
- It loads each result plus its node record, then keeps an unbounded map of the task's refs. The walk is bounded but the resolver is not, and cost grows with the whole store.
- Full scans are an existing convention (`history.go`).
- **Fix:** index results by task (prefix `task/…`), or bound the per-task ref count and refuse past it.

**L4. Smaller gaps:**
- An empty `In.Acceptance` passes everything. **Fix:** have `Records` also return the task's acceptance digests from its own records, instead of trusting the caller.
- The no-resolver and omitted-input rows (`intent_test.go:112-122`) run only `Builder`, though the body says every refusal row runs for both roles.
- No row checks that the byte bound passes at exactly the bound. It isn't claimed inclusive, so this is informational.

But the obligation is recorded only in `01-invariant-inventory.md:249`. The P22a row (`docs/design/m1/00-slice-plan.md:645`) names "an acceptance ref as a build or review input" as its fault, but not the fold check, the `intent.Builder`/`Reviewer` calls, or the M3 constraint. **Fix:** the lead should add a #226 entry or update the P22a row.
- **Gate ids verbatim as quoted data: acceptable.** `Report` lists only blocking findings (`internal/gate/receipt.go:205-212`), so candidate-controlled ids reach a reviewer only when the gate has already blocked. A reviewer's GO cannot clear a failed gate on its own `[INFERENCE, from the requirement and gate ownership code]`. The ids are cut to 256 bytes, and the reviewer has no tools and returns a typed decision. The residual stated in the body is honest. The quoted-data renderer stays a P22a obligation; tie it to the `hostile-gate-output` fixture.
