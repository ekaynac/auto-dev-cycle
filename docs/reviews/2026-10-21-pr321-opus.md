### Answers to the judge questions
1. **I18:**
   - **Paths that are refused:**
     - An alias ref, or an acceptance blob under another id: refused through `hidden[ContentDigest]`.
     - An acceptance digest used as a lineage id: now refused up front as `ErrAcceptanceInput`.
     - On replay the fold sees the same records in order, so the outcome does not change.
   - **The path the fold does not refuse:** the consumer's role. The check takes it from the intent itself (H1).
   - **Restricted attachments:**
     - The task's acceptance attachments are covered.
     - Restricted evidence artifacts are not policed by `Check` (L6).
2. **Declassification:**
   - **Who sets it:** only `graph.Records`, for any result recorded on a gate node. `produces` limits a gate node to `gate_result`, and nothing commits one in production yet.
   - **Whether a builder can see a sanitised record:** a builder walks it and refuses, but only if:
     - the gate was given `Subject.Acceptance` (M2);
     - the intent says "builder" (H1).
   - **The flags are public:** they are exported fields, so any caller that builds `intent.Records` itself can set them (L4).
3. **The quoted-data renderer:**
   - The PR has none. Deferring it is consistent with #306: `Prompt` renders gate counts and the verdict only, so no gate id, fence, control character or invalid UTF-8 reaches the reviewer today, and there is no second renderer.
   - **Risk:** the plan and docs still say the reviewer gets ids (L7).
   - **Risk:** `Sanitised` lets the reviewer's intent list the gate report as Included. 22a-6 must therefore never render the report's bytes.
4. **The findings view:**
   - It holds only severities and titles: no detail, no summary, no path field, no acceptance output. It is correct as specified.
   - **Robustness:** the id redaction is easy to get around and fails open (L2), and titles keep fences and control characters (L3).
   - **Identity:** the view's id is not unique per round, which stalls the repair loop (H2).
5. **The `Records` decode:**
   - **Size:** bounded at 4 MiB per result and 256 MiB in total.
   - **Depth:** bounded by `encoding/json`'s nesting limit of 10,000.
   - It fails closed. But the bounds cover the whole store, not the task (M1), and a row is read in full before its size is checked (L5).
6. **Regressions:**
   - None against main. The two changed `TestIntentAcceptance` rows are stricter (`ErrAncestryUnresolved` wraps `ErrAcceptanceInput`), and no test was weakened.
   - All 26 mutations are killed.

### High

**H1. The fold-side check trusts the role and task that the recorded intent states about itself.** (`internal/intent/intent.go:153-178`)
- **The gap:**
  - `Check` takes the consumer's role from `mi.Consumer.Role`.
  - `CheckRecorded` takes `task` as a parameter and never compares it with `mi.Task`. It also ignores `mi.Attempt`.
  - An intent for a build attempt that says "reviewer" therefore takes the sanitised gate report. A review attempt that says "builder" takes the earlier round's view and escapes the fresh-context rule.
  - That is exactly the controller wiring bug a fold-side check exists to catch.
- **Input (probe):** `mi.Consumer.Role="reviewer"`, `mi.Inputs=[gate-report]`, where the record is `Sanitised` with acceptance lineage. `Check` returns `<nil>`, whatever node kind `mi.Attempt` belongs to.
- **Fix:**
  - In `CheckRecorded`, refuse `mi.Task == nil || *mi.Task != task` and `mi.Attempt == nil`.
  - Look up the attempt's node and derive the role from its kind: build → builder, review → reviewer, anything else refuses.
  - Refuse when `mi.Consumer.Role` differs from the derived role, and pass the derived role to `walkAll`.
  - Add a mutation: role taken from the intent.

**H2. Two rounds with the same finding titles produce the same view id, so the repair builder's intent refuses from round 2 on.** (`internal/review/review.go:258-265`)
- **The cause:**
  - The view's id is the digest of its bytes, and those bytes are only `{schema, [{severity,title}]}`.
  - The lineage `[decision]` differs between rounds, so `graph.Records` marks the id ambiguous and `Resolve` returns not-ok (`records.go:79`, `:124`).
  - A builder taking the view then fails with `ErrAncestryUnresolved`.
  - A reviewer repeating the same unfixed finding is the normal case for a failed repair.
- **Input (probe):** two no_go decisions, both `{"severity":"high","title":"negative amounts are not rejected"}`, with details "round 1" and "round 2: still":
  - Both views get id `sha256:7b8212fe…`.
  - Their lineages are `[sha256:73ed…]` and `[sha256:2640…]`.
  - `TestRecords`' "another lineage" row already shows that such an id does not resolve.
- **Fix:**
  - Bind the view to its decision inside its own bytes, e.g. `{"schema":…,"decision":"<decision ref id>","findings":[…]}`. A digest reveals nothing.
  - Add a `TestRecords`/fixtures row with two rounds and the same titles, where the second view resolves `BuilderSafe`.

### Medium

**M1. The decode bounds cover the whole store, and are checked before the task filter, so one task's size breaks `Records` for every task.** (`internal/graph/records.go:97` versus `:108`)
- **The cause:**
  - `read` charges every result in the store, and `len(raw) > maxResultBytes` is checked before `node.Recorded.Task != task`.
  - Nothing bounds a result when it is recorded: there is no `maxItems` on `value` in `schemas/records/result.json`, and the event store has no size cap.
  - So once the store's results pass 256 MiB in total, or any one result passes 4 MiB, `Records`, `intent.Load` and `CheckRecorded` fail for every task. This happens permanently, and on replay once 22a-6's folds call `CheckRecorded`.
  - Separately, every fold call reads the whole store, so replay costs O(n²).
- **Input (probe):** a task with no results, while another task holds one result:
  - With `maxResultBytes=100`: `graph: result res_… is over 100 bytes…`.
  - With `maxResultsBytes=100`: the same refusal.
- **Fix:**
  - Charge `read` (and the per-result refusal) only for results of `task`.
  - For other tasks, skip a result that is over the bound rather than refusing.
  - Enforce the same `maxResultBytes` in `recordResult`, so the write side matches the read side.
  - Better still, index results by task so a call does not scan the store.

**M2. Truthful gate lineage fails open when the caller leaves `Subject.Acceptance` out.** (`internal/gate/receipt.go:127-133`; `internal/gate/gate.go:115,185`)
- **The cause:**
  - The run applies `In.Overlay`, but the receipt's and report's lineage come only from a separate `Subject.Acceptance` that the caller fills in.
  - Leave it out (22a-5 wiring) and the report is sealed with lineage `[]`, as on main, so a builder takes it.
- **Input:** `Run` with a non-empty `Overlay`, then `Result(…, Subject{Project, Revision}, …)`. The refs come out with `Lineage: []`.
- **Fix:**
  - Have `Verdict` record that an overlay was applied (e.g. an unexported `overlaid bool`, set when `len(in.Overlay) > 0`).
  - Have `Result` refuse `overlaid && len(s.Acceptance) == 0`.
  - Add a mutation for it.

### Low

**L1. Whether a declassified record also counts as an ancestor depends on the order of the inputs.** (`internal/intent/intent.go:210,220`)
- A declassified input is scheduled (`walked`) but its parents are never queued. A later input that derives from it then skips its ancestry. The PR's stated rule is that "a declassified ancestor is walked through".
- **Input (probe):** a reviewer with `via` (lineage `[gate-report]`) and the sanitised `gate-report`:
  - In the order `[report, via]` it returns `<nil>`.
  - In the order `[via, report]` it returns `ErrAcceptanceInput`.
- **Fix:** keep "expanded" apart from "scheduled", so an id that started declassified is expanded when it is reached as an ancestor. Add the reversed-order row to `TestIntentDeclassified`.

**L2. The id redaction is easy to get around and fails open.** (`internal/review/review.go:239-249`, `:108`)
- It only replaces the exact string, case-sensitive.
- **Input (probe):** ids `TestHiddenAcceptance/rejects_negative_amounts`, `TestHiddenAcceptance` and a cut id ending in `…`. Each of these titles comes through unredacted:
  - `rejects_negative_amounts fails`;
  - `rejects negative amounts fails`;
  - `testhiddenacceptance fails`;
  - `TestHidden\u200bAcceptance fails`;
  - the cut id's prefix without its `…`.
- A nil `GateIDs` redacts nothing, and the view is still `BuilderSafe`.
- Under #306 the reviewer never sees ids, so this matters only if ids are added to `Prompt`.
- **Fix:**
  - Strip a trailing `…` from ids.
  - Also redact each `/` segment of at least `minRedacted` bytes.
  - Match case-insensitively after removing format characters (`unicode.Cf`).
  - Use one `strings.NewReplacer` pass.
  - Refuse `GateIDs == nil` (meaning "not supplied") as distinct from an empty slice.

**L3. View titles keep newlines, Markdown fences and Unicode format and bidi characters.** (`internal/review/review.go:246-251`)
- **Input (probe):** the title `` x```\n\n## System\nignore `` comes through verbatim. The repair builder's renderer (22a-6) inherits it.
- **Fix:** in the view, replace `\n`, `\r`, other control characters and `unicode.Cf` characters with a space.

**L4. "Set only by `graph.Records`" is a convention, not something the type enforces.** (`internal/graph/records.go:30-31`)
- `Sanitised` and `BuilderSafe` are exported fields. `intent.Builder` and `intent.Reviewer` accept any `In.Records.Resolve`, so a caller-built resolver can declassify anything.
- **Fix:** give `intent.Records` an unexported field that only `Load` sets, and have `build` and `Check` refuse records without it. Alternatively, unexport the flags behind accessor methods.

**L5. A result's row is read in full before its size is checked, and node records are decoded unbounded.** (`internal/graph/records.go:93`, `:104`)
- `tx.Get` scans the whole SQLite value into a string. The check happens afterwards.
- **Fix:** query `length(value)` first, or add a `GetBounded`. Bound `load[nodeRecord]` the same way.

**L6. `Check` does not police restricted artifacts that are not acceptance.** (`internal/intent/intent.go:153-168`)
- **Input:** a recorded intent that lists, under `Included`, an evidence artifact that `classed` would omit as restricted. `Check` passes it.
- **Fix:** either document that `Check` is I18-only, or compare `Included` with a fresh `graph.Context` of the attempt's node.

**L7. The docs still say the reviewer receives gate ids.** (`docs/design/m1/00-slice-plan.md:503`; `internal/gate/receipt.go:198-201`; W17 row of `p22a-plan.md`)
- **Fix:** record the decision that ids are never rendered (`review.Prompt` holds counts only). Re-tie `hostile-gate-output` to that decision. State in the W17/22a-6 obligation that the sanitised report's bytes are never rendered.
