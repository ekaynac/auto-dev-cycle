### Medium

**M1. A full Ready backlog can never be emptied, which breaks liveness once P22a activates intake.**
- Where: `internal/authority/task.go:145` (the logic's bound) and `:257-258` (the fold's bound).
- Two kinds of task count toward the five but can never leave Ready:
  - a supervisor's task: it has no approval and no way to get one, because `Minted` means it is never proposed;
  - a task whose approval was revoked: P22a's first-claim re-check will refuse it.
- No action removes a task from Ready. So one granted supervisor making five tasks, or one revoked operator who made five, blocks the project's intake for good. Revoking the supervisor does not free the slots.
- Fix: before P22a activates `intake`, register an owner for removal (a `task.cancel` or `task.withdraw` action, or an approval path for a supervisor's task) in the PR's deviations and the backlog. Name it as a P22a prerequisite. Do not drop these tasks from the bound instead: that would let a supervisor create tasks without limit.
- The deviation "supervisor tasks without approval count toward the bound" is acceptable only together with that follow-up.

**M2. Replay compares stored approvals with what the current code would build.**
- Where: `recordTaskApproval`, `task.go:280-285` (`sameCanonical(TaskApprovalOf(...), a)`), and `addTask`, `:248` (`acceptanceOf`).
- Approval equality includes the constant `taskApprovalReason` (`:53`) and every field `TaskApprovalOf` sets. Issue #147 already plans to pass the command's `--reason` into the approval, and a change of class text would have the same effect. After either change, every recorded approval stops matching, and startup is wedged on rebuild.
- P1 avoided this deliberately: `addProject` reads only what the record needs.
- Fix: in the fold, check only the binding fields:
  - `object` = `{task, t.ID, 0, t.SpecDigest}`;
  - actor = the creator, who is an operator;
  - action, project, `expected_state` = 0, and policy `none`;
  - `ContentDigest(a.Scope) == t.SpecDigest`.
- Keep the full `TaskApprovalOf` equality only in the logic's own tests.
- Then add a frozen `task.created/v1` + `approval.recorded/v1` replay golden now, under `internal/eventstore` or `internal/authority` testdata. The PR's own note says the fold reads the whole payload, so a golden is what makes that safe to change later. It is cheap, and it is not a test-budget line.

### Checked and fine
- **Approval binding:**
  - The digest is RFC 8785 over the whole scope (title, requirement, project, and each attachment's name and digest). The fold recomputes it from the stored spec, so it covers exactly what the builder and reviewer will see.
  - A proposal-less approval is admitted only by the creating operator, whose kind is operator and who matches `ev.Actor`. It must come once, in the same command (`*ev.Command == t.Command`), at the event's time, with `/` keys refused.
  - A supervisor cannot produce or forge an operator approval, and an approval in a later command or of no task is refused.
  - The `recordApproval` → `recordTaskApproval` delegation keeps the subject and actor checks ahead of it.
- **Uploads:**
  - `Publish(c.Actor, …)` is per actor, so another actor's upload gives `ErrNoUpload` → `stale_expected_state`.
  - `Drop` runs only when the commit is `Applied && !Replayed`.
  - A refused command keeps its uploads, and a repeated digest is harmless.
- **Bound:** the count is checked inside the writer's transaction and again in the fold, so it is race-free. `ready_backlog_full` (`failed`) is justified: `capacity_reserved_full` is `could_not_run` and comes with a hold.
- **Revocation:** handling `actor_revoked` matches 04 for operator approvals, which have no grant. The `approver/` index is deleted when an approval is revoked, and the status is kept on the record.
- **Inert:** `task.create` stays in `deferred`, `handlers()` has no entry for it, and `TestTaskCreateStaysDeferred` runs the real `adcd` and `adc`.
- **Fault evidence:** discriminating. The four other-digest variants plus the positive control fail under mutations 1 and 3 as the PR claims.
- **Deviations:** acceptable:
  - base names from the CLI: they are valid single-segment paths;
  - the fixed reason: acceptable, but see M2 before #147 changes it;
  - supervisor tasks counting toward the bound: only with the follow-up in M1.
