## External review of #230 (Mythos, 2026-10-13)

Verdict: GO with changes

Read-only review of 2a3b16c against origin/main (daf58d8). `go test ./internal/blobstore/... ./internal/api/... ./internal/daemon/... ./internal/cli/...` passes. No Critical or High finding. The two Medium items should land before or with P3, which is the first consumer of the event subject and of `Publish`/`Drop`.

### Judgement by question

1. **Bounds.** Held. The count and byte check, the temp write and the rename all run under one lock (`internal/blobstore/uploads.go:73-118`), so two concurrent uploads by one actor cannot both pass at 63 or at 31 MiB. The body is capped at 1 MiB twice before the store reads it, and the store re-checks the length. Tombstones are not counted, but a tombstone exists only between set-aside and burial, and a failing burial aborts the run before a second one is made. Published-but-not-dropped uploads stay counted until expiry.
2. **Ownership.** Held. The actor comes from the authenticated principal, the digest is recomputed from the bytes, and both are matched against strict regexps before any path is built (`uploads.go:60-67`). Renewal is per actor directory, so uploading the same content reveals nothing about another actor's holdings. GET is operator-only; no route serves bytes.
3. **Purge.** Crash-safe and race-free as far as I can trace. Tombstone first with the mtime re-checked under the lock, event second under a key bound to actor, digest and mtime, removal last. Replay adds no second event because the writer fingerprints action plus input and the record is deterministic for a tombstone. `Publish` holds the lock through `Put`, so it cannot interleave with `Tombstone`. A concurrent second purge finds the file missing and skips, or replays the same key. The log cannot record a purge whose bytes were never set aside, and cannot miss one. The one honest gap is that a committed event can precede the bytes going for up to a minute when burial fails, which is the documented design.
4. **Publish/Drop for P3.** Sound. A retry republishes from the kept upload; `Drop` is idempotent. A published-but-never-dropped upload stays a live upload: counted, refused at `PT1H` exactly by `Publish`, purged within a minute after.
5. **Authorization and streaming.** POST is operator or supervisor, GET operator, 405 otherwise, all decided after authentication and before the body is read. The stream allow-list keeps only `digest` and `expires_at` of the payload, but the envelope's `subject` is the uploader's actor id (M1). Readers are operators or holders of an every-project read grant naming the `blob` domain, so exposure is narrow.
6. **Contract changes.** The new reason with HTTP 413 is coherent with the client's refusal path and the CLI exit. The two schemas are identical copies with a 1 MiB ceiling matching the constant; the record's description is wrong in one race (L2). Routes and parity rows are consistent and pinned.
7. **Fault evidence.** Discriminating. M1 and M2 to M4 each name a test that fails under the mutation; M5 proves commit-before-remove through an injected burial failure and a replay, which stands in for a restart. Missing: evidence that the stream withholds the actor (it does not, see M1) and that a purge leaves the uploader's object version unchanged (it does not).

### Findings

**Medium**

- **M1. The purge event's subject is the uploader's actor id. That moves the actor object's version and puts the actor id on the stream.** `internal/api/blobs.go:193` sets `Subject: u.Actor`. `actor.revoke` and `token.issue` bind the actor as their object with no custom version (`internal/authority/admin.go:92`, `internal/authority/tokens.go:75`), so their version is the max seq of any event on that subject (`internal/eventstore/writer.go:321`). Every purge of an operator's or supervisor's upload bumps that actor's version, and an `adc actor revoke --expect N` whose N was read before the purge is refused `failed/stale_expected_state` for a change that never touched the actor. Today that is recoverable, since actor.revoke is operator-only and no proposal binds the version, but it is a background job silently invalidating expected state on an unrelated object, and it will matter for P3 and any later two-person flow on actors. The same line defeats pre-review item 9: `redact` filters the payload only (`internal/api/redact.go:40-52`) and the envelope keeps `subject`, so "never whose it was" is not true on the wire.
  *Fix:* use a subject that is not an existing object, for example `u.Digest`. The writer only requires a non-empty subject. Add two assertions to `TestBlobUploadThroughTheCLI`: the operator's subject version is unchanged across `PurgeExpired`, and the streamed purge event contains neither actor id anywhere in its bytes. Update the comment at `blobs.go:40`.

- **M2. One unreadable or stuck entry stalls every actor's purges.** `PurgeExpired` returns on the first `Tombstone`, `recordPurge` or `Bury` error (`internal/api/blobs.go:166,172,175`), and the daemon only retries a minute later (`internal/daemon/daemon.go:247-258`). A tombstone whose burial keeps failing, say a permission fault on one actor's directory, means no upload of any other actor is purged again, their quota stays consumed by expired uploads, and a log line per minute is the only signal. Malformed entries are skipped one by one, but failures are not.
  *Fix:* continue the loop on a per-entry failure, collect the errors with `errors.Join` and return them at the end, returning early only on `ctx.Err()`. Add a case to `TestPurgeEventBeforeRemoval` with two expired uploads by two actors where burial fails for the first and the second is still purged.

**Low**

- **L1. The route's cap is not independent of the listener's.** `internal/daemon/server.go:261` still wraps the body at `lim.bodyBytes` for the blobs path; line 257 only skips the early plain-text 413. The comment at `internal/api/blobs.go:59` is misleading: lowering `bodyBytes` below the upload bound would make near-limit uploads fail with `upload_bound_exceeded` for no visible reason. *Fix:* skip the server wrapper for the blobs path too, or assert at serve time that `bodyBytes` is at least `MaxUploadBytes`, and fix the comment.

- **L2. The purge record claims the bytes were "never published".** `schemas/records/blob-upload-purged.json:5` and its generated doc. After `Publish` succeeded and the purge set the upload aside before P3's `Drop`, the digest is in the content store, as the PR description itself notes. *Fix:* "Its upload bytes are gone; the digest may remain in the store if a command published it before the purge."

- **L3. `Drop` after a renewal removes the newer upload.** `internal/blobstore/uploads.go:195`. If the actor re-uploads the same digest between P3's `Publish` and `Drop`, the renewed upload is removed and a second command referencing it gets `ErrNoUpload` although the blob is published. Nothing is lost since the content is identical, but P3 should know. *Fix:* record it in the P3 contract, or have `Drop` take the published `UploadedAt` and skip a file with a newer mtime.

- **L4. Error text prints a nil error.** `internal/blobstore/uploads.go:224` formats `err` with `%v` on the path where it is nil. *Fix:* drop the `%v`.

- **L5. Layering note, not a defect.** `PurgeExpired` and `recordPurge` put a system-principal writer into `internal/api`, which until now only read the store and relayed commands. Fine for P2. If P3 adds more system actions, consider a home under `internal/blobstore` so `api` stays the HTTP layer.

### Not found

I looked for and did not find: a path from a supervisor or agent to another actor's upload by publish, list, read or renewal probing; a way past the 1 MiB, 64 or 32 MiB bounds through concurrency or tombstones; a purge event without a tombstone or a removal without an event; a lock-order inversion, since the upload lock is taken before the store lock in `Publish` and nothing takes them the other way; an idempotency fingerprint that varies across replays; a bearer path to `blob.purge_upload`, which is absent from the action registry and refused by `authorizeSystem` for non-system actors.
